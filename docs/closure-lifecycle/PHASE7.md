- 작성일: 2026-10-10
- 브랜치: `experiment/closure-lifecycle-performance`
- 출발: 6단계 `52a40b5eec3ba8bbcb06855da0d29c7fc2559e40`
- 방향: 기존 Concurrent 빌드에 포함. 추가 코어 빌드 분기 없음.
- 상태: 활성 경계 콜백 최적화와 공개 helper API 검토안. 공개 exports 미연결.

## 남아 있던 불필요한 호출

6단계는 등록된 경계가 모두 활성 상태여도 `blocks` 콜백을 연결했다.
콜백 안에서 중단 개수가 0임을 확인하고 false를 반환하므로, 갱신마다 불필요한 함수 호출이 남았다.

이번에는 중단 경계가 하나 이상 있을 때만 `blocks`와 `reparent`를 연결한다.
첫 pause와 초기 비활성 경계의 mount에서 설치하고, 마지막 resume 또는 중단 경계의 dispose에서
제거한다. 활성 경계가 등록된 채로 남아 있어도 두 콜백을 제거한다.

렌더 경로 밖의 `boundaryOwner` 예약은 등록된 경계가 있는 동안 유지한다.
콜백 제거가 다른 adapter의 등록을 허용하는 것으로 해석되지 않도록 기존 충돌 검사를 보존한다.
캐시·중첩 dirty·관련 작업 처리 계약은 그대로다. 같은 코어에는 같은 버전의 adapter 하나를 사용한다.

Concurrent 코어 source·bundle, 기본 코어, 기존 helper, 패키지 설정을 변경하지 않는다.
렌더 경로에 새 예약 검사를 넣지도 않는다. 조건문·선택적 콜백 조회 자체는 기존 Concurrent에 남는다.
활성 경계에서 불필요한 콜백을 제거했다는 사실과 전체 렌더 성능 영향 0이라는 주장은 구분한다.

## 검증 결과

| 확인                                              | 결과                                                  |
| ------------------------------------------------- | ----------------------------------------------------- |
| 실험 adapter 기본·Concurrent                      | 57/57, 68/68                                          |
| 활성 경계·첫 pause·마지막 resume                  | 콜백 제거·설치·제거 확인. DOM·effect·commit 횟수 유지 |
| 활성 루트가 남은 상태에서 마지막 중단 경계 폐기   | 콜백 제거 후 갱신 가능. 다시 pause하면 차단·재개 정상 |
| 중첩 경계·초기 비활성·props/slot·portal·최종 정리 | 기존 실험 회귀 통과                                   |
| TypeScript·수정 파일 ESLint·실험 라이브러리 빌드  | 통과                                                  |
| 기본·Concurrent·helper ESM/CJS/UMD 9개 번들       | 6단계 SHA-256과 모두 동일                             |
| Chromium 두 코어·일반/Custom Element 호스트       | 32/32, page JavaScript 오류 없음                      |

Chromium 두 코어·일반/Custom Element 호스트 검증은 기존 32개 시나리오를 재실행했다.
Concurrent 전체 코어 225개와 element 85개는 source·bundle이 같은 6단계 결과를 유지하며,
이번 변경을 검사했다는 의미로 재실행 횟수를 합산하지 않는다.

Node v24.19.0에서 UMD Brotli는 기본 코어 4,758B, Concurrent 코어 6,635B,
기존 helper 1,879B로 동일하다. 실험 라이브러리 전체는 2,243B로 6단계보다 19B 증가한다.
모든 포맷·해시는 [SIZE_RESULTS_PHASE7.json](./SIZE_RESULTS_PHASE7.json)에 기록한다.

7단계 구현 검증 때는 시간 벤치마크를 다시 실행하지 않았으며 이번 변경의 개선율을 제시하지 않는다.
콜백이 연결되지 않은 상태와 실제 중단·재개의 결과를 검사했다.
[6단계 성능 수치](./PHASE6.md)는 그 단계의 adapter로 측정한 역사 기록이다.
이후 사용자 요청으로 7단계 구현의 원본 대비 [최종 성능 측정](./PERFORMANCE_FINAL.md)을 수행했다.
기능 미사용·활성·중단 상태의 시간 증가와 동일 코드 대조군의 실행 변동을 함께 기록한다.

## 다음 단계로 진행하는 판단

기본 코어는 원본을 유지하고, Concurrent에 작은 검사 비용을 포함하는 방향을 유지한다.
이 조건에서 기능 미사용 시 검사 비용까지 완전히 제거하지는 않는다.
현재 계약을 유지하는 범위에서 다음 API 정리를 막을 정도의 필수 성능 개선 항목은 확인하지 못했다.

이미 effect·초기화를 실행한 관련 작업의 pause 지연은 남는다. 완료를 기다리는 비동기 pause나
effect 보류를 도입하면 계약 자체가 달라지므로 이번 단계의 추가 최적화로 넣지 않는다.

다음 단계의 구체적인 배치·API·사용 계약을 [API_REVIEW.md](./API_REVIEW.md)에 작성했다.
기존 helper entry를 사용하는 제안이며 lifecycle 전용 코어 빌드는 만들지 않는다.
