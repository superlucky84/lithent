# 6단계 — Concurrent 경계 탐색·중단 비용 개선

- 작성일: 2026-10-10
- 브랜치: `experiment/closure-lifecycle-performance`
- 출발·직접 비교: 5단계 `25821b015d23f258a1012a0e1721d7a4c5b8839b`
- 원본 코어·크기 비교: 3단계 `925b4aa98c40ca20b309ea2613cc625d260fa5b1`
- 상태: **Concurrent 전용 성능 개선 실험. 기본 코어 동일성 유지. 공개 API 미출하.**

## 변경

기본 `src/`·타입·패키지 설정을 그대로 보존한다. Concurrent의 내부 경계와 선택적 실험 어댑터만 바꾼다.
기본 ESM·CJS·UMD는 3단계 원본과 SHA-256이 같으며 크기와 갱신 검사 증가가 없다.

### 경계 소속 캐시

부모 WDOM을 매번 탐색하는 대신 안정된 컴포넌트 키를 WeakMap의 키로 사용한다.
컴포넌트의 출력 WDOM이 교체되어도 소속을 재사용한다. 저장하는 값은 경계 entry 목록이며,
active·dirty 상태는 매번 entry에서 읽어 중첩 경계 모두에 갱신을 기록한다.

경계 등록·폐기, 마지막 중단 경계의 재개, 기존 노드의 부모 재연결에서는 캐시를 무효화한다.
Concurrent의 h/출력 wrapper, diff attach, 루트 parent 연결에 내부 reparent 호출을 연결했다.
중단 경계가 없을 때는 탐색과 캐시를 사용하지 않고 reparent 콜백도 제거한다.
공통 타입, 기본 코어, alias table, 공개 core exports에는 연결하지 않는다.

### 중단할 경계와 관련된 작업만 처리

`pause()`가 경계의 컴포넌트 키를 내부 beforePause에 전달한다.
renderer는 현재 parked pass의 소속·관측 가능 여부를 판단하고 scheduler는 동기 완료 중 low 표시를 해제한다.

| 현재 대기 작업                                               | 중단 처리                                                               |
| ------------------------------------------------------------ | ----------------------------------------------------------------------- |
| 경계와 다른 루트·형제 작업                                   | 그대로 low lane에서 이어감. pause가 동기 완료하지 않음                  |
| 관련 작업, updater effect·새 컴포넌트 초기화를 실행하지 않음 | 기존 hook snapshot 복원 후 폐기. renew를 큐에 넣어 중단 후 dirty를 기록 |
| 관련 작업, updater effect 또는 새 컴포넌트 초기화를 실행함   | 활성 상태에서 한 번 동기 완료한 뒤 중단                                 |

안전 폐기 조건은 기존 Concurrent의 store retry·새 갱신 선점과 같은 hook trace 기준이다.
updater의 임의 부수 효과를 감지하는 기능은 추가하지 않는다. 이미 실행한 effect와 초기화는 버리지 않으며,
재개 시 최신 모델을 한 번 갱신하는 기존 계약을 유지한다.
순수 작업을 버리는 경우에는 pause 직전 모델이 DOM에 commit되지 않고 이전 commit을 보존한다.

새 어댑터는 beforePause뿐 아니라 이번 settle capability를 확인한다.
기본 코어 또는 이전 실험 core와 섞어 사용하면 frozen host 초기화 전에 거부한다.
이전 실험 브랜치의 core·adapter는 그 브랜치끼리 함께 사용한다.

## 검증

| 검증                                                   | 결과                                    |
| ------------------------------------------------------ | --------------------------------------- |
| 기본 source·ESM/CJS/UMD                                | 원본 source diff 없음·세 번들 해시 동일 |
| 실험 어댑터                                            | 기본 57/57, Concurrent 67/67            |
| Concurrent 공유·전용 전체 회귀                         | 225/225, 58 files                       |
| 기존 Concurrent element                                | 85/85                                   |
| Chromium 두 코어·일반/element 호스트                   | 32/32, page JavaScript 오류 없음        |
| TypeScript·수정 파일 ESLint·코어/라이브러리/probe 빌드 | 통과                                    |

관련 없는 실제 parked 작업 유지, 순수 작업의 폐기·dependency 복원, 초기화를 실행한 작업 보존을 추가했다.
다른 중단 루트가 남아 있는 동안 경계를 직접 dispose해도 이전 캐시가 자식 갱신을 막지 않는 것을 검사한다.
기존 props·slot, keyed 이동, 중첩, portal, 제거·late renew, effect 한 번 재개도 통과한다.
수정하지 않은 기본 코어·기본 element의 전체 회귀는 5단계 검증 결과를 유지한다.

## 성능

같은 Chromium 실행에서 5단계 core와 그때의 실제 adapter를 이번 core·adapter와 직접 비교한다.
모듈 인스턴스는 분리하고 3회 전체 warmup·표본마다 200회 warmup 후 순서를 번갈아 실행한
9개 표본의 중앙값을 사용한다. 다른 테스트·빌드·벤치마크와 동시에 실행하지 않는다.

| workload                           | 5단계 일반 | 5단계 다른 경계 중단 | 6단계 일반 | 6단계 다른 경계 중단 | 중단 시 5단계 대비 |
| ---------------------------------- | ---------: | -------------------: | ---------: | -------------------: | -----------------: |
| 깊이 16 leaf renew 10,000회        |     42.4ms |               57.9ms |     41.4ms |               42.1ms |             -27.3% |
| 자식 64개 parent renew 2,000회     |    258.7ms |              322.0ms |    266.4ms |              268.3ms |             -16.7% |
| 8,192행 보존 화면 옆 input 1,000회 |     92.4ms |              110.9ms |     88.5ms |               95.6ms |             -13.8% |

이번 일반 갱신 대비 중단 경계의 추가 시간은 leaf **+1.7%**, parent **+0.7%**,
보존 화면 input **+8.0%**였다. 이 표본에서 활성 경계와 일반 갱신의 차이는 약 −2.2~+2.1%다.
작은 차이의 재현성과 실제 응답성은 별개이며 Concurrent 일반 경로의 추가 검사가 무비용이라는 뜻은 아니다.

`retained-host`는 8,192행 편집 화면을 숨겨 보존하고, 옆 화면의 input 이벤트를 1,000번 처리하며
32개 결과 컴포넌트를 갱신하는 합성 시나리오다. 숨긴 자식의 native renew도 입력마다 요청한다.
숨김 중 자식 draw는 0회이고 재개 시 최신 모델을 1회 반영하며 draft와 동일 input DOM을 보존한다.
초기 구성·숨김·재개 시간은 입력 갱신의 측정 구간에서 제외한다.
실제 제품의 프레임 지연·낮은 사양 장치·다른 브라우저 성능을 보장하는 결과는 아니다.

모든 원본 표본·메서드·번들 해시는 [PERFORMANCE_RESULTS_PHASE6.json](./PERFORMANCE_RESULTS_PHASE6.json)에 기록한다.
기본 시간 차이는 동일한 코드의 실행 변동이며 기능 비용이나 개선으로 해석하지 않는다.

## 실제 대기 작업의 pause 시간

zero low budget으로 작업이 실제 parked 되었음을 확인하고 pause를 측정한다.
이후 budget을 복원해 작업을 마치고, 관련 없는 작업의 low 완료, 중단 중 관련 갱신 차단,
effect·commit 횟수와 재개 시 최신 모델을 함께 검사한다. 버전 순서를 번갈아 실행한 1회 warmup·5개 표본이다.

| 8,192행의 대기 작업       | 5단계 중앙값 | 6단계 중앙값 | 6단계 5개 표본의 최댓값 |
| ------------------------- | -----------: | -----------: | ----------------------: |
| 관련·effect 실행          |       26.8ms |       17.9ms |                  23.6ms |
| 관련·effect/초기화 미실행 |       15.4ms |        0.0ms |                   0.0ms |
| 무관·effect 실행          |       18.0ms |        0.0ms |                   0.1ms |

0.0ms 표본은 Chromium 시간 측정 해상도 아래라는 뜻이며 무비용·최악 지연 0을 뜻하지 않는다.
관측 가능한 관련 작업의 동기 완료 정책은 바꾸지 않았다. 그 행의 시간 차이로 새로운 개선을 주장하지 않는다.
해당 경우 큰 트리가 여전히 한 프레임 이상을 동기 점유할 수 있다.
원본 표본·최댓값·두 probe 해시는 [PAUSE_RESULTS_PHASE6.json](./PAUSE_RESULTS_PHASE6.json)에 기록한다.
