# 2단계 — 활동 수명과 명시적으로 관리하는 화면 보존

- 브랜치: `experiment/closure-lifecycle`
- 기준 커밋: `3d9fc7a3ff9a67a4a75a67f293671bdc39cca642`
- 상태: **코어 무수정 프로토타입 자동 검증 완료. 공개 API 미출하.**

## 검증 범위

1. 인스턴스 자원은 최종 폐기에 정리한다. 활동 자원은 비활성화에 정리하고 재활성화에 다시 만든다.
2. 활동마다 새 범위와 `AbortSignal`을 생성한다. 오래된 활동에 늦게 등록하면 즉시 정리한다.
3. 검색 등 활동 작업은 닫을 때 취소한다. 저장 등 인스턴스 작업은 닫아도 모델 반영을 계속할 수 있다.
4. 정리·시작 실패와 재진입이 중복 타이머·구독이나 이전 세대 결과 반영으로 이어지지 않는다.
5. 보존 시연은 독립된 렌더 루트의 컴포넌트·VDOM·DOM을 유지한다. 일반 `let`과 편집 기록을 다시 초기화하지 않는다.
6. 제공된 갱신 함수를 사용한 화면은 숨김 중 갱신하지 않고, 숨김 중 변경을 재활성화에 한 번 반영한다.
7. 갱신을 예약한 직후 숨기거나 폐기하는 경우에도 숨김 중 새 화면이 만들어지거나 폐기된 화면이 되살아나지 않는다.

코어·기존 helper·element·공개 exports를 변경하지 않고 base·concurrent에서 검증한다.
기존 산출물 9개 해시와 1단계 대비 실험 번들 크기를 비교한다.

## 지원 경계

명시적 활동 범위와 `createRetainedView`의 갱신 함수를 사용한 화면이 대상이다.
다른 컴포넌트의 독립 renew, 기존 effect, portal, 외부에서 제거되는 Custom Element의 장기 보존을
자동으로 제어하지 않는다. 이 제한을 재현하는 테스트를 두고 일반 서브트리 차단에 필요한 코어 연동을 기록한다.
CSS 숨김은 영상·iframe 등의 브라우저 활동까지 정지시키지 않으므로 필요한 작업을 활동 범위에 등록한다.

포커스·선택 영역의 복원, state-ref/query 어댑터, 범위 계층 및 일반 concurrent build 중단은 다음 단계다.
저장 취소의 서버 롤백이나 결과가 불확실한 저장의 자동 재시도는 제공하지 않는다.

## 구현과 계약

| API                                    | 책임                                                                              |
| -------------------------------------- | --------------------------------------------------------------------------------- |
| `createActivityScope()`                | 처음 비활성인 인스턴스 소유 범위. `activate` / `deactivate` / `dispose`로 전이    |
| `scope.own(cleanup)`                   | 비활성화 중에도 유지하고 최종 폐기에 정리                                         |
| `scope.onActive(start)`                | 활성화마다 새 활동 핸들로 동기 생성 함수를 실행. 반환한 cleanup을 비활성화에 정리 |
| `activity.own(cleanup)`                | 해당 활동이 종료될 때 정리. 종료된 활동에 늦게 등록하면 즉시 정리                 |
| `createScopedTask(scope, 'activity')`  | 기본값. 비활성화에 취소·무효화하고 재활성화에 새 작업 그룹 생성                   |
| `createScopedTask(scope, 'instance')`  | 숨김 중에도 실행·결과 반영 가능. 최종 폐기에 취소·무효화                          |
| `createRetainedView(host, initialize)` | 독립된 DOM 루트와 클로저를 유지. 제공한 `renew`를 통해 화면 갱신 관리             |

활동 핸들은 `disposed`, `signal`, `own`을 제공하며 활동 종료는 인스턴스에서 제어한다.
`onActive` 등록 해제는 생성 함수의 재실행을 막고, 반환한 cleanup을 즉시 실행한다.
`activity.own`으로 직접 등록한 자원은 활동 전체가 소유하므로 등록 해제 후에도 활동 종료까지 유지된다.
개별 등록 해제까지 연결하려면 자원 정리 함수를 생성 함수에서 반환한다.

비활성화는 먼저 현재 활동을 지운 후 abort와 전체 정리를 수행한다.
정리 중 재활성화를 요청하면 이전 정리가 끝난 다음 새 활동을 만든다. 최종 폐기 중에는 다시 활성화하지 않는다.
시작이 실패하면 해당 활동 전체를 정리하고 비활성으로 돌아가 `AggregateError`를 던진다.
실패 정리 중 발생한 재활성화 요청은 재시도하지 않으며, 호출자가 명시적으로 재시도할 수 있다.
여러 정리 함수가 실패해도 나머지를 모두 시도한다. 비동기 cleanup 완료는 기다리지 않는다.

최신 작업의 성공·오류·pending observer만 반영하는 1단계 계약을 그대로 사용한다.
숨김으로 취소한 활동 작업은 `pending=false`를 발행하지 않으므로 재활성화 UI의 pending 초기화는 호출자가 담당한다.
저장을 새로 시작하면 같은 저장 그룹의 이전 작업도 무효화한다. 서버가 이전 저장을 적용하지 않았다는 뜻은 아니다.

화면 생성은 숨긴 컨테이너에 한 번 렌더한다. 활동 생성 함수는 `show()`부터 실행한다.
`initialize`의 일반 `let`, history와 자식 컴포넌트 인스턴스·DOM을 숨김 중 유지한다.
`show()` / `hide()` / `dispose()`로 화면을 제어하고, 반환된 `scope`는 자원과 작업 등록에 사용한다.
숨김 중 관리된 `renew`는 dirty 상태만 기록하고 재활성화 후 한 번 그린다.
이미 코어에 예약된 갱신은 마지막으로 해석된 구체 WDOM을 반환해 새 `draw()` 호출을 막는다.
이 경우 코어의 예약 작업·diff 자체를 취소한다는 보장은 없다.
최종 폐기는 한 번만 수행하며, 소유 범위 정리가 실패해도 루트 제거를 시도한다.
초기화와 정리가 함께 실패하면 두 오류를 모아서 보고하고 컨테이너를 제거한다.

1단계 24개에 25개를 추가했다. 활동 세대 변경, 반복 폴링, 늦은 등록, 등록 해제,
정리·시작 오류, 정리 중 재진입, 숨김 시 검색 취소·저장 계속 진행, 이전 활동의 오류·finally 억제,
클로저·undo·자식 인스턴스·DOM 보존, 관리 갱신 병합, 두 시점의 예약 갱신 후 숨김,
예약 갱신 후 폐기와 초기화 실패를 검증했다.

지원 경계 테스트에서는 숨겨진 자식이 자체 `renew()`를 호출하면 DOM이 실제로 갱신된다.
임의의 서브트리를 중단하려면 코어의 갱신 예약, 부모 diff, effect 및 concurrent build/commit 경계와 연동해야 한다.
전체 회귀 스위트와 실제 브라우저의 포커스·미디어 동작은 이번 단계에서 실행하지 않았다.

## 크기와 비용

Node `v24.19.0`, Vite `5.4.8`, gzip level 9, Node 기본 Brotli 설정.
source map 제외, `lithent` external. 실험 파일은 1·2단계 전체 API를 함께 내보낸다.

| 산출물          | raw (B) | gzip (B) | Brotli (B) | 1단계 대비 Brotli |
| --------------- | ------: | -------: | ---------: | ----------------: |
| base UMD        |  12,966 |    5,142 |      4,758 |               0 B |
| concurrent UMD  |  17,045 |    6,906 |      6,385 |               0 B |
| 기존 helper UMD |   6,145 |    2,134 |      1,879 |               0 B |
| 실험 UMD        |   3,898 |    1,643 |      1,468 |            +798 B |
| 실험 CJS        |   3,689 |    1,525 |      1,371 |            +797 B |
| 실험 ESM        |   6,182 |    1,842 |      1,646 |            +952 B |

base UMD와 실험 UMD를 각각 Brotli로 전송하면 **6,226 B**다.
코어를 사용하는 기존 앱의 파일 증가는 **0 B**이며, 관리 갱신은 실험을 선택한 화면에만 추가된다.
일반 코어 경로에 체크나 래퍼를 추가하지 않았다. 갱신 처리량·메모리 사용량은 별도 벤치마크하지 않았다.
보존한 화면은 클로저·DOM을 계속 보유하므로 호스트가 보존 개수와 최종 폐기를 관리해야 한다.
ESM 앱의 tree shaking 후 비용은 이 전체 실험 파일의 압축 크기와 다를 수 있다.
해시·전체 수치·1단계 차이는 [SIZE_RESULTS_PHASE2.json](./SIZE_RESULTS_PHASE2.json)에 기록했다.
