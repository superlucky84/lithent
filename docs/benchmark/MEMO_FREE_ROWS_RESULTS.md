# #1261 주석 없는 행 구현 — memo 행 컴포넌트 진단 (DC-29)

2026-11-09. **판단: 진행 중(프로토타입 단계).** 행 데이터에 VDOM 캐시를 붙이는 현재 등재 앱 대신,
평범한 행 컴포넌트를 라이브러리의 `memo`로 건너뛰는 앱을 만들고 코어의 컴포넌트 경로를 줄였다.
이 세션의 진단 측정으로는 현재 등재 조합 대비 **가중 전체 약 +8~10%**(세 번 측정 +7.8~+10.4%)까지 왔다. 아직 "비슷한 성능"이라고
하기에는 선택·삭제·추가 항목의 차이가 남는다. 채택·크기 한도·공식 러너 측정은 하지 않았다.

- **무엇이 #1261인가:** upstream `fa510a7`에서 대조한 9개 keyed 구현 중 `issues`가 있는 것은
  lithent뿐이다. React `memo`, class/Inferno의 `shouldComponentUpdate`, ivi 컴포넌트의 props 비교,
  Vue `v-memo`는 주석이 없다. 등재된 Lithent 앱은 행 **데이터 객체**에 `cacheUpdate` view를 붙인다.
- **새 앱(M):** `const Row = memo(mount(...))`, `<Row key id label selected />`. 데이터에 붙는 캐시가 없다.
- **진단 결과:** M + 후보 코어는 A + 현재 코어 대비 가중 전체 **+7.8%**, 스크립트 **+29.2%**다.
  같은 조건에서 행 컴포넌트 + `cacheUpdate`(C)는 +30.4%, memo 없는 행 컴포넌트(R)는 +70.1%다.
- **기존 앱에는 중립:** A 앱을 후보 코어로 돌리면 가중 전체 −1.4%(스크립트 −0.7%)로 잡음 범위다.
- **메모리:** 1,000행 JS heap 3.60 → 4.04MB(+12.2%), 10,000행 18.74 → 23.01MB(+22.8%).
- **크기:** base UMD Brotli 4,857 → 5,026B(+169B), 추가 후보 J4-a까지 5,045B. guard 4,953B를 **92B 초과**한다.
- **결정(2026-11-09 사용자):** 행 컴포넌트 + `memo`로 간다. 합격 기준은 Mac 공식 러너 가중 전체 +3%·항목 +10%·1,000행 메모리 +15% 이내다. 크기 한도는 공식 결과를 본 뒤 정한다.
- **한계:** 공식 러너가 아니다. 페이지 안에서 잰 스크립트 + 강제 layout 시간이며 paint가 없다.
  공유 클라우드 컨테이너라 항목별 수 %는 잡음이다. 채택 판단에는 Mac 공식 러너 측정이 필요하다.

## 배경

[PR #2136](https://github.com/krausest/js-framework-benchmark/pull/2136)으로 1.25.5가 등재됐지만
`"issues": [1261]`은 그대로다. 이전 실험에서 행을 컴포넌트로 바꾸면 A 대비 +16~32%였고
([컴포넌트 비용](./COMPONENT_COST_RESULTS.md)), hook 기반 생략(C3)은 +21%였다
([C3 캐시](./PARENT_MEMO_CACHE_RESULTS.md)). 그 실험들의 생략은 updater 안이나 hook 조회 뒤에
일어나서, 부모가 행을 다시 서술할 때마다 props 동기화·updater 진입·래퍼 재생성이 남았다.

이번에는 생략을 diff 입구로 옮겼다. 1.25.5에서 넣은 "같은 노드 반환" 경로와 같은 자리다.

## 추가 후보 J4-a — 판정을 맨 앞으로, 문자열 태그 먼저

위 측정 뒤 별도 커밋으로 넣은 후보다. diff에서 memo 판정을 다른 분기보다 먼저 하고, `h`가 문자열
태그(일반 element)를 Fragment·컴포넌트 확인 없이 처리한다. base Brotli +19B(5,045B, guard 92B 초과).

| 측정                               | A 현재 | A 후보(J4-a 없음) | A 후보(J4-a) | M 후보(J4-a 없음) | M 후보(J4-a) |
| ---------------------------------- | -----: | ----------------: | -----------: | ----------------: | -----------: |
| 행 선택 스크립트 ms, 40표본 중앙값 |   3.08 |              3.05 |         3.15 |              4.08 |         3.89 |

- memo 행의 선택 스크립트가 약 5% 줄었고 A 앱은 차이가 없다(40표본, 사분위 범위는 서로 겹친다).
- J4-a를 넣은 상태로 9항목 12표본을 다시 돌린 값은 M 가중 전체 **+10.4%**(스크립트 +28.6%),
  A 후보 −0.3%다. 같은 날 세 번의 M 가중 전체는 +8.8%(수정 전 빌드), +7.8%, +10.4%였다.
  **이 도구로는 M의 가중 전체를 "약 +8~10%"로만 말할 수 있고**, J4-a의 효과는 9항목 합산에서
  구분되지 않는다. 약한 신호이므로 공식 러너에서 J4-a 유무를 따로 확인한다(커밋이 분리돼 있다).
- 메모리는 같다(1,000행 4.05MB).

## 남은 차이가 있는 곳

생성 + 삭제 반복의 CPU 프로파일(`profile.mjs`, source 빌드, 80회)에서 A와 M의 함수별 차이는 한 곳에
몰려 있지 않다. 반복당 약 +2.9ms(1,000행 생성 + 삭제) 중 큰 항목은 다음과 같다.

| 위치                                             | M − A (ms / 1,000행) |
| ------------------------------------------------ | -------------------: |
| `wDomToDom` + 자식 순회 콜백                     |                +0.77 |
| GC                                               |                +0.30 |
| `recursiveRunUnmount`(삭제 때 하위 순회)         |                +0.27 |
| `createCompWDom`(래퍼 생성)                      |                +0.23 |
| `setComponetRef`(인스턴스 등록 객체 11개)        |                +0.19 |
| 대량 삭제 일치 확인(`matches`)                   |                +0.18 |
| mount 큐·mountReady 큐 확인(`componentMap` 조회) |                +0.17 |

③을 넣기 전에는 `appendChild` 차이가 +0.61, `DocumentFragment` 생성이 +0.17이었다. ③ 뒤 `appendChild` 차이는 +0.07이고 행별 fragment 생성은 없어졌다.

후보(미착수, DESIGN DC-29-9):

1. 마운트 때 행마다 도는 `componentMap` 조회와 등록 객체 생성을 줄인다.
2. 삭제 때 컴포넌트가 없는 하위 트리를 걷지 않는 방법을 찾는다.
3. 갱신 계열: `h(Row, props)`가 행마다 만드는 서술 객체와 판정 전 분기 수를 줄인다(새 페이지
   조건에서 차이가 커지는 부분).

2. 합격 기준은 Mac 공식 러너에서 가중 전체 +3% 이내, 9항목 각각 +10% 이내, 1,000행 메모리 +15% 이내.
3. 크기 한도는 지금 바꾸지 않고, 공식 러너 결과를 본 뒤 상향 여부와 값을 정한다.

진단값(가중 약 +8~10%, 선택 +37%, 메모리 +12%)은 paint가 빠진 값이라 공식 전체 시간의 비율과
같지 않다. 스크립트가 전체에서 차지하는 몫만큼 희석되지만 얼마나인지는 재 봐야 안다.

다음 단계:

- **Mac 공식 러너(J6의 앞당긴 확인):** A + 현재 코어 / A + 후보 코어 / M + 후보 코어를 9항목 양순서로
  잰다. M 앱은 upstream 형식 파일 [`experiments/memo-free-rows/upstream/main.tsx`](../../experiments/memo-free-rows/upstream/main.tsx)를
  `frameworks/keyed/lithent/src/main.tsx` 자리에 두고 후보 코어의 dist로 빌드한다(`tsc --noEmit`와
  이 도구의 9개 시나리오 DOM 확인을 통과했다). 이전 공식 측정의 준비·실행 도구
  (`experiments/positional-keys/official-*.mjs`)를 같은 방식으로 쓸 수 있다.
- 공식 결과가 기준 밖이면 남은 후보(마운트 조회·등록 객체, 삭제 순회, 행 서술 객체)를 그 수치로
  우선순위를 정해 진행한다.
- concurrent 이식과 양코어 공유 테스트(J5)는 base 후보가 정해진 뒤 한다.
