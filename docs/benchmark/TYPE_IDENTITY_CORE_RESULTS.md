## 후보와 조건

원본 upstream 앱·helper를 그대로 두고 base·concurrent의 타입 비교만 변경한다.
이전 VDOM이 존재하면서 새 VDOM과 같은 객체면 타입 비교 결과를 바로 `true`로 판정한다.
이전 VDOM이 없는 생성 경로는 기존처럼 타입 비교를 생략한다.

일반화, empty 노드의 삭제 판정, 렌더링 종류 결정, 메타데이터 상속·정리와 concurrent 작업
프레임은 그대로 수행한다. [과거의 전체 diff 조기 반환](./PERFORMANCE_CLOSEOUT.md)과는 다른
후보다. [목록 할당](./ORDERED_CORE_RESULTS.md)과 [Map 삭제](./KEYMATCH_CORE_RESULTS.md)
후보는 복원했으며 이번 변경과 섞지 않았다.

먼저 keyed 매칭 뒤에 동일 VDOM의 전체 diff를 생략하는 후보도 확인했다. 캐시·키·재정렬
관련 기존 검사 34개는 통과했지만 base brotli가 **4,808B**였다. 이후 타입 비교만 생략하는
더 작은 후보를 만들었으며, 기능이 같은 표현 세 가지의 base 크기는 **4,803 / 4,802 / 4,803B**다.
사전 CPU 비교에는 가운데 구현(`type-v3`, `after`)을 사용했다.

사전 비교는 공식 **290개 표본**에서 가중 전체 **−1.2%**, JS **−2.7%**였다.
선택은 **7.956→7.437ms**였지만 부분 갱신은 **19.378→19.478ms**였다.
이 구현은 크기 한도를 2B 초과하므로 채택하지 않았으며, 사전 표본을 최종 구현의 수치에 합치지 않는다.

최종 후보는 base 함수 입구에서 복제 여부를 판단할 때 이미 수행하는 객체 비교의 결과를
지역 변수로 재사용한다. 같은 비교를 다시 하지 않으며 base brotli는 기존과 같은 **4,798B**로
**4,800B** 한도 안이다. concurrent는 **6,903→6,910B**로 한도 **9,000B** 안이다.
크기 기준은 바꾸지 않았다. 최종 소스·번들은 `final-after`, 최종 측정은 `final`에 보존한다.

## 측정 방식

- `~/project/js-framework-benchmark-upstream`의 기존 공식 Puppeteer 러너와 Vite **5.4.21** 사용.
- **동일 원본 앱과 npm 1.25.2 helper**, npm **1.25.2 코어** 대 **로컬 미배포 코어** 비교다.
  실제 upstream 작업트리의 `targeted-main.tsx`는 교체하지 않는다.
- Apple **M4 Pro / 12코어 / 24GB**, 고정 Chrome **155.0.8059.85**.
  실행 파일과 Chrome Framework의 해시를 시작/종료 때 확인한다.
- CPU 9개 항목은 base 대상이다. concurrent에 공식 성능 개선율을 적용하지 않는다.
  warmup·throttling·GC·trace·최종 paint 계산은 기존 공식 방식 그대로다.
- 항목마다 선행 앱을 교대한다. 행 선택은 앱당 **25개**, 나머지는 **15개** 표본이다.
  다른 후보나 과거 브라우저의 수치와 합산하지 않는다.

작업 경로는 `/tmp/lithent-keyed-identity-20261020`이다. 초기 keyed 후보 때문에 정해진
경로 이름이며, 최종 측정 대상은 위 타입 비교 후보다. `before`·`final-after`에 소스와 번들을,
`final`에 동일 앱의 프로덕션 빌드·공식 표본·trace를 보존한다. 사전 비교의 `after`·`main`은
별도로 유지한다.

```sh
export LITHENT_CHROME_BINARY='/tmp/lithent-benchmark-chrome-155.0.8059.85.app/Contents/MacOS/Google Chrome'
export LITHENT_BENCHMARK_ROOT="$HOME/project/js-framework-benchmark-upstream"
export LITHENT_PRODUCTION_OUT=/tmp/lithent-keyed-identity-20261020/final
export LITHENT_PRODUCTION_ALTERNATE_ORDER=1
node docs/benchmark/production-run.mjs cpu lithent-before,lithent
```

전후 소스·번들 준비가 먼저 필요하며 새 측정에는 별도 결과 경로를 사용한다.

## 최종 작업트리

두 코어의 소스를 복원하고 ESM·UMD·CJS·소스맵을 다시 빌드했다. 변경했던 diff·render 소스와
ESM·UMD는 실험 전 해시와 같고, base 런타임 소스 16개와 세 번들 형식은 npm **1.25.2**와
바이트까지 일치한다. 복원 후 캐시·keyed 소비 계약 검사 **4개씩**, 빌드·크기 검사를 통과했다.
base br **4,798 / 4,800B**, concurrent **6,903 / 9,000B**다.

이전 Map 후보 때 추가한 `core-keyedConsumption.test.tsx`는 유지한다.
실제 upstream 앱은 이전 `targeted-main.tsx` 그대로다. 이번 결과가 그 앱을 전체 성능의
최선으로 선정한 것은 아니며, 원본 앱을 고정한 코어 비교의 결론이다.
버전 변경·커밋·배포는 하지 않았다.
