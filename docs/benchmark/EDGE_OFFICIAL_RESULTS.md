# 기존 keyed 앱의 공식 러너 재측정 — 2026-10-16

사용자 요청으로 이전 릴리스 준비 커밋 `592d320`과 현재 `0ccd126`을
`../js-framework-benchmark`의 기존 Lithent 앱에서 비교했다.
**전체적으로 렌더링 성능은 유지되거나 개선됐다.** 9개 CPU 항목의 가중 시간 비율은
전체 **0.9665(−3.4%)**, JavaScript **0.8982(−10.2%)**다.
다만 **10,000행 생성의 JavaScript 시간은 두 실행 순서에서 모두 약 1.5% 증가**했다.
이 항목의 전체 시간 증가는 재측정에서 반복되지 않았다.

## 비교 조건

- 수정 후: `0ccd1265384fd68ebd0db63e8d7b4ca74088726e`.

  행마다 `cacheUpdate`로 keyed `tr`를 캐시하는 base 코어 앱이다.
- 각 커밋을 별도 디렉터리에 추출하고 Vite **5.4.8**로 core/helper를 새로 빌드했다.
  두 앱은 기존 Vite **5.4.21** 프로덕션 설정으로 빌드했다.
  앱 소스와 helper 번들의 SHA-256은 양쪽이 동일하다.
- 실제 환경: **Apple M4 Pro, 12코어, 24GB**, macOS,
  시스템 Chrome **155.0.8059.82** headless, Node **20.3.0**, Puppeteer **24.23.0**.
  과거 문서의 다른 기기·Chrome 버전에서 측정한 절대 시간과 섞지 않는다.
- 원본 `forkedBenchmarkRunnerPuppeteer.executeBenchmark`를 호출했다.
  준비 횟수, 새 탭, 강제 GC, CPU 배율, trace와 paint 계산은 원래 러너 그대로다.
  03·04·05·09는 CPU 4배, 06은 2배이며 나머지는 배율을 적용하지 않는다.
- 항목마다 전후 실행 순서를 뒤집었다. 선택은 코어당 **25회**, 나머지는 **15회**로
  전체 **290개 표본**이다. 10,000행 생성만 순서를 다시 뒤집어 **30개 표본**을 추가했다.
  합계 **320개**이며 실패·재시도·러너 경고는 없었다. 성공 표본은 버리지 않았다.
- 1차 측정 UTC **06:58:09~07:05:48**, 재측정 **07:06:42~07:07:45**.
  1차 묶음 종료 시 1분 load average는 약 **2.8~6.2**, 재측정 종료 시 **2.9~3.8**였다.
  전용 격리 머신의 측정은 아니므로 작은 차이에 환경 오차가 남는다.

## 10,000행 생성 재확인

1차에는 기준 코어를 먼저 실행했다. 2차에는 수정 후 코어를 먼저 실행했다.
각 차수 코어당 15회이며, 같은 번들을 사용했다.

| 차수              | 전 전체 ms | 후 전체 ms |  변화 | 전 JS ms | 후 JS ms |  변화 |
| ----------------- | ---------: | ---------: | ----: | -------: | -------: | ----: |
| 1차, 기준 먼저    |    287.722 |    294.933 | +2.5% |   62.977 |   63.884 | +1.4% |
| 2차, 수정 후 먼저 |    288.565 |    287.776 | −0.3% |   62.695 |   63.657 | +1.5% |
| 합산, 코어당 30회 |    288.144 |    289.775 | +0.6% |   62.727 |   63.694 | +1.5% |

전체 시간은 실행 순서에 따라 증가 방향이 달라졌고, 합산 중앙값 차이는 **+0.6%**다.
반면 JS 차이는 두 차수 모두 같은 방향이며 합산 **약 +0.97ms(+1.5%)**다.
큰 생성 성능 저하는 보이지 않았지만 이 작은 JS 증가까지 없다고 판단하지는 않는다.
증가의 구체적 원인은 이번 측정으로 분리하지 않았다.

## 동작 검증과 원본

양쪽 빌드 모두 공식 `isKeyed`의 생성·삭제·교환 검사를 통과했다.
별도 9개 동작 검사에서는 선택 전환, 부분 갱신, 교환 후 DOM 정체성,
이동한 행의 삭제 핸들러, 추가, 교체, 전체 삭제, 10,000행 생성과 폰트 로딩을 확인했다.
브라우저 오류와 HTTP 오류는 없었다. 격리 빌드의 TypeScript·ESLint도 통과했다.

- [edge-official-results.json](./edge-official-results.json): 검증, 실행 환경, 모든 표본,
  차수별·합산 중앙값과 사분위수, 빌드·앱·helper·러너 해시, 가중치와 근거 소스 해시.
- [edge-official-evidence.json.gz](./edge-official-evidence.json.gz): 실제 측정한 core/helper,
  앱 소스와 두 프로덕션 번들. 압축 파일의 SHA-256은 결과 JSON에 있다.
- 임시 빌드·공식 trace·로그: `/tmp/lithent-edge-official-20261016`.
  소스 checkout을 바꾸거나 벤치마크 저장소의 기존 결과를 덮어쓰지 않았다.

## 재현

빌드 준비는 존재하지 않는 새 출력 디렉터리를 요구한다.

```sh
export LITHENT_PRODUCTION_OUT=/tmp/lithent-edge-official-rerun
node docs/benchmark/edge-official-prepare.mjs 592d320 0ccd126
node docs/benchmark/production-run.mjs verify lithent-before,lithent
LITHENT_PRODUCTION_ALTERNATE_ORDER=1 \
  node docs/benchmark/production-run.mjs cpu lithent-before,lithent
node docs/benchmark/edge-official-summarize.mjs "$LITHENT_PRODUCTION_OUT"
```

재확인 디렉터리에 같은 `build-manifest.json`과 `versions.json`을 복사하고,
`lithent-before`와 `lithent`를 원래 빌드에 연결한 링크로 만든다.
`LITHENT_PRODUCTION_OUT`을 그 디렉터리로 지정하고
`cpu lithent,lithent-before 07`을 실행하면 10,000행 생성만 역순으로 재측정할 수 있다.
집계 스크립트의 두 번째 인수부터 재측정 디렉터리를 전달하면 양쪽 표본을 모두 보존한다.

측정용 `production-run.mjs`는 CPU/메모리 시작 전에 실제 Chrome 버전을 읽도록 했다.
공식 러너의 측정 코드는 변경하지 않았다.
