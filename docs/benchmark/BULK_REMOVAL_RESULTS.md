# 중첩 컴포넌트 목록의 일괄 제거 — 2026-10-19

**미채택이며 base·concurrent 런타임을 변경 전으로 복원했다.** 중첩된 행 컴포넌트의 DOM을
한 번에 제거해 전체 삭제는 두 차수 모두 빨라졌다. 그러나 우선 개선 대상인 행 선택의
화면 표시까지 시간이 세 차수 모두 늘었다. 선택 성능을 보존하는 조건을 충족했다고
판단할 수 없어 이번 코어 변경과 행 캐시 조합을 적용하지 않았다.

공식 CPU **800개 표본**을 보존했다. 9개 항목의 3개 구현 비교 435개, 코어 전후의 모든
항목을 반대 순서로 측정한 290개, 선택의 동일 번들 대조군을 포함한 추가 75개다.
실험 소스·번들·테스트는 압축 증거 파일에 남고, 현재 upstream 앱은 `targeted-main.tsx`,
설치된 코어는 npm 1.25.2 그대로다. 버전 변경·커밋·배포는 하지 않았다.

## 변경 범위

실험에서 `src/render.ts`와 `lithentConcurrent/src/render.ts`의 목록 제거 경로를 같은 방식으로
바꿨다가 복원했다. 아래는 미채택 후보의 설명이다.
기존에는 직계 자식이 Element/Text인 목록만 일괄 제거할 수 있었다. 행마다 컴포넌트가 있으면
Fragment wrapper 때문에 이 경로에서 제외되어 각 행의 DOM을 따로 제거했다.

이제 Fragment·컴포넌트 wrapper 아래의 실제 루트를 순서대로 확인한다. 제거할 노드가 부모의
현재 자식과 **정체성·순서·개수 모두 일치**할 때만 `parent.textContent = ''`를 한 번 실행한다.
중간에 다른 노드가 있거나 남은 형제가 있으면 기존 개별 제거 경로로 돌아간다. 노드 개수만
같은 외부 DOM을 잘못 지우는 기존 경로의 약점도 함께 막는다.

일치 검사는 첫 불일치에서 멈춘다. 긴 목록에서 한 컴포넌트를 지울 때 전체 형제를 매번 세지
않으며, 후보가 한 개면 새 검사를 수행하지 않는다. portal·HTML 루트는 일괄 제거 대상에서
제외한다. 컴포넌트 생명주기 정리와 portal 호스트의 이벤트 정리는 기존 순서로 실행한다.

`typeDeleteUnused`는 그대로다. 일부 keyed 행을 지울 때는 각 행의 정리 콜백 직후 DOM을
제거한다. 다음 콜백이 앞선 행이 제거된 DOM을 볼 수 있다는 기존 동작을 보존해야 하므로,
전체 교체까지 무조건 한 번에 지우도록 확장하지 않았다. 이번 변경으로 부모가 행 컴포넌트를
다시 실행하는 비용이나 행 컴포넌트 자체의 메모리 비용이 없어지는 것은 아니다.

## 비교 조건

| 이름 | 앱 | 코어 |
| --- | --- | --- |
| `lithent-before` | 현재 upstream에 반영된 행별 renew 앱 | npm 1.25.2 |
| `lithent` | 위와 동일한 앱 소스 | 로컬 일괄 제거 변경본 |
| `retained` | 앞선 실험의 현재 행 VDOM 캐시 | 로컬 일괄 제거 변경본 |

첫 두 구현은 앱·helper가 같고 코어만 다르다. 변경 전 로컬 ESM 코어와 npm 1.25.2의 ESM
코어는 SHA-256까지 같다. 세 번째 구현은 코어 변경과 앱 변경을 조합했을 때 앞서 관찰한
전체 삭제·교체 악화가 해소되는지 확인하기 위한 별도 후보다.

사용자가 지정한 `~/project/js-framework-benchmark-upstream`의 Vite 설정과 원본
`webdriver-ts/dist/forkedBenchmarkRunnerPuppeteer.js`를 사용했다. 프로덕션 번들은 별도
디렉터리에 준비했고, 공식 러너의 워밍업·스로틀·trace·paint 계산은 변경하지 않았다.
CPU 항목의 `total`은 클릭부터 화면 표시까지 걸린 시간이며 CPU 점유율이 아니다.

Apple M4 Pro 12코어·24GB, Chrome 155.0.8059.82, Node 20.3.0에서 측정했다.
메인은 06:39–06:50 UTC, 반대 순서는 11:35–11:45 UTC의 별도 차수다.
선택은 구현당 25회, 나머지는 15회이며, 재측정에서는 각 항목의 두 구현 선후를 정확히
뒤집었다. 전용 격리 머신이 아니므로 차수 사이 부하·프레임 타이밍 차이는 남는다.
모든 차수의 표본·trace를 별도 경로에 보존했으며, 뒤의 결과로 앞의 결과를 덮어쓰지 않았다.

## 코어만 변경한 결과

각 차수의 전체 시간 중앙값(ms)이다. 기준은 현재 행별 renew 앱이며, 컴포넌트 없는
최초 앱과 비교한 표가 아니다.

| 항목 | 메인 변경 전 | 메인 후보 | 반대 순서 변경 전 | 반대 순서 후보 |
| --- | ---: | ---: | ---: | ---: |
| 1,000행 생성 | 27.997 | 28.074 | 28.196 | 28.076 |
| 1,000행 교체 | 30.981 | 30.838 | 30.944 | 30.829 |
| 부분 갱신 | 14.543 | 14.632 | 16.672 | 16.008 |
| 선택 | 5.001 | 5.778 | 4.194 | 5.496 |
| 교환 | 24.198 | 24.008 | 25.296 | 25.436 |
| 한 행 삭제 | 14.343 | 14.583 | 15.035 | 15.032 |
| 10,000행 생성 | 302.749 | 310.771 | 306.183 | 304.791 |
| 1,000행 추가 | 33.563 | 33.498 | 33.921 | 33.873 |
| 전체 삭제 | 14.267 | 13.632 | 15.444 | 14.152 |

전체 삭제는 각각 **4.5% / 8.4%** 줄었다. JS 중앙값도 **11.767 → 11.136ms**,
**12.727 → 11.755ms**로 줄었다. 두 차수의 30개씩을 합친 전체 중앙값은
**14.624 → 14.027ms (-4.1%)**다. 실제 Chrome의 MutationObserver에서도 같은 1,000행의
제거가 **1,000개 기록 → 1개 기록**으로 바뀌었다. 생명주기 정리를 생략한 결과가 아니다.

부분 갱신·생성·교환의 작은 증감은 차수마다 방향이 바뀌었다. 메인 가중 전체 시간 비율은
후보/변경 전 **1.0079**, 반대 순서는 **0.9963**이며, JS는 각각 **1.0095 / 0.9607**이다.
종합값이 비슷하더라도 선택의 개별 악화 신호를 지우지 않는다.

## 선택을 추가 확인하고 미채택한 이유

선택의 메인·반대 순서 50개씩을 합친 전체 중앙값은 **4.484 → 5.711ms (+27.4%)**다.
다만 각 표본은 약 3–10ms 범위로 넓게 퍼졌고, JS 중앙값은 차수마다 증감 방향이 달랐다.
이를 곧바로 코어의 JS 처리량 증가로 해석하지 않았다.

추가 차수에서는 변경 전의 **완전히 같은 번들**을 `control`이라는 별도 이름으로도 실행했다.
코어 후보 → 복제 대조군 → 변경 전 순서이며, 공식 워밍업과 측정 계산은 그대로다.

| 구현 | 전체 ms | JS ms | paint ms |
| --- | ---: | ---: | ---: |
| 변경 전 | 3.979 | 0.503 | 2.289 |
| 변경 전과 동일한 복제 대조군 | 4.033 | 0.717 | 2.490 |
| 일괄 제거 후보 | 4.449 | 0.721 | 2.321 |

이 차수에서도 후보 전체 시간은 변경 전보다 **11.8%** 높았다. 대조군도 표본 편차가 있고
이 결과만으로 인과관계를 확정할 수는 없다. 그러나 세 차수 모두 같은 방향의 전체 시간
증가가 있어, 사용자가 우선하는 선택 성능을 보존한 개선으로 채택하기에는 근거가 부족하다.

trace에서 `UpdateLayoutTree` 종료부터 다음 `Paint` 시작까지의 간격 중앙값은 메인
**2.165 → 3.218ms**, 반대 순서 **0.872 → 2.564ms**, 추가 차수 **0.767 → 1.366ms**였다.
실제 DOM 갱신은 동일하며, 이 구간이 늘어 전체 시간 차이에 기여했다.
이 간격은 관찰한 구간이지 코어 변경이 브라우저 대기를 늘렸다는 원인 증명은 아니다.
측정 구간 안에서 GC 이벤트는 관찰되지 않았지만, 구간 밖 GC나 시스템 영향을 배제하지는 않는다.
`bulk-removal-traces.mjs`가 이 구간과 원본 trace의 해시를 기록하며 공식 시간은 수정하지 않는다.

## 행 캐시 조합과 비용

행 캐시를 조합한 후보는 메인에서 기존 행별 renew 대비 교환 **24.198 → 17.390ms**,
한 행 삭제 **14.343 → 11.830ms**, 선택 **5.001 → 3.460ms**였다. 그러나 전체 삭제는
**14.267 → 15.487ms**, 교체는 **30.981 → 31.621ms**로 여전히 느렸다.
일괄 DOM 제거만으로 앞서 확인한 조합의 손해를 모두 해결하지 못해 이 앱도 미채택이다.
이 조합은 이번 메인 차수만 측정했으며, 코어만 비교한 반대 순서·추가 차수와 섞지 않는다.

후보의 base UMD brotli는 **4,798 → 4,795B**, concurrent는 **6,903 → 6,909B**이며
기존 크기 한도는 통과했다. 복원 후 크기는 다시 **4,798 / 6,903B**다.
선택 시간 기준에서 후보를 탈락시켰으므로 이번 후보의 추가 메모리·100회 반복 보유 검사는
실행하지 않았다. 앞선 실험의 메모리 측정값을 이번 후보의 결과로 재사용하지 않는다.

## 검증

- `pnpm test:dual`: base·concurrent 및 양쪽 위성 패키지 통과.
- 새 공유 테스트 4개: 중첩된 여러 루트의 단일 제거, 정리 콜백 순서·DOM 가시성,
  삭제된 행의 예약 renew 무효화, 부분 목록의 형제 정체성, 외부 DOM과 portal 호스트 보존.
- `pnpm build:core`, `pnpm build:concurrent`, 변경 파일 ESLint·Prettier와 크기 검사 통과.
- `pnpm test:e2e`: base·concurrent 브라우저 통합 검사 **64개** 통과.
- 세 프로덕션 앱의 공식 keyed·9개 동작·glyph 폰트 검사 통과.
- 선택 이동의 class 2개, 부분 갱신의 텍스트 100개, DOM 정체성 유지,
  같은 task 안의 부모·자식 갱신 양쪽 순서, 20회 갱신·삭제·재생성 검사 통과.

위 검사는 미채택 후보를 대상으로 수행했다. 후보 전용 테스트는 증거 파일의
`runtime/after/src/tests/core-bulkRemoval.test.tsx`에 보존하고 현재 자동 테스트 경로에서는
제거했다. 두 코어를 복원·재빌드한 뒤 소스와 ESM·UMD가 변경 전 스냅샷과 같은지 검사했다.

다음에 다시 시도한다면 전체 삭제의 DOM 호출 수만 보지 말고 선택의 화면 표시까지 시간을
같이 확인해야 한다. 생명주기 정리 순서를 깨뜨려 교체 비용을 줄이거나, 이번 후보를 이미
검증된 개선으로 그대로 복원하지 않는다. 부모가 변경 없는 행 컴포넌트를 다시 실행하는 비용과
컴포넌트 캐시의 명시적 계약은 여전히 별도 개선 지점이다.

## 원본과 재현

[bulk-removal-results.json](./bulk-removal-results.json)은 공식 전체 표본, 동작 검사,
선택 trace 분석과 해시를 보존한다.
[bulk-removal-evidence.json.gz](./bulk-removal-evidence.json.gz)는 소스, 전후 코어,
세 프로덕션 번들, 원본 러너, 측정 도구, 단위·브라우저 테스트 로그를 담는다.
trace는 결과 JSON의 경로에 별도로 남긴다.
과거 `targeted-update-*`와 `structural-update-*` 측정값은 덮어쓰지 않는다.

코어만 변경한 두 구현의 재현 방법이다. 먼저 압축본의 `files`에서
`runtime/after/dist/lithent.mjs`의 UTF-8 `content`를 `/tmp/lithent-bulk-candidate.mjs`로 추출한다.
현재 저장소의 코어는 복원본이므로 그냥 재빌드한 `dist`를 후보로 쓰면 전후가 같아진다.
새 출력 디렉터리를 쓰고 다른 성능 측정과 동시에 실행하지 않는다.
`prepare`의 기준 코어는 upstream에 설치된 npm 패키지이고, 후보만 별도 파일로 지정한다.

```sh
export LITHENT_BENCHMARK_ROOT="$HOME/project/js-framework-benchmark-upstream"
export LITHENT_PRODUCTION_OUT=/tmp/lithent-bulk-rerun
export LITHENT_BASELINE_SOURCE=docs/benchmark/targeted-main.tsx
export LITHENT_CANDIDATE_SOURCE=docs/benchmark/targeted-main.tsx
export LITHENT_CANDIDATE_CORE=/tmp/lithent-bulk-candidate.mjs
node docs/benchmark/targeted-update.mjs prepare
node docs/benchmark/targeted-update.mjs contracts
node docs/benchmark/targeted-update.mjs verify lithent-before,lithent
node docs/benchmark/targeted-update.mjs cpu lithent-before,lithent
```

행 캐시와의 조합은 다른 새 출력 디렉터리에서 `LITHENT_CANDIDATE_SOURCE`를
`docs/benchmark/retained-row-main.tsx`로 지정해 빌드한다. 코어 변경본은 미배포 소스이며
upstream 앱의 설치된 npm 패키지를 바꾸거나 새 버전을 발행하지 않았다.
