- 공식 점수의 가중치(로컬 `Common.ts`, [DC-25 원자료](./dc25-keyed-fast-path-final-results.json)에 기록)는 select 0.19, 교환 0.13으로 낮고, 1k 생성 0.64, 교체·부분 갱신·10k 생성·추가가 각 약 0.56, 1행 삭제 0.53, 전체 삭제 0.42다.

- DC-25 원자료(앱 6개, 항목당 표본 30개)에서 Lithent의 JS만 줄였다고 가정해 다시 계산한 가중 점수다. Preact class = 1.000, 낮을수록 좋다.

### 위치 매칭이 기존 매칭과 같은 이유

- 목록의 모든 자식이 키가 유일한 목록의 원본과 짝지어졌다면, 새 목록의 키도 유일하다. 짝은 서로 다른 원본과 이뤄지고, 그 원본 키들이 SameValueZero로 서로 다르기 때문이다. 이런 목록을 `WeakSet`에 기록한다.
- 기록된 목록에서 키가 같은 위치의 원본은 그 키의 유일한 원본이다. 기존 Map 매칭(같은 키의 첫 원본)과 같은 짝이다. 처음 어긋나면 아직 짝지어지지 않은 원본만으로 Map을 만든다. 유일한 키라서 이미 짝지어진 원본의 키는 다시 나올 수 없다.
- 기록되지 않은 목록(처음 diff, 중복 키, 짝 없는 자식이 있던 목록)은 기존처럼 Map을 먼저 만든다. 키 읽기 순서를 고정한 기존 테스트도 이 경로를 쓴다. `NaN` 키는 위치 비교(`===`)에서 어긋나 Map으로 간다.

### 바뀐 테스트 계약

`core-keyedFastPath.test.tsx`의 첫 테스트는 다시 쓰인 같은 노드의 `children` getter가 **읽혀야** 한다고 고정했다. base는 이제 그 노드를 다시 읽지 않으므로, base는 읽지 않고 concurrent는 계속 읽는 것으로 바꿨다. 요소 정체성과 텍스트 검사는 그대로다.

### 넣지 않은 것

새 페이지 1k 생성 프로파일에서 다음 세 가지를 함께 시험했다. 텍스트 노드의 `updateProps` 호출 생략, 노드마다 부르던 컴포넌트 콜백 함수 2개를 `compKey`가 있을 때만 호출, 이전 props가 없을 때 빈 객체를 공유. 1k 생성은 14.90 → 15.50ms(+4%, 표본 30개)로 이득이 없어 넣지 않았다.
