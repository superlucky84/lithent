# #1261 주석 없는 행 구현 — Mac 공식 러너 측정 (2026-11-10, DC-29)

**결정(2026-11-10 사용자): `memo`와 등재 앱 교체는 넣지 않는다. 코어 개선 + 코드 정리만 적용하고
#1261 주석은 유지한다.** 아래 측정에서 memo 행 앱(M) + 후보 코어는 현재 등재 조합(A 앱 + main 코어)
대비 **가중 전체 약 +3%**였다. 배포와 같은 빌드로 잰 2차 세션에서 HEAD는 **+3.11%**(95% 구간
+2.19~+3.85%), 추가 후보 J4-b를 넣으면 **+2.96%**(+2.00~+3.75%)로, 합격 기준(DC-29-8) +3%의 경계였다.
같은 측정에서 기존 A 앱은 후보 코어에서 **−1.9~−2.1%**였다. 사용자는 표기값이 느려지고(메인테이너에게
받은 1.31 기준 약 1.35 예상) base가 5KB에 가까워지는 데 비해 얻는 것이 주석 제거뿐이라고 판단했다.
적용 결과와 최종 코어의 재확인은 [아래](#결정-뒤-적용한-것-2026-11-10)에 있다.

## 해석

- **가중 전체는 두 세션·두 빌드 도구에서 같은 값(약 +3%)으로 재현됐다.** 표본을 더 모아도 구간이
  좁아질 뿐 기준값 위아래 어느 쪽인지는 바뀌기 어렵다. "+3% 이내"를 문자 그대로 적용하면 HEAD는
  0.11%p 넘고 J4-b는 0.04%p 안이다. 이 차이는 측정 해상도(±0.9%p)보다 작다.
- **차이는 스크립트에서 나온다.** M의 가중 스크립트는 +11~12%이고 paint·layout이 섞이는 전체에서는
  약 +3%가 된다. 정상 상태 반복 프로파일(이 Mac, 생성+삭제 반복)에서는 A 5.90ms·M 5.88ms로 같았다.
  공식 조건(새 페이지, 웜업 5회 안팎)에서 덜 최적화된 코드가 행마다 컴포넌트 경로를 한 번 더 지나는
  비용으로 본다. 이 해석은 프로파일 한 번에 근거한 추정이다.
- **2차에서 교체·갱신·교환이 +5~7%로 가장 크다.** 교체는 모든 회차에서 +5.4~+7.7%로 일정하다.
  갱신과 교환은 회차별로 +0.3~+10.9%로 흔들리고, 1차에서는 교환이 −0.09%였다. 생성 계열(1천 행
  +0.4%, 추가 +3.4%, 1만 행 +3.6%)은 작다. 선택은 M이 양 세션 모든 회차에서 빠르다. wait 중앙값이
  0.003ms라 프레임 대기 변화 때문이 아니다.
- **전체 삭제는 불안정하다.** 2차 m-j4b의 +9.43%는 1회차 +27.1%와 3회차 +8.3%가 끌어올린 값이고
  2·4회차는 −2.8%/+5.4%다. active 변화는 +5.98%다. m-j4b와 m-head의 전체 삭제 차이(+4.0%)도 active로는
  +0.16%다. J4-b가 삭제를 느리게 했다는 증거로 보지 않는다.
- **2차 1회차는 시작 부하가 높았다**(1분 load 최대 7.2, `a-main`의 1행 삭제 중앙값 16.9ms로 다른
  회차 11.5~12.3ms와 다름). 평균 집계가 중앙값 집계보다 낮게 나온 것도 이 회차의 `a-main` 이상치
  때문이다. 표본은 빼지 않았다.
- **J4-b는 메모리 후보다.** 훅을 쓰지 않는 행마다 빈 배열 6개와 클로저 하나를 만들지 않는다. 메모리는
  양 회차에서 같은 방향(1,000행 −2.4%/−2.2%)이고 시간은 구간이 0을 포함한다. A 앱에는 영향이 없다
  (A는 행이 컴포넌트가 아니다).
- bootstrap은 회차 안에서 독립 재표집한 중앙값 비율이다. 세션·시스템 부하에 따른 불확실성은 나타내지
  않는다. 수집 중 1분 load average는 배치 시작 기준 1차 1.1~4.8, 2차 1.0~7.2였다.
- base 코어 결과다. concurrent 이식(J5)은 하지 않았다.

  재지 않았다.

  돌리지 않았지만 문서 편집과 서식 검사 한 번, 진행 확인 명령을 같은 기기에서 실행했다.
- 표기값 추정: 가중 기하평균은 항목별 "가장 빠른 구현 대비 배수"를 같은 가중치로 평균하므로, 항목별 최고

  추정값이다.
