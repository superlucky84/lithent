## 해석

- **부분 갱신·선택·1천 행 생성은 양순서에서 개선**됐다. 합산 전체 시간의 95% bootstrap 구간은 부분 갱신 [−14.19%, −4.84%], 선택 [−20.12%, −3.55%], 1천 행 생성 [−1.93%, −0.77%]다.
- 교환과 추가는 회차에 따라 전체 시간의 방향이 바뀌었다. 1행 삭제는 전체 시간이 거의 같다. 전체 삭제의 큰 1회차 이득도 역순에서는 반복되지 않았다. 이 항목들의 합산 차이를 안정적인 개선·회귀로 단정하지 않는다.
- 선택의 main/candidate idle wait 중앙값은 모두 0.003ms이고, main-thread active 중앙값은 −14.69%다. 이번 선택 개선이 프레임 대기 변화만으로 생겼다는 증거는 없다. active/wait는 진단값이며 공식 전체 점수를 대체하지 않는다.
- bootstrap은 각 회차 안에서 독립 재표집한 중앙값 비율(4,000회, seed 1)이다. 세션·시스템 부하에 따른 불확실성까지 나타내지는 않는다. 수집 중 1분 load average는 배치 시작 기준 약 1.56~8.56이었다. 양순서 비교도 이 영향을 완전히 제거하지는 못한다.
- base 공식 A 앱에 대한 결과다. concurrent 이식과 메모리 측정은 별도다. 코어 변경 내용·기존 테스트·크기 증거는 [기존 보고서](./POSITIONAL_KEYS_RESULTS.md)에 있다.

## 배포 전 호환성 검토

같은 VDOM을 반환할 때 children getter를 다시 읽지 않는 변경을 확인했다. 또한 앞 행의
갱신 콜백에서 뒤 행의 기존 `props.key`를 직접 바꾸거나, 기존 key getter가 갱신 중
다른 키를 반환하도록 하면 main과 매칭 결과가 달라질 수 있다. 이 사례를 일반적인
동일 키 재사용의 오류로 해석한 초기 판정은 철회했다. 사용자와 확인한 지원 범위는
reconciliation 중 키를 안정적으로 유지하고, 식별자를 바꿀 때 새 키를 가진 새 노드를
렌더하는 것이다. 이 범위의 동작과 갱신 도중 기존 키를 직접 수정하는 동작을 구분하며,
관찰 차이는 1.25.5의 [릴리스 노트](../../CHANGELOG.md)에 명시했다.

배포 전 검토에서 전체 빌드, 양코어·부속 1,176통과·3제외, E2E 78개, 타입·린트,
실제 tarball의 ESM/CJS·strict 타입 소비자, Concurrent 산출물·크기 검사를 통과했다.
1.25.5 manifest로 다시 빌드한 base ESM은 측정한 후보와 바이트 단위로 같다.
