# 전체 삭제 후속 검증 — 2026-10-08

**작은 개선 가능성은 확인했지만, 이번 함수 분리 후보는 채택하지 않았다.**
전체 삭제를 개선할 여지가 있는지 사용자가 물어봐, 최근 portal 정리 추가로 커진 unmount
함수를 분리하는 한 가지 후보를 실제 공식 러너로 검증했다. 전체 삭제의 개선 폭보다 다른
삭제 경로의 비용과 크기 증가를 함께 보고 판단했다.

## 변경 범위와 조건

- 기준은 props·portal 오류 수정까지 완료한 현재 코어다. 이전 성능 종료본과 비교한
  [COMPATIBILITY_PERFORMANCE.md](./COMPATIBILITY_PERFORMANCE.md)의 A/B와는 기준이 다르다.
- 후보는 shared unmount의 portal 호스트 정리만 별도 함수로 옮긴다. 일반 노드에서는 tag 확인을
  하고, portal일 때만 함수를 호출한다. 순회 방식·unmount 순서·DOM 제거·props 처리는 같다.
- 일반 DOM의 리스너 해제 생략, portal 호스트의 실제 이벤트 정리, props 오류 수정은 유지했다.
  진단용 `portalAblation`은 필요한 정리를 생략하는 대조군이며 채택 가능한 수정이 아니다.
- 같은 benchmark 앱 `8839611`, helper, Vite 5.4.21 빌드와 공식 CPU 러너를 사용했다.
  각 차수는 정확히 같은 두 번들·manifest를 복사해 측정했다. 공식 러너는 수정하지 않았다.
- Apple M4, 10코어, 24GB, 시스템 Chrome 154.0.8037.98 headless. 전체 삭제는 공식 설정의
  4배 CPU throttling, 한 행 삭제는 2배다. 각 조합 15개 표본이며 **공식 표본 합계 210개**다.
  전체 삭제 3차수, 한 행 삭제 2차수, 생성·교체 각 1차수를 포함한다.
- CPU 측정 중 빌드·단위 테스트·다른 브라우저 검사를 실행하지 않았다. 전용 격리 머신은 아니며
  차수별 부하와 페인트 변동이 있다. 절대 시간을 일반 환경의 체감 시간으로 환산하지 않는다.
- 사전 진단은 두 순서 × 3개 variant × 삭제·교체 × 12회로 **144개 표본**이다. 이 진단은
  paint를 포함한 공식 결과가 아니며 채택 근거는 아래 공식 비교다.

## 전체 삭제

각 칸은 해당 차수·코어 표본의 중앙값이다.

| 차수        | 실행 순서   | 전체 기준 | 전체 후보 | 전체 변화 |  JS 기준 |  JS 후보 | JS 변화 |
| ----------- | ----------- | --------: | --------: | --------: | -------: | -------: | ------: |
| 첫 차수     | 후보 → 기준 |  13.277ms |  13.200ms |     -0.6% | 10.882ms | 10.469ms |   -3.8% |
| 반대 순서   | 기준 → 후보 |  14.530ms |  14.020ms |     -3.5% | 12.119ms | 10.958ms |   -9.6% |
| 독립 재확인 | 후보 → 기준 |  13.050ms |  12.763ms |     -2.2% | 10.492ms |  9.842ms |   -6.2% |

세 차수 모두 개선 방향이지만 전체 시간 이득은 **0.077~0.510ms**로 작다. 합친 각 45개 표본의
전체 중앙값은 **13.590 → 13.242ms (-2.6%)**, JS는 **11.103 → 10.676ms (-3.8%)**다.
부하가 다른 표본의 합친 중앙값은 차수별 변화와 다를 수 있어, 위 차수별 비교도 함께 보존한다.
이 결과를 이전에 확인한 8.4% 삭제 악화의 완전한 복구나 새 종합 점수로 해석하지 않는다.

## 다른 경로와 판단

| 항목                  | 전체 기준 | 전체 후보 | 전체 변화 |  JS 기준 |  JS 후보 | JS 변화 |
| --------------------- | --------: | --------: | --------: | -------: | -------: | ------: |
| 1,000행 생성          |  28.675ms |  28.420ms |     -0.9% |  9.254ms |  9.175ms |   -0.9% |
| 1,000행 교체          |  31.736ms |  31.867ms |     +0.4% | 11.825ms | 12.043ms |   +1.8% |
| 한 행 삭제, 기준 먼저 |  12.598ms |  13.198ms |     +4.8% |  1.615ms |  1.670ms |   +3.4% |
| 한 행 삭제, 후보 먼저 |  12.477ms |  12.801ms |     +2.6% |  1.637ms |  1.668ms |   +1.9% |

한 행 삭제는 순서를 바꿔도 전체·JS 모두 조금 늘었다. 이번 측정만으로 모든 차이를 함수
분리의 비용으로 확정하지는 않지만, 전체 삭제의 작은 이득만 보고 채택할 결과는 아니다.
후보의 brotli 크기도 base·concurrent에서 각각 **12B** 늘었다. **결정은 `reject`**다.
9개 전체 CPU 항목을 새로 비교하지 않았으므로 종합 개선율을 계산하지 않았다.

DOM 일괄 제거와 일반 DOM의 개별 리스너 해제 생략은 이미 적용돼 있다. 남은 순회에서는
컴포넌트 unmount와 외부 portal 정리를 지켜야 한다. 하위 트리의 정리 필요 여부를 미리
추적해 순회를 줄이는 구조는 가능성 있는 후속 방향이지만, 생성·갱신과 메모리 비용이 추가될
수 있다. 이 구조를 이번에 구현하거나 검증한 것은 아니다. 배포 전 추가 대규모 최적화로
확장하지 않고 이번 후보 검증으로 마무리했다.

## 최종 상태와 원본

- 함수 분리만 되돌렸고, 9개 런타임 파일이 측정 기준 스냅샷과 정확히 일치한다.
  다시 빌드한 base core의 SHA-256도 기준 manifest와 일치한다.
- 후보와 복원 후 각각 base 18개·concurrent 22개의 portal·discarded listener·destroy/unmount
  계약 검사를 통과했다. 두 코어 빌드와 변경 파일 ESLint도 통과했다.
- 후보의 양쪽 공식 keyed·9개 동작·폰트 검사도 통과했다. 후보는 기능 실패 때문에 거절한 것이
  아니다. 이전 전체 단위·dual·Playwright 검증의 런타임을 복원했으며, 전체 검사를 새로 반복하지 않았다.
- 현재 크기는 다시 base **4,855 / 4,800B**, concurrent **6,385 / 9,000B**, element **998 / 1,000B**다.
  기존 base 크기 게이트의 **55B 초과**는 남는다. 한도를 올리거나 버전·커밋·배포를 변경하지 않았다.
- [unmount-results.json](./unmount-results.json)에 210개 공식 표본과 144개 진단 표본, 환경·해시·
  검증 결과·미채택 결정을 보존했다. [unmount-evidence.json.gz](./unmount-evidence.json.gz)에 두 앱
  입력·번들, 양쪽 런타임 9개 파일, 진단 번들과 측정 도구를 보존했다. 압축 해시는 결과 파일에 있다.
- [followup-edits.mjs](./followup-edits.mjs)의 `portalCold`로 진단 후보를 만들 수 있다.
  공식 비교는 보존한 기준·후보 런타임을 각각 빌드해 [creation-prepare.mjs](./creation-prepare.mjs)의
  `before`·`after` 단계로 준비하고 [production-run.mjs](./production-run.mjs)로 실행한다.
  [unmount-summarize.mjs](./unmount-summarize.mjs)는 네 공식 차수와 진단을 검증하고 원본을 묶는다.
  기존 성능·호환성 자료는 덮어쓰지 않았다.
