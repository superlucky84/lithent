# 행 선택·부분 갱신 개선 — 2026-10-19

> 구조 변경의 상쇄 비용을 줄이는 [후속 실험](./STRUCTURAL_UPDATE_RESULTS.md)을 추가했다.
> 교환·한 행 삭제의 개선 가능성을 확인했지만 전체 삭제·교체가 더 느려져 후속 후보는 미채택했다.
> 이 문서의 앞선 후보와 실제 upstream 앱은 그대로 유지한다.

선택·부분 갱신을 우선한 앱 후보다. 두 항목의 비용은 줄었으나, 9개 CPU 항목 전체에 로컬 결과표
가중치를 적용한 후보/기존 비율은 **1.0473**으로 약 **4.7% 느려졌다**. 교환·삭제·추가의 비용을
함께 확인해야 하며, 전체 성능의 개선안으로 해석하면 안 된다. 코어 최적화나 릴리스는 포함하지 않는다.

## 적용 방식

[기존 진단](./SELECT_PARTIAL_UPDATE_ANALYSIS.md)의 전체 Table 갱신을 행별 `renew`로 바꿨다.
선택은 이전·새 행, 부분 갱신은 라벨이 바뀐 행을 갱신한다. Table은 생성·교체·추가·교환·삭제 때만
갱신한다. [최종 앱 소스](./targeted-main.tsx)는 공개 `mount`, `h`, `cacheUpdate`만 사용한다.

- 행 ID와 삭제 버튼, 빈 셀의 VDOM을 mounter에서 한 번 만든다. 라벨 셀은 문자열 의존성으로 캐시한다.
- 행 전체도 `[row.label, selected === row]`로 캐시해 부모의 구조 갱신에서 정적인 출력은 재사용한다.
- 행의 props 객체를 재사용해 구조 갱신 때 새 props 할당과 동일 값 복사를 줄인다.
- 선택 상태는 선택된 행 객체 하나다. 교체·전체 삭제·선택 행 삭제 때 참조를 해제한다.
- DOM 직접 변경, 앱 이벤트 위임, 벤치마크 횟수에 따른 특수 처리, 지연 렌더는 사용하지 않는다.

코어와 helper는 npm `lithent@1.25.2`와 동일하다. `makeNewWDomTree` 조기 반환 후보를 복원하거나
공개 API를 추가하지 않았다. 렌더되는 행 수를 줄여도 코어 `replaceWDom`의 부모 배열 `indexOf`는
남으므로 선택 전체가 엄밀하게 O(1)이라고 주장하지 않는다.

## 측정 조건

`~/project/js-framework-benchmark-upstream`의 원본 `executeBenchmark`를 호출했다. 기존 Vite
5.4.21 프로덕션 설정, 준비 횟수, 시나리오별 CPU 배율, GC, 새 탭, trace·paint 계산을 유지했다.
배포된 core·helper의 바이트가 전후 동일하다. 비교군은 같은 checkout의 소스와 lockfile로 각각
`npm ci`와 원래 `build-prod`를 실행했다.

React hooks는 19.2.0, React classes는 19.0.0, Preact hooks/classes는 11.0.0이다.
버전 차이는 upstream lockfile 그대로이며, 새 버전으로 임의 교체하지 않았다.

최종 후보의 CPU는 전후 9개 항목 290개 표본과 선택·부분 갱신의 6개 구현 비교 240개 표본이다.
9개 항목에서는 기존 앱을 먼저 실행하고, 핵심 두 항목의 추가 차수에서는 후보를 먼저 실행했다.
선택은 차수당 25회, 나머지는 15회다. 초기 후보의 240개 공식 표본과 진단은 별도로 보존하며
최종 수치에 합치지 않는다. 전용으로 격리한 머신이 아니므로 부하·프레임 타이밍 오차는 남는다.

## 선택·부분 갱신 비교

최종 전후 두 차수를 합친 중앙값이다. Lithent의 부분 갱신은 30개, 선택은 50개 표본이고,
비교군은 각각 15개·25개다. 모두 동일한 Chrome **155.0.8059.82**, Apple **M4 Pro** 12코어·24GB에서
측정했다. 후보의 부분 갱신은 기존 대비 **약 15.3%**, 선택은 **약 40.5%** 줄었다.

| 구현                  | 부분 갱신 전체 ms | 선택 전체 ms | 부분 갱신 JS ms | 선택 JS ms |
| --------------------- | ----------------: | -----------: | --------------: | ---------: |
| 기존 Lithent          |            18.265 |        7.369 |           6.206 |      4.305 |
| 행별 renew 후보       |        **15.474** |    **4.387** |       **3.755** |  **0.619** |
| React hooks 19.2.0    |            16.861 |        6.200 |           4.668 |      3.121 |
| React classes 19.0.0  |            17.183 |        6.631 |           4.198 |      3.525 |
| Preact hooks 11.0.0   |            24.959 |       15.288 |          11.035 |     10.981 |
| Preact classes 11.0.0 |            15.240 |        4.570 |           2.475 |      1.556 |

이번 조건에서 후보의 부분 갱신은 Preact classes보다 약 1.5% 느리고, 선택은 약 4.0% 빨랐다.
이 작은 차이를 환경을 넘어선 우열로 해석하지 않고, 두 항목이 비슷한 수준에 도달했다고 평가한다.
부분 갱신의 차수별 전후는 **17.693 → 14.925ms**, 역순은 **18.401 → 15.774ms**다.
선택은 **7.207 → 4.928ms**, 역순은 **7.606 → 3.684ms**다. JS 개선은 두 차수에 나타나지만,
선택 전체 시간에는 paint·프레임 대기 변동도 크다.

## 9개 CPU 항목의 상쇄 비용

첫 차수의 중앙값 ms다. 각 항목 15회, 선택 25회이며, paint를 포함한 전체 시간이다.

| 항목             | 기존 전체 | 후보 전체 | 기존 JS | 후보 JS |
| ---------------- | --------: | --------: | ------: | ------: |
| 01 1,000행 생성  |    27.808 |    28.238 |   8.221 |   8.720 |
| 02 1,000행 교체  |    31.097 |    31.058 |  11.657 |  11.437 |
| 03 부분 갱신     |    17.693 |    14.925 |   6.078 |   3.741 |
| 04 선택          |     7.207 |     4.928 |   4.185 |   0.679 |
| 05 교환          |    16.776 |    25.355 |   3.648 |   9.639 |
| 06 한 행 삭제    |    12.227 |    14.775 |   1.206 |   3.538 |
| 07 10,000행 생성 |   288.803 |   304.874 |  64.379 |  79.023 |
| 08 1,000행 추가  |    30.871 |    34.502 |   8.172 |  10.917 |
| 09 전체 삭제     |    11.553 |    14.841 |   9.266 |  12.472 |

행별 컴포넌트를 둔 비용이 구조 갱신 때 드러난다. 부모가 모든 행 컴포넌트를 통과하고,
행 제거 때 컴포넌트 정리도 필요하다. 1,000행 생성·교체의 작은 차이를 확정적인 개선으로
평가하지 않는다. 10,000행 생성은 이번 차수에서 전체 약 5.6%, JS 약 22.7% 늘었다.

가중 비율은 첫 차수 9개 항목만으로 계산했다. `webdriver-ts-results/src/Common.ts`의 가중치를
그대로 사용했으며 공개 공식 점수가 아니다. 핵심 두 항목만 추가 측정한 차수를 전체 가중치에
섞거나, 두 항목으로 React·Preact의 9개 항목 전체 순위를 추정하지 않는다.
동일 가중치의 JS 후보/기존 비율도 **1.1278**, 약 **12.8% 증가**다.

## 메모리

원본 러너의 `performance.measureUserAgentSpecificMemory()`로 3회씩 측정했다. 1,000행을 보유할 때
중앙값은 **3.502 → 4.421MB**, 약 **26.2% 증가**했다. 행별 컴포넌트 상태와 캐시를 유지하는 비용이다.
JS heap만의 크기가 아니며, CPU 목표 두 항목의 개선과 함께 판단해야 한다.

생성·삭제 5회 뒤 공식 메모리는 **0.903 → 0.942MB**였다. 별도의 GC 후 진단을 새 컨텍스트에서
3차수 실행해 생성·삭제를 100회 반복했고, 전후 모두 DOM 노드 **63개**, 리스너 **32개**로 돌아왔다.
후보의 1,000행 부분 갱신 0회·100회 뒤 JS heap 중앙값은 **4.569 → 4.820MiB**다.
라벨 문자열이 계속 길어지는 조건이며, 이 경로에서 과거처럼 큰 VDOM 선형 누적은 관찰하지 않았다.
이 진단을 공식 메모리 값과 합치거나 모든 경로의 누수가 없다는 증명으로 쓰지 않는다.

## 검증

- 전후 앱과 비교군 4개 모두 원본 `isKeyed` 및 9개 동작·실제 glyph 폰트 로딩 검사를 통과했다.
- 작은 갱신은 기존 `tr`를 유지했다. 선택 이동의 DOM 변경은 class 2개, 부분 갱신은 텍스트 100개이며
  두 경우 모두 자식 삽입·삭제는 없었다.
- 교환 후 선택·삭제, 선택 후 추가·교체, 선택된 행 삭제를 검사했다.
- 부모 구조 변경과 행 갱신을 한 task에 양쪽 순서로 예약해도 DOM 순서·라벨이 맞았다.
- 행 갱신을 예약하고 바로 전체 삭제하는 경우와 이후 재생성·선택을 20회 반복해 검사했다.
- strict TypeScript, 변경 앱 ESLint, 도구 Prettier와 `pnpm size`를 통과했다. 코어는 변경하지 않았으며
  기존 base UMD br는 **4,798 / 4,800B**다.
- 마지막에 수동 `h` 호출의 컴포넌트 타입 단언만 보완했다. 보완 전후 소스·manifest를 별도 보존했고,
  두 프로덕션 JS의 SHA-256은 **동일**하다. TypeScript에서 지워지는 변경이므로 같은 실행 바이트의
  성능 표본을 유지했다.
- 실제 upstream 작업트리에 최종 소스를 반영하고 원래 `npm run build-prod`를 실행했다.
  실제 `dist/main.js`가 측정한 후보와 바이트까지 일치한다. 실제 파일의 keyed·9개 동작·폰트도 재검사했다.

공유 CSS를 제외한 프로덕션 HTML+JS 합계 gzip은 **6,370 → 6,476B**로 106B 늘었다.

## 원본과 재현

[targeted-update-results.json](./targeted-update-results.json)은 공식 표본·진단·환경·소스 및 번들
해시를, [targeted-update-evidence.json.gz](./targeted-update-evidence.json.gz)는 전후 앱·core·helper,
비교군 소스·lockfile·프로덕션 번들, 실행한 러너 JS와 재현 도구를 보존한다. 과거 진단 원본은 유지한다.
trace 파일은 결과 JSON의 `traceDirectory`에 남긴다.
03·04는 추가 차수에서 같은 trace 파일명을 재사용했으므로 해당 trace는 추가 차수분이다.
첫 차수의 숫자 표본은 결과 JSON에 모두 보존했으며, 530개 전부의 trace를 보존했다는 의미는 아니다.

새 출력 경로와 원본 벤치마크 앱을 준비한 뒤 다음과 같이 실행한다. 앱을 이미 교체했다면
보존된 `final/sources/lithent-before/src/main.tsx`를 추출해 `LITHENT_BASELINE_SOURCE`로 지정한다.

```sh
export LITHENT_PRODUCTION_OUT=/tmp/lithent-targeted-rerun
export LITHENT_BENCHMARK_ROOT="$HOME/project/js-framework-benchmark-upstream"
node docs/benchmark/targeted-update.mjs peers
node docs/benchmark/targeted-update.mjs suite
```

`suite`는 새 출력을 요구한다. 개별 단계 재실행은 `contracts`, `diagnostic`, `verify`, `cpu`, `mem`,
`retention` 모드로 실행한다. CPU가 중단되면 동일 manifest에서 `LITHENT_PRODUCTION_RESUME=1`로
완료된 묶음을 유지하고 이어갈 수 있다. 서로 다른 성능 측정은 동시에 실행하지 않는다.
별도 보존된 비교군을 재사용할 때는 해당 출력 디렉터리를 `LITHENT_PEERS_OUT`으로 지정한다.
