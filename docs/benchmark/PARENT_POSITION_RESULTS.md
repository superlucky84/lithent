# C1 — 컴포넌트 부모 위치 검색 후보

2026-10-21, 시작 HEAD `979f88f222c45cadadd1871d8d9f861a5e71f9a0`.

**C1 한정 검증 완료, 기본 코어 채택은 보류한다.** 큰 목록의 반복 자체 갱신에서
실제 이득은 확인했지만, 원래 앱의 전체 가중 시간은 한 차수에서 **−0.55%**로 작고
크기 게이트는 53B 초과했다. 후보 소스·측정은 보존하고 런타임은 baseline으로 복원한다.
한 항목의 회귀 때문에 기각하거나 코어가 최적이라고 판정한 결과가 아니다.

[진단 도구](./parent-position.mjs), [집계·보존 도구](./parent-position-summarize.mjs).

## 변경과 적용 범위

base `replaceWDom`에 `WeakMap<CompKey, WeakMap<WDom[], number>>`를 추가했다.
같은 부모 배열에서 자체 갱신을 반복하면 저장한 위치의 노드 identity를 확인해 재검색을
생략한다. 최초 접근·새 부모 배열·stale 위치는 기존 `indexOf`를 수행하고 성공 위치만
저장한다. index 0과 미등록 상태를 구분하고 compKey 없는 공개 호출도 기존 경로로 처리한다.

slot 설명 배열은 같은 노드를 여러 번 담을 수 있어 native 첫 등장 검색을 유지한다.
concurrent의 commit 경로는 수정하지 않는다. 전체 WDom의 필드 추가, 생성 시 eager
인덱싱, 구조 변경 때 전체 위치 재작성, 공개 API 변경은 없다.

이 후보는 **자식 컴포넌트의 반복 자체 갱신**을 줄인다. 원래 Table 앱의 부모 검색은
한 칸이므로 1,000행 cache 검사·keyed 매칭·diff/render 순회는 그대로다.

## 검증 방법

- 기준선은 npm `lithent@1.25.2`, 후보는 변경한 base ESM이다. helper와 앱은 고정했다.
- 원래 앱을 기존 증거의 `official-main.tsx`에서 추출해 양쪽 production 빌드에 동일하게
  넣었다. 실제 sibling의 기존 targeted 앱은 변경하지 않았다.
- 일반 입력 예제에서 1k/10k, 직접 자식/중첩 slot, 처음/말미/10% 갱신, 반복 갱신,
  부모 역순 갱신 뒤 자체 갱신을 확인한다. 추가로 live 배열의 in-place 순서를 바꾼
  **합성 stale 진단**을 수행한다. 이 조작은 권장 앱 패턴이나 시간 측정 시나리오가 아니다.
- 계측 빌드의 카운터와 비계측 production ESM의 시간·메모리를 분리한다. 일반 시간은
  throttle 없는 JS + `nextTick`이며 공식 클릭→paint 지표가 아니다.
- 공식 러너는 Phase 1과 같은 Chrome `155.0.8059.85`, upstream checkout·9개 시나리오를
  사용한다. 메타데이터·번들·브라우저 해시는 raw 결과와 압축 증거에 남긴다.

- `pnpm test:dual`: 13개 suite의 합계 **1,050 passed, 3 skipped**. base 399,
  concurrent 302이며 새로운 부모 위치 회귀 4개씩을 포함한다.
- 최초 build는 새 테스트의 props 타입에 `key`가 없어 실패했다. 타입 수정 뒤

- 후보 UMD: raw **12,882B**, gzip **5,227B**, brotli **4,853B**.
  baseline brotli **4,798B**에서 **55B 증가**, 현행 **4,800B 한도보다 53B 초과**다.
  게이트를 변경하지 않았다. concurrent 6,903B·element 998B는 기존 산출물과 같다.
- 동일 production 두 빌드의 DOM·선택·부분 갱신·배칭 계약과 공식 keyed·9개 동작·폰트
  검사는 통과했다. 최종 채택 단계의 전체 e2e·peer 비교를 대신하지 않는다.

## 검색과 실제 갱신 시간

64개 일반 시나리오와 4개 합성 stale 검사에서 입력 값·행 순서·DOM 정체성을 확인했다.
1만 항목 중 1천 개의 warm 갱신은 부모 native 검색 방문 추정 **4,996,000 → 0회**,
대신 위치 lookup/identity 확인 **1,000회**였다. 직접 자식/중첩 slot 양쪽에서 같다.
중첩 예제의 조상 slot 검색 **4,997,000회**는 그대로 남는다.

처음 접근은 여전히 검색한다. 선행 첫/말미 갱신 때문에 부분 갱신의 첫 차수에는 1개가
이미 warm이며, 나머지 999개는 native 검색·WeakMap 생성·위치 쓰기를 수행한다.
부모 역순 갱신으로 배열이 교체되면 다시 검색하고, 같은 배열의 합성 stale은 identity
실패 뒤 native 결과 1번 위치로 복구했다. 전체 위치를 미리 재작성하지 않는다.

아래는 서로 독립적인 context 3개에서 각 5회 예열 후 30회 측정한 중앙값이다.
CPU throttle 없는 **JS + nextTick 진단**이며 paint 시간·공식 점수와 섞지 않는다.

| 항목 수 / 변경 수 | 구조      | baseline ms |  C1 ms |   변화 |
| ----------------- | --------- | ----------: | -----: | -----: |
| 1,000 / 100       | 직접 자식 |      0.2500 | 0.2475 |  −1.0% |
| 1,000 / 100       | 중첩 slot |      0.2675 | 0.2600 |  −2.8% |
| 10,000 / 1,000    | 직접 자식 |      2.1550 | 1.7650 | −18.1% |
| 10,000 / 1,000    | 중첩 slot |      2.7725 | 2.3000 | −17.0% |

10k에서는 세 context 모두 후보의 warm 중앙값이 더 낮았다. 1k의 이득은 매우 작다.
10k 첫 갱신은 직접 자식 5.920→5.910ms, slot 6.600→6.610ms로 같았고,
역순 재구성 직후에는 4.120→4.185ms / 5.440→5.560ms였다. 최초 검색·배열 교체의
비용을 없앤 결과가 아니다. 생성/역순 3개씩의 원본 분포도 JSON에 보존하며 작은
표본으로 생성 성능 우열을 확정하지 않는다.

## 공식 원래 앱: 전체 9항목 사전 비교

동일 앱·helper, 고정 Chrome의 **290개 표본**, 실패·재시도 0회다. 실행은
2026-10-21 12:47:20~12:54:54 UTC. 각 항목에서 앱 순서를 번갈았으나 전체 반대 순서의
두 번째 차수는 실행하지 않았다. 시스템 부하는 격리하지 않았고 시작/종료·배치별 load를
기록했다. 이는 Phase 2 사전 비교이며 Phase 4의 최종 비교가 아니다.

큰 목록 자체 갱신의 진단 개선율을 이 표에 적용하지 않는다.

## 메모리·회수

1천 컴포넌트를 모두 자체 갱신해 위치를 채운 일반 예제의 강제 GC 후 JS heap 중앙값은
**2,792,348 → 2,876,856B**, 약 **+82.5KiB (+3.0%)**였다. 공식 메모리 지표가 아닌
CDP JS heap이다. 생성 직후 중앙값은 2,740,172→2,740,280B였으며 lazy 저장이라
아직 1천 개 inner WeakMap이 생기지 않는다. 한 모듈당 outer WeakMap 1개는 존재한다.

해제 후에도 1천 component key를 일부러 유지한 3개 context씩에서 component 등록 0개,
기존 VDOM 1천 개와 부모 배열 1개의 WeakRef 생존 0개, host DOM 0개를 확인했다.
키가 살아 있으면 빈 inner WeakMap의 비용은 남을 수 있다. 해제 후 heap도 raw에 남겼으며
JIT/GC 등의 차이를 포함하므로 그 차이를 그대로 캐시의 순수 크기로 환산하지 않는다.
100회 생성/삭제·공식 메모리 5항목·peer 메모리 비교는 이번 미채택 사전 후보에서 미실행이다.

## 판단과 다음 작업

- C1은 큰 목록의 반복 자체 갱신을 개선하는 근거가 있다. 소스와 증거를 보존해 후속
  후보와 결합할 때 다시 비교할 수 있다. 일부 회귀나 +82.5KiB 자체가 치명적이라는 판정은 없다.
- 현재 목표의 핵심인 원래 Table의 전체 순회를 해결하지 못하고, 공식 전체 이득은
  단일 차수 −0.55%에 그쳤다. 크기 상쇄/옵트인 분리도 아직 없다. 이번 구현을 기본값으로
  채택하거나 reverse·peer 검증을 통과한 것처럼 표시하지 않는다.
- 다음은 **C3의 부모 갱신과 자체 갱신 분리 계약**을 구체화한다. Phase 1에서 확인한
  불필요한 부모 기인 updater n회와 retained-row 앱의 개선 근거를 연결하되, 현재 live
  VDOM을 앱이 직접 읽지 않아도 되는 범용 계약을 먼저 정한다. C2는 시간상 기각 없이
  별도 보류, C1의 slot/concurrent 확장도 별도 연구다.
- 추가 C1을 검토한다면 parent-array를 outer weak key로 하는 저장 구조로 inner map의
  컴포넌트당 생성 비용을 줄일 가능성이 있다. **미구현 가설**이며 이번 수치에 포함하지 않는다.

## 재현

[후보 패치](./parent-position-candidate.patch)는 baseline의 `src/wDom.ts`에만 적용된다.
별도 checkout에 적용한 뒤 core를 빌드하고, 새 출력 디렉터리에서 실행한다.

```sh
pnpm build:core
LITHENT_C1_OUT=/tmp/c1-fresh/diagnostic-v3 node docs/benchmark/parent-position.mjs prepare
LITHENT_C1_OUT=/tmp/c1-fresh/diagnostic-v3 node docs/benchmark/parent-position.mjs measure
```

공식 앱 준비는 `targeted-update.mjs prepare`에 `LITHENT_BASELINE_SOURCE`와
`LITHENT_CANDIDATE_SOURCE` 모두 원래 앱 경로를 지정하고 `LITHENT_CANDIDATE_CORE`에
후보 ESM 경로를 지정한다. `contracts`, `verify`, `cpu lithent-before,lithent`를 순서대로
실행한다. 실제 실행 명령·경로·로그는 증거에 보존한다.

진단 도구 초기 버전은 숫자 0의 input 표현을 문자열로 가정해 baseline 검사에 실패했다.
문자열 필드로 고친 뒤의 초기 회수 검사도 baseline/candidate 모두 노드가 남아 실패했다.
해제 함수의 지역 배열을 캡처할 수 있는 검사 콜백을 module-level noop으로 바꾸고,
GC 전 event-loop task 경계를 추가한 최종 `diagnostic-v3`에서 양쪽 회수를 확인했다.
앞선 실행은 최종 수치와 합산하지 않는다.
