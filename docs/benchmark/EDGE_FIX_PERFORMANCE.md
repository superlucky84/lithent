# 엣지 케이스 수정의 렌더링 성능 영향 — 2026-10-15

React·preact·inferno 엣지 케이스를 옮겨 와 고친 base 코어 수정(브랜치 `ccr-31c1aa56-9zffas`)이
이 디렉터리와 [performance-improvement](../performance-improvement/)에 기록된 렌더링 성능
개선을 되돌리지 않는지 사용자 요청으로 확인했다. 확인하면서 찾은 비용은 줄였고, 그 과정에서
찾은 HMR 회귀도 고쳤다. 이어서 사용자 요청으로 크기를 한도 안으로 줄였다(`17b10e6`,
아래 "크기 줄이기").

## 결론

- **느려진 렌더링 경로는 찾지 못했다.** 프레임워크 JS 명령어 수는 main 대비 공식 벤치마크 앱
  구조(행 컴포넌트 없이 행마다 `cacheUpdate`, 아래 `flat`)에서 −0.9%~−26.8%, 행마다 컴포넌트가
  있는 앱에서 −0.5%~−11.3%다. 하나뿐인 증가는 행 컴포넌트 1,000개 생성의 +0.7%다.
- Chromium(실제 DOM)에서도 재렌더는 main과 같거나 빠르다. flat 선택 0.674 → 0.584ms,
  교환 0.668 → 0.512ms, 갱신 2.589 → 2.001ms다. 생성은 라운드 간 변동 안에 있다.
- 세 앱 × 8개 시나리오 모두 DOM 쓰기(삽입·제거·교체, 속성, 리스너, textContent 횟수)가 main과
  같다. 반복 갱신 후 heap도 늘지 않는다.
  이전 VDOM 회수 계약([parent-retention](../../e2e/parent-retention.spec.ts))을 포함한 e2e 64개가 통과한다.
- 크기: base **br 4,791 → 4,784B / 4,800B**(dist, `pnpm size`). concurrent는 6,679 → 6,895B / 9,000B다.

## 측정 방법

도구는 [edge-fix/](./edge-fix/)에 있다. 앱([app.tsx](./edge-fix/app.tsx))은
[adapter-baseline](./adapter-baseline/main.tsx)을 seed 고정 라벨로 만든 것이며 세 형태로 돌린다.

| 이름     | 구조                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------- |
| `flat`   | 공식 앱([APP_AUDIT](./APP_AUDIT.md)의 flatFull): 행 mount 없음, 행마다 `cacheUpdate`로 keyed `tr` |
| `cached` | adapter-baseline: 행 `mount` + `cacheUpdate`                                                      |
| `plain`  | 행 `mount`, 캐시 없음 (일반 앱에 가까운 형태)                                                     |

- **명령어 수**: callgrind로 `node --predictable --single-threaded`의 명령어를 센다. young generation을
  1GB로 키워 GC가 돌지 않으므로 프레임워크 자신의 비용이다. DOM은 O(1) stub이다.
  30 사이클 워밍업 뒤 (40 사이클 − 30 사이클) / 10. 같은 번들은 매번 같은 값이 나온다.
  빌드가 다르면 코드 배치만으로 ±1% 안팎이 달라질 수 있다.
- **GC 작업량**: 기본 heap에서 `--trace-gc-nvp`로 60~100 사이클 동안 scavenge가 복사·승격한
  바이트를 더한다. 단일 스레드 GC 기준이다.
- **브라우저**: Chromium 141 headless(Playwright), 실제 DOM. 페이지마다 30회 워밍업 뒤 300회
  (생성은 100회) 연산의 평균을 재고, 변형 순서를 라운드마다 뒤집어 16라운드의 중앙값을 낸다.
  layout·paint는 강제하지 않으므로 공식 러너 수치와 직접 비교하지 않는다. 라운드 간 변동은 ±10~20%다.
- 공식 러너([production-run.mjs](./production-run.mjs))로는 재지 않았다. 이 환경에는
  js-framework-benchmark checkout이 없다.

## HMR 회귀 (`1f46202`에서 수정)

e2e를 돌려 보니 `hmr-stateless.spec.ts` 두 개가 base·concurrent 모두에서 실패했다(main은 통과).
새로 만든 컴포넌트의 출력 안에 있는 컴포넌트는 diff 없이 바로 인스턴스가 만들어지는데,
그것을 그릴 때 다시 복사해 **인스턴스가 둘** 생겼다. 먼저 만든 인스턴스는 setup·HMR 등록만
되고 그려지지 않아, HMR 경계가 DOM을 찾지 못하고 전체 새로고침으로 넘어갔다. 이미 그린
노드만 복사하도록 고쳤다. 렌더 fuzz와 matrix는 이제 같은 노드에서 나온 인스턴스가 그려지지
않은 채 남는지도 검사한다.

## 크기 줄이기 (`17b10e6`)

base UMD는 vite의 esbuild minify 뒤 terser로 이름만 줄인다(`compress: false`, 부모 getter를
격리하는 함수 경계를 지키기 위해서다). 그 위에서 코드만 고쳐 br 5,082 → 4,784B가 됐다.
같은 빌드를 1초 안에 만드는 측정으로 바꿀 때마다 크기를 쟀고, brotli 때문에 원본 바이트가
줄어도 압축 크기가 늘어나는 변경(반복 패턴을 함수로 묶기 등)은 넣지 않았다.

- `getWDomType`은 노드 종류를 네 번 검사하는 대신 `type`을 읽는다. 이것이 부르는 같은 종류
  검사들은 유일한 호출자가 이미 확인한 것(평범한 노드, 원본이 있음)을 다시 보지 않는다.
  행마다 `'resolve' in node` 조회가 여러 번 줄어 재렌더 명령어가 크게 줄었다.
- `diffLoopChildren`이 남은 원본을 직접 지우고, 컴포넌트 children은 splice 한 번으로 맞추며,
  LIS는 뒤에 붙는 값의 빠른 경로를 유지한 채 한 번의 순회로 쓴다.
- 렌더 핸들러, 루트 삽입, 부모·형제 찾기, 삭제, 스타일 갱신에서 중복 분기를 없앴다.
  `updateProps`는 이벤트를 먼저 처리한다(키가 "on"으로 시작해 나머지 키와 겹치지 않는다).
  hydration 여부에 따라 하는 일이 같았던 매개변수는 뺐다.
- 훅은 실행 중인 컴포넌트를 한 helper로 얻고, 큐 실행 함수는 모든 항목에 있는 큐의 존재 확인을 뺐다.
  컴포넌트 인스턴스는 감싸는 함수 호출과 배열 반환 하나씩을 덜 쓴다.

추가와 갱신의 children 재구성을 한 함수로 합친 판은 크기를 9B 더 줄였지만 1,000행 생성이
6% 느려져(명령어, Chromium 모두) 되돌렸다. 두 함수로 둔 이유는 코드 주석에 남겼다.
concurrent 코어는 공유하는 `predicator.ts` 변경만 받는다.

## 남은 차이와 판단

- **행 컴포넌트 생성 +0.7%(plain 명령어)**: `makeNewWDomTree`가 새 노드마다 이미 그린
  노드인지(`nr`) 확인하는 비용이다. 이 검사가 hoisted 노드·같은 노드의 여러 위치 수정의 핵심이다.
  Chromium의 전체 삭제 + 생성 시간에서는 차이가 보이지 않았다.
- **요소 노드의 children**: main은 교체된 원본의 `children`을 모두 비웠다. 그렇게 하면
  hoisted 상수를 다시 그릴 때, 한 노드를 여러 곳에 그릴 때, 컴포넌트가 받은 children을 다시
  배치할 때 빈 노드가 그려진다(되돌리면 회귀 테스트 3개와 fuzz 묶음 12개가 실패한다). 그래서
  컴포넌트 노드만 비운다. 대신 plain 앱에서 단일 스레드 GC의 scavenge 복사량이 사이클당 약
  2.4MB → 5.9MB로 는다. flat 앱은 GC 자체가 거의 돌지 않아 차이가 없다. Chromium에서는 요소까지
  비운 변형과 차이가 없었다(plain 선택 7.05 vs 7.09ms, 교환 7.19 vs 7.25ms, 갱신 8.54 vs 8.57ms).
- **크기 여유**: base 16B, element 2B. 다음 변경은 크기 측정부터 해야 한다.

## 후속 정확성 수정 — 2026-10-16

기준은 `b420187`이다. 위 성능 기록 이후의 릴리스 검토에서 찾은 세 가지 누락을 고쳤다.

- 같은 컴포넌트 노드를 서로 다른 부모 아래 재사용하면 `h()`가 첫 노드의 부모 링크를
  마지막 부모로 덮어썼다. 그 인스턴스가 자체 갱신으로 태그를 바꾸면 `NotFoundError`가 났다.
  이제 처음 그리는 자식과 복제한 자식 모두 실제 부모를 가리키며, 형제들은 getter 하나를 공유한다.
- 렌더 예외 뒤 이미 큐에 있던 다른 컴포넌트의 갱신은 새 `renew()`가 오기 전까지 정체됐다.
  base·Concurrent sync 큐는 남은 일을 다른 microtask에 이어 실행한다. Concurrent low 큐도
  남은 작업과 `whenIdle()` 대기를 다음 task에서 마친다. 원래 예외는 그대로 보고한다.
- 런타임이 빈 자식으로 처리하는 `true`를 공개 `MiddleStateWDom` 타입에도 허용했다.
  기존 테스트의 강제 캐스팅을 없애고 배포 선언을 사용하는 소비자 검증에 추가했다.

회귀 테스트는 서로 다른 부모에 있는 두 인스턴스 각각의 태그 교체·빈 출력·다중 출력·해제,
같은 tick에 예약된 형제의 오류 복구, low 큐의 남은 작업 유무에 따른 idle 완료를 확인한다.
각 오류 재현은 수정 전 실패하고 수정 후 통과했다.

관련 파일: `src/tests/core-edgeRegressions.test.tsx`, `src/tests/core-redrawRecovery.test.tsx`,
`lithentConcurrent/src/tests/concurrent-schedulerLane.test.tsx`, `scripts/verify-release.mjs`.

검증 결과:

- 전체 workspace 빌드·TypeScript·ESLint, `pnpm test`, `pnpm test:concurrent`,
  `pnpm test:satellites:concurrent`, base SSR 테스트 통과.
- `verify:concurrent`, `verify:release` 통과. 두 코어의 실제 tarball을 설치한 소비자가
  강제 캐스팅 없이 `true` 자식과 `true`를 반환하는 컴포넌트를 타입 검사한다.
- 기존 Chromium E2E **64개 통과**. 배포 ESM을 직접 불러온 별도 Chromium 재현에서도
  두 부모의 컴포넌트 자체 갱신이 정상이며 DOM 예외가 없다.
- base **br 4,798 / 4,800B**, Concurrent **6,903 / 9,000B**, element **998 / 1,000B**.
- 위 `edge-fix/domwrites.mjs`로 `b420187`과 비교한 세 앱 × 8개 시나리오의 DOM 쓰기는
