# 엣지 케이스 수정의 렌더링 성능 영향 — 2026-10-15

React·preact·inferno 엣지 케이스를 옮겨 와 고친 base 코어 수정(브랜치 `ccr-31c1aa56-9zffas`)이
이 디렉터리와 [performance-improvement](../performance-improvement/)에 기록된 렌더링 성능
개선을 되돌리지 않는지 사용자 요청으로 확인했다. 확인하면서 찾은 비용은 줄였고, 그 과정에서
찾은 HMR 회귀도 고쳤다.

## 결론

- **느려진 렌더링 경로는 찾지 못했다.** 실제 DOM의 Chromium에서 모든 측정 항목이 main과 같거나
  빠르다. 프레임워크 JS 명령어 수는 생성(+3.1%)을 빼면 main 대비 −5.1%~+1.2%다.
- 공식 벤치마크 앱 구조(행 컴포넌트 없이 행마다 `cacheUpdate`, 아래 `flat`)의 선택은 명령어 −4.4%,
  삭제 −5.1%, 교체 −1.8%다.
- 세 앱 × 8개 시나리오 모두 DOM 쓰기(삽입·제거·교체, 속성, 리스너, textContent 횟수)가 main과
  같다. 반복 갱신 후 heap도 늘지 않는다.
  이전 VDOM 회수 계약([parent-retention](../../e2e/parent-retention.spec.ts))을 포함한 e2e 64개가 통과한다.
- 남은 판단: base 크기가 **br 4,791 → 5,082B**로 한도 4,800B를 **282B 초과**한다.
  concurrent는 6,679 → 6,971B / 9,000B다.

## 측정 방법

도구는 [edge-fix/](./edge-fix/)에 있다. 앱([app.tsx](./edge-fix/app.tsx))은
[adapter-baseline](./adapter-baseline/main.tsx)을 seed 고정 라벨로 만든 것이며 세 형태로 돌린다.

| 이름     | 구조                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------- |
| `flat`   | 공식 앱([APP_AUDIT](./APP_AUDIT.md)의 flatFull): 행 mount 없음, 행마다 `cacheUpdate`로 keyed `tr` |
| `cached` | adapter-baseline: 행 `mount` + `cacheUpdate`                                                      |
| `plain`  | 행 `mount`, 캐시 없음 (일반 앱에 가까운 형태)                                                     |

- **명령어 수**: callgrind로 `node --predictable --single-threaded`의 명령어를 센다. young generation을
  1GB로 키워 GC가 돌지 않으므로 프레임워크 자신의 비용이다. DOM은 O(1) stub이다.
  30 사이클 워밍업 뒤 (40 사이클 − 30 사이클) / 10. 같은 번들은 매번 같은 값이 나온다.
  빌드가 다르면 코드 배치만으로 ±1% 안팎이 달라질 수 있다.
- **GC 작업량**: 기본 heap에서 `--trace-gc-nvp`로 60~100 사이클 동안 scavenge가 복사·승격한
  바이트를 더한다. 단일 스레드 GC 기준이다.
- **브라우저**: Chromium 141 headless(Playwright), 실제 DOM. 페이지마다 30회 워밍업 뒤 300회
  (생성은 100회) 연산의 평균을 재고, 변형 순서를 라운드마다 뒤집어 16라운드의 중앙값을 낸다.
  layout·paint는 강제하지 않으므로 공식 러너 수치와 직접 비교하지 않는다. 라운드 간 변동은 ±10~20%다.
- 공식 러너([production-run.mjs](./production-run.mjs))로는 재지 않았다. 이 환경에는
  js-framework-benchmark checkout이 없다.

## HMR 회귀 (`1f46202`에서 수정)

e2e를 돌려 보니 `hmr-stateless.spec.ts` 두 개가 base·concurrent 모두에서 실패했다(main은 통과).
새로 만든 컴포넌트의 출력 안에 있는 컴포넌트는 diff 없이 바로 인스턴스가 만들어지는데,
그것을 그릴 때 다시 복사해 **인스턴스가 둘** 생겼다. 먼저 만든 인스턴스는 setup·HMR 등록만
되고 그려지지 않아, HMR 경계가 DOM을 찾지 못하고 전체 새로고침으로 넘어갔다. 이미 그린
노드만 복사하도록 고쳤다. 렌더 fuzz와 matrix는 이제 같은 노드에서 나온 인스턴스가 그려지지
않은 채 남는지도 검사한다.

## 남은 차이와 판단

- **생성 +3.1%(flat 명령어)**: `makeNewWDomTree`가 새 노드마다 이미 그린 노드인지(`nr`)
  확인하는 비용이 대부분이다(검사를 빼면 +1.3%). 이 검사가 hoisted 노드·같은 노드의 여러 위치
  수정의 핵심이다. Chromium의 전체 삭제 + 생성 시간에서는 차이가 보이지 않았다.
- **요소 노드의 children**: main은 교체된 원본의 `children`을 모두 비웠다. 그렇게 하면
  hoisted 상수를 다시 그릴 때, 한 노드를 여러 곳에 그릴 때, 컴포넌트가 받은 children을 다시
  배치할 때 빈 노드가 그려진다(되돌리면 회귀 테스트 3개와 fuzz 묶음 12개가 실패한다). 그래서 컴포넌트 노드만 비운다.
  대신 plain 앱에서 단일 스레드 GC의 scavenge 복사량이 사이클당 약 2.4MB → 5.9MB로 는다.
  flat 앱은 GC 자체가 거의 돌지 않아 차이가 없다. Chromium에서는 요소까지 비운 변형과 차이가
  없었다(plain 선택 7.05 vs 7.09ms, 교환 7.19 vs 7.25ms, 갱신 8.54 vs 8.57ms).
- **크기**: base br 5,082B / 4,800B. 사용자가 크기보다 렌더링 성능을 우선한다고 했으므로 줄이기
  위해 성능을 희생하지 않았다. 한도를 올릴지 줄일지는 결정이 필요하다.

```sh
cd docs/benchmark/edge-fix
node build.mjs main <main checkout>     # 기준 코어
node build.mjs head ../../..            # 이 저장소
./ir.sh main flat select 30 0; ./ir.sh main flat select 30 10   # 명령어 수 (valgrind 필요)
python3 summarize.py <ir.sh 출력 파일> main head

```
