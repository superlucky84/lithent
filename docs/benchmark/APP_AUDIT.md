## 1. 기존 측정은 유효하지만 결론에는 정정이 필요하다

- 4차 CPU 결과의 7개 구현 × 9개 시나리오 × 3개 지표를 원본 러너 JSON과 대조했다.
  중앙값과 표본 수 **189개 항목이 모두 일치**했다. CPU 15회, 선택 25회는 러너 기본값과 같다.
- 무가중 기하평균도 재계산 결과와 일치한다: Lithent 1.7533, Preact 1.7393, React 1.9054.
- 그러나 결과표 코드 `webdriver-ts-results/src/Common.ts:computeGeometricMean`의
  실제 가중치를 같은 중앙값에 적용하면 순위가 달라진다.

| 구현         | 기존 무가중 계산 | 결과표 가중치 적용 |
| ------------ | ---------------: | -----------------: |
| Lithent      |           1.7533 |             1.6384 |
| Preact hooks |           1.7393 |             1.5726 |
| React hooks  |           1.9054 |             1.5904 |

둘 다 이 로컬 측정의 vanillajs 기준이다. 공식 표는 시나리오별 가장 빠른 구현을 분모로 삼는다.
따라서 오른쪽 숫자를 공개 공식 점수로 제시하면 안 된다. 공통 분모 변경은 구현 간 순서를 바꾸지 않는다.
가중 계산에서 Lithent는 Preact보다 약 4.2%, React보다 약 3.0% 느리다.
이 데이터로 "공식 방식에서도 Preact와 동급이고 React보다 앞선다"고 결론 내릴 수는 없다.

공식 근거:
[가중치 계산](https://github.com/krausest/js-framework-benchmark/wiki/Computation-of-the-weighted-geometric-mean),
[구현 규칙](https://github.com/krausest/js-framework-benchmark#contributing-a-new-implementation).

측정의 나머지 한계:

- 부하가 높은 상태에서 구현을 순차 측정했으므로 실행 순서에 따른 오차가 남는다.
  load average만으로 특정 구현에 유리하거나 불리했다고 단정할 수 없다.
- 3차와 4차는 비교 라이브러리 버전이 다르므로 절대 점수의 전후 변화로 회귀를 판단하면 안 된다.
- 메모리 각 1회, 생성·삭제 5회 후 0.90 MB는 회수되는 신호다. 누수 부재의 증명은 아니다.
  더 많은 반복과 GC 이후 잔존 메모리 추세를 확인해야 한다.
- 현재 재현 환경에서 Bootstrap CSS의 `../fonts/`는 없는 `css/bootstrap/dist/fonts/`를 가리킨다.
  실제 폰트는 `css/bootstrap/fonts/`에 있다. 이전 4차 측정 당시의 폰트 응답은 기록이 없어 확인하지 못했다.
  아래 임시 서버에서는 이 경로를 실제 폰트로 연결했다.
- upstream README는 정적 HTML 버튼도 허용한다. "버튼이 정적이므로 화면 전체 렌더가 필수"는
  과한 표현이다. 전체 화면을 Lithent로 만들면 이벤트 연결과 구현 설명이 더 자연스럽다.

## 2. 현재 앱의 cacheUpdate는 의도대로 작동한다

`RowView`의 의존성은 `[props.row, props.selected]`다. `update()`가 변경 행만 새 객체로 바꾸므로
행 데이터 참조를 비교하는 현재 구현과 맞는다. key는 안정적인 행 ID이고 이벤트 핸들러는 mounter에서 만든다.

실제 Chromium 브라우저에 검사 횟수와 updater 실행 횟수만 계측했다.

| 작업          | 캐시 검사 | 새 행 VDOM 생성 |
| ------------- | --------: | --------------: |
| 1,000행 생성  |     1,000 |           1,000 |
| 첫 행 선택    |     1,000 |               1 |
| 선택 이동     |     1,000 |               2 |
| 10행마다 갱신 |     1,000 |             100 |
| 교환          |     1,000 |               0 |
| 1행 삭제      |       999 |               0 |
| 1,000행 추가  |     1,999 |           1,000 |

추가는 앞선 삭제 이후 행 수가 999인 동작 검사다. 공식 추가 측정은 원래 러너대로 1,000 + 1,000행이다.

`cacheUpdate`는 출력 VDOM의 메모이제이션이다. 상태 변경을 묶는 API가 아니다.
캐시가 적중해도 현재 `RowView`는 컴포넌트 props 동기화·업데이트 훅 처리·Fragment 래핑을 거친다.

## 3. 앱만 바꾸는 가장 유망한 후보

행에는 로컬 상태나 생명주기 훅이 없다. 행별 `mount`를 빼고, 행 모델에
`cacheUpdate(() => [row.label, selectedId === row.id], renderRow)`로 만든 렌더 함수를 둔다.
목록은 `rows.map(row => row.view(row))`로 **key가 붙은 tr VDOM**을 직접 반환한다.

- 선택 상태는 테이블 ID 하나로 유지한다. 행별 선택 플래그를 저장하지 않는다.
- 핸들러는 행당 한 번 만든다. 직접 DOM 조작이나 앱의 이벤트 위임은 없다.
- label 변경은 문자열 의존성으로 검사하므로 행 객체를 유지하고 label을 갱신할 수 있다.
- 화면 전체를 Lithent로 만든다. 정적 버튼 영역은 한 번 렌더하고, Table 컴포넌트의 renew로 목록을 갱신한다.
- 행 컴포넌트의 WeakMap 항목·훅 배열·Fragment·props 동기화 비용을 줄인다.

이것은 공개 `h`/`mount`/`cacheUpdate`를 이용하는 앱 후보다. 캐시 렌더 함수를 행 모델에 두는 방식이
등재용 관용적 구현으로 받아들여질지는 upstream 리뷰에서 확인해야 한다.
`cacheUpdate`와 key를 유지하며 직접 DOM을 조작하지 않는다는 점에서 시험할 가치가 높다.

비교한 후보:

| 이름       | 내용                                                    |
| ---------- | ------------------------------------------------------- |
| base       | 현재 앱                                                 |
| full       | 기존 RowView 유지, 전체 화면 Lithent 렌더, Table만 갱신 |
| scalarFull | full + label 의존성 및 label 제자리 갱신                |
| flat       | 행 mount 제거, 기존 정적 화면 유지                      |
| flatFull   | 행 mount 제거 + 전체 화면 Lithent 렌더                  |

5개 후보 모두 생성·선택 이동·부분 갱신·교환·이동한 행의 삭제 핸들러·추가·교체·전체 삭제·10,000행 생성·
생성/삭제 20회 반복을 통과했다. 캐시 적중 수는 현재 앱과 같았다.
원본 공식 `isKeyed.js`로 **base와 flatFull의 HTML 및 keyed 검사도 통과**했다.

## 4. 공식 러너 코드로 비교한 예비 결과

원본 `forkedBenchmarkRunnerPuppeteer.executeBenchmark`를 직접 호출했다.
준비 횟수, 시나리오별 1/2/4배 CPU 배율, GC, 새 탭, 트레이스 및 페인트 계산은 원본 러너대로다.
**각 5회** 중앙값이며 원래 전체 측정의 15/25회보다 적다. 구현 순서는 시나리오마다 번갈았다.
기존 4차 수치와 섞지 않는다. 두 후보는 같은 현재 코어 소스를 같은 Vite 설정으로 빌드했다.
배포 dist와 앱의 기존 프로덕션 빌드를 그대로 실행한 것은 아니다.

| 시나리오      | 현재 앱 총 시간 ms | flatFull 총 시간 ms |  감소 | 현재 / 후보 script ms |

| 1,000행 생성  |             29.079 |              28.427 |  2.2% |         9.953 / 9.198 |
| 1,000행 교체  |             32.941 |              32.729 |  0.6% |       12.374 / 12.376 |
| 10행마다 갱신 |             21.874 |              17.966 | 17.9% |         9.928 / 5.815 |
| 행 선택       |             10.220 |               9.508 |  7.0% |         6.667 / 2.744 |
| 행 교환       |             21.810 |              16.011 | 26.6% |         7.685 / 3.290 |
| 1행 삭제      |             14.168 |              12.445 | 12.2% |         3.433 / 1.566 |
| 10,000행 생성 |            301.985 |             293.180 |  2.9% |       85.516 / 71.122 |
| 1,000행 추가  |             35.116 |              31.914 |  9.1% |        11.677 / 9.037 |

같은 가중치를 적용한 후보/현재 비율은 0.8851이다. 약 11.5% 개선의 신호지만 확정 점수는 아니다.
생성·교체의 2~3% 이하 차이를 5개 표본으로 확정적인 개선이라고 평가하지 않는다.
선택도 총 시간에는 프레임 대기 변동이 있어 script 시간 감소가 더 명확했다.

원본 러너의 `performance.measureUserAgentSpecificMemory()` 메모리 측정도 실행했다.
각 1회 측정이므로 크기 차이의 신호로만 읽는다.

| 상태             | 현재 앱 MB | flatFull MB |
| ---------------- | ---------: | ----------: |
| 로드 직후        |      0.589 |       0.534 |
| 1,000행          |      4.301 |       3.543 |
| 5회 갱신 후      |      5.421 |       4.301 |
| 생성·삭제 5회 후 |      0.899 |       0.927 |
| 10,000행         |     35.064 |      28.244 |

행 보유 시 메모리가 약 18~19% 줄었다. 생성/삭제 후 잔존 메모리는 개선됐다고 말할 수 없다.

일반 진단도 실행했다: Chromium 153, 모든 시나리오 CPU 4배, 준비 6회, 12회 × 순서를 뒤집은 2라운드.
flatFull은 선택·교환·단일 삭제의 JS 갱신 시간에서 반복해서 개선됐다.
scalarFull은 full보다 일관되게 좋아지지 않아 우선하지 않는다.
이 진단의 옛 add 항목은 반복할 때마다 행 수가 증가하므로 공식 추가 시나리오의 근거로 쓰지 않는다.
재현 스크립트에서는 매회 1,000행으로 되돌리도록 수정했다.

## 5. 남은 확인 사항

- 후보를 일반 프로덕션 설정으로 빌드하고, 7개 구현을 같은 고정 버전·같은 Chrome으로 15/25회 다시 잰다.
- 공식 방식 메모리와 시작·크기도 확인한다. 생성/삭제 후 GC 회수를 더 많이 반복해서 확인한다.
- 코어를 추가로 바꾸기 전에 앱의 행 컴포넌트 비용을 줄이는 후보를 우선한다.
  기존 FOLLOWUP_ANALYSIS의 동일 VDOM 빠른 반환과 빈 배열 정리는 그 뒤에 개별 측정한다.
  현재 base는 br 4,754/4,800B로 여유가 46B다. 옛 "+17B가 예산 밖" 판단은 지금에는 적용되지 않는다.

별도로 발견한 cacheUpdate 문제: 의존 배열 길이를 비교하지 않아 `[1] → [1,2]`에서
같은 VDOM을 잘못 재사용한다. 직접 재현했다. 이번 고정 길이 2요소 벤치마크에는 영향이 없다.
또한 helper의 옛 cacheupdate 테스트는 `nextTick().then(...)`을 return/await하지 않아
비동기 검증 보장이 약하다. 해당 수정 시 await하는 계약 테스트를 추가하는 것이 좋다.
