# 행 선택·부분 갱신 비용 분석 — 2026-10-18

공개 결과표의 Lithent **1.25.2**에서 행 선택 **6.9ms**, 부분 갱신 **17.5ms**가
다른 작은 갱신에 특화된 구현보다 느린 이유를 조사했다.
결론은 **변경량이 작아도 Table 전체의 캐시 검사와 keyed 목록 처리를 수행하는 구조**다.
캐시는 실제 DOM 변경을 줄이고 있지만, 변경 없는 행의 검사·매칭 비용까지 제거하지는 않는다.
이번 작업에서는 런타임이나 공식 벤치마크 앱을 수정하지 않았다.

## 조사 대상과 조건

- 공식 앱: [keyed/lithent/src/main.tsx](https://github.com/krausest/js-framework-benchmark/blob/master/frameworks/keyed/lithent/src/main.tsx).
  다운로드한 소스와 SHA-256을 보존했다. 앱의 `package.json`은 `lithent`를 **1.25.2**로 고정한다.
- npm에서 설치한 **lithent 1.25.2**의 배포 번들과 동봉 소스를 사용했다.
  계측 대상 `src/diff.ts`의 해시는 현재 저장소 소스와도 일치했다.
- Node **24.19.0**, Linux Chromium **151.0.7922.173**, Playwright **1.63.0**,
  진단 번들 빌드 도구 Vite **5.4.8**. 공식 앱이 선언한 Vite는 **5.4.21**이다.
- 호출 횟수는 npm 소스에 카운터를 넣은 별도 빌드로 측정했다.
  `MutationObserver`로 실제 DOM 변경을 확인하고, 기존 `tr`가 그대로 유지되는지 검사했다.
- 시간 측정은 **카운터 없는 배포 번들**로 수행했다. CPU 4배, 차수별 구현 순서 교대,
  3차수 × 16회다. JavaScript 완료와 강제 스타일·레이아웃 시간을 따로 기록했다.
- CPU 프로파일은 함수 이름을 읽을 수 있는 **별도 비압축 소스 빌드**다.
  CPU 4배, 샘플링 간격 100µs로 선택 40회·부분 갱신 16회를 수집했다.
- 공유 CSS는 사용했지만 Bootstrap glyph 폰트는 진단 서버에서 제공하지 않았다.
  강제 스타일·레이아웃 시간은 원본에 남기되 공식 결과를 설명하는 수치 근거로 사용하지 않는다.

공식 러너의 실제 클릭부터 최종 paint까지를 재현한 측정은 아니다.
첨부 이미지와 하드웨어·Chrome·빌드 설정도 다르다. 따라서 아래 계측으로
이미지의 6.9ms·17.5ms를 정확히 분해하거나 공식 점수·개선율을 산출하지 않는다.

## 1,000행에서 확인한 작업량

| 작업          | 캐시 검사 | 새 행 VDOM | 행 diff | 전체 diff 호출 | 실제 DOM 변경  |
| ------------- | --------: | ---------: | ------: | -------------: | -------------- |
| 첫 선택       |     1,000 |          1 |   1,000 |          1,012 | class 속성 1개 |
| 선택 이동     |     1,000 |          2 |   1,000 |          1,021 | class 속성 2개 |
| 10행마다 갱신 |     1,000 |        100 |   1,000 |          1,903 | 텍스트 100개   |

`전체 diff 호출`은 `makeNewWDomTree` 호출 수이며, DOM 변경 횟수가 아니다.
세 작업 모두 기존 `tr` 1,000개의 DOM 정체성을 유지했고 자식 삽입·삭제는 없었다.
Table의 컴포넌트 `runUpdate`는 **각 1회**, LIS 함수 호출은 **0회**였다.
현재 공식 앱에는 행별 `mount`가 없으므로 과거 행 컴포넌트 기반 분석의
“1,001개 컴포넌트 갱신”을 이번 원인으로 적용하면 안 된다.

## 비용이 발생하는 경로

### 앱: 선택 하나에도 Table 전체 갱신

행의 선택 핸들러는 `selected`를 바꾼 뒤 `renewTable()`을 호출한다.
Table의 updater는 매번 다음 표현식을 실행한다.

```tsx
<Fragment>{store.state.rows.map(row => row.view(row))}</Fragment>
```

따라서 선택을 옮겨도 모든 행의 `cacheUpdate`가 실행된다. 각 검사는
`[row.label, selected === id]`라는 새 의존 배열을 만든다.
선택 이동에서는 998개, 부분 갱신에서는 900개가 캐시에 적중했다.
캐시가 반환한 기존 VDOM도 이후의 목록 매칭에는 참여한다.

### 코어: 캐시 적중 뒤에도 key 매칭과 목록 순회

[`diffLoopChildren`](../../src/diff.ts)은 이전 1,000행으로 key Map을 만들고,
새 1,000행의 key를 조회·삭제하며 기존 위치를 기록한다. 각 행은
`makeNewWDomTree`를 거치고, 마지막에는 사용하지 않은 이전 행을 필터링한다.

[`makeNewWDomTree`](../../src/diff.ts)는 같은 VDOM 객체여도 유형 판별과 일반화 등을 거친 뒤
`N`으로 판정한다. 하위 트리는 생략하지만 그 입구의 비용은 남는다.
[`updateChildren`](../../src/render.ts)도 목록의 순서·위치를 확인하고 자식과 메타데이터를 순회한다.
이번에는 순서가 그대로여서 LIS와 DOM 이동은 없었지만, 위치 배열 등의 준비는 수행했다.

읽기 가능한 빌드의 CPU 프로파일에서도 Table의 `map`, 기존 key Map을 채우는 콜백,
새 행을 매칭하는 콜백, `makeNewWDomTree`, `updateChildren`이 선택 경로의 주요 표본이었다.
함수별 표본 시간은 원본 JSON에 있으며, 배포 번들의 전체 시간과 직접 합산하지 않는다.

### 부분 갱신: 라벨 하나 때문에 행 전체 VDOM 재생성

변경된 행은 캐시가 무효화되어 `tr`와 셀·링크·아이콘의 VDOM을 다시 만든다.
100행 갱신에서 `h`는 외부 Fragment를 포함해 **801회** 실행됐다.
정적인 셀과 핸들러 props도 비교하면서 전체 diff 호출은 **1,903회**가 됐다.
실제 DOM 결과는 [`updateText`](../../src/render.ts)의 텍스트 쓰기 100회였다.

프로파일에서도 VDOM 생성, 자식 비교·갱신, 텍스트 쓰기와 GC 비용이 추가로 관찰됐다.
GC만을 주원인으로 확정하거나 개별 함수 표본을 정확한 비용 비중으로 해석하지 않는다.

## 결과표에서 선택의 상대 격차가 큰 이유

비교한 공식 VanillaJS 구현은 선택된 DOM 행을 보관해 이전·새 행의 class를 직접 바꾼다.
부분 갱신도 10행마다 라벨의 텍스트 노드에 바로 쓴다.
Lithent는 같은 DOM 결과를 얻기 전에 전체 캐시 검사와 VDOM 목록 처리를 추가로 수행한다.
특히 선택은 필요한 DOM 변경이 2개뿐이어서 이 공통 비용이 상대적으로 크게 드러난다.
CPU 4배 스로틀은 이 JavaScript 비용 차이를 확대한다.

행 수를 1,000에서 10,000으로 늘린 보조 실험에서도 선택의 스크립트 시간이 증가했다.
순서 교대한 세 차수의 중앙값은 Lithent 1,000행 **2.9~5.3ms**, 10,000행 **21.9~29.9ms**였다.
짧은 VanillaJS 선택 시간과 강제 레이아웃 시간에는 편차가 커서 이 실험의 배수를 공식 격차로 쓰지 않는다.
부분 갱신의 공식 전체 시간에는 실제 텍스트 변경 이후의 스타일·레이아웃·paint도 포함된다.

## 개선 방향과 검증 조건

1. **변경 없는 keyed 목록의 처리 비용 줄이기.** 순서·구성원이 그대로인 경우 key 매칭·위치 계획을
   덜 수행하거나, 동일 캐시 VDOM의 반복 처리를 줄이는 경로를 검토한다.
   혼합·중복 key, 노드 재사용, 부모 연결과 생명주기 계약을 보존해야 한다.
2. **갱신 범위를 행·라벨 단위로 줄이기.** 선택은 이전·새 행, 부분 갱신은 바뀐 라벨만 갱신하는
   구성을 비교한다. 행마다 컴포넌트를 추가하면 생성 시간과 메모리 비용이 늘 수 있다.
3. **배열·VDOM 할당 비용 줄이기.** 의존 배열과 변경 행의 전체 VDOM 생성 비용을 별도로 측정한다.

이 항목들은 아직 적용·검증하지 않은 후보다. 9개 공식 시나리오와 생성·메모리·크기를 함께 확인해야 한다.
기존 [동일 VDOM 조기 반환 실험](./PERFORMANCE_CLOSEOUT.md)은 JS 시간이 줄어도 부분 갱신의
공식 전체 시간이 증가해 미채택했다. 이번 진단만으로 그 후보를 그대로 복원할 근거는 없다.

앞서 논의한 props 복사가 캐시된 행마다 반복되는 경로는 이번 앱에 없다.
생성기 의존 버전이나 `componentUpdate` 문서 변경도 이 갱신 경로를 바꾸지 않았다.

예를 들어 Python의 `gzip.decompress`와 `json.loads`로 읽고 각 `content`를 새 작업 디렉터리에 추출할 수 있다.
원본 측정 도구 `build.mjs`·`run.mjs`에는 당시의 절대경로가 있으므로 재실행 전에 다음 경로를 맞춘다.

| 도구의 경로                                             | 재현 환경에서 지정할 대상                     |
| ------------------------------------------------------- | --------------------------------------------- |
| `/tmp/lithent-select-review`                            | 보존 파일을 추출할 새 출력 디렉터리           |
| `build.mjs`의 `npm` 변수                                | `lithent@1.25.2`를 새로 설치한 `node_modules` |

| `/usr/bin/chromium`                                     | 사용할 Chromium 실행 파일                     |

저장소의 의존성을 설치하고 별도 디렉터리에 `lithent@1.25.2`를 설치한 뒤,
위 경로를 조정한 `build.mjs`, `run.mjs` 순서로 실행한다. 로컬 HTTP 포트는 **8794**다.
시간 측정은 다른 벤치마크와 동시에 실행하지 않는다. 공식 전체 시간을 다시 비교하려면
이 진단 도구 대신 원래 `js-framework-benchmark` 러너로 별도 측정해야 한다.
