# 코어 성능 추가 분석 — 2026-10-07

기준: `326a181` + 기존 `src/render.ts` 미커밋 수정 + `cacheUpdate`를 적용한 로컬 벤치마크 앱.
이번 작업은 진단이다. 코어에는 추가 수정을 적용하지 않았다.

## 결론

일반적인 keyed 행 갱신은 이미 Map 매칭과 LIS 최소 이동을 사용한다. 남은 주요 비용은
**변하지 않은 컴포넌트까지 통과하는 갱신 절차와 객체 메타데이터 변경**이다.
전체 삭제에는 실제 DOM 해체와 이벤트·생명주기 정리 비용이 남아 있다.
또한 기존 삭제 수정은 **단일 DOM을 반환하는 행**에는 효과가 있지만,
여러 형제 DOM을 반환하는 컴포넌트에는 O(n²) 순회가 아직 남는다.

소규모 임시 변경으로 선택·부분 갱신의 JS 시간이 줄어드는 것을 확인했다.
따라서 개선 여지는 있다. 다만 후보를 모두 합치면 교체·전체 삭제가 오히려 느려지기도 해서,
일괄 적용하거나 공식 점수가 이미 개선됐다고 판단할 단계는 아니다.

## 1. 기존 비교 결과가 보여 주는 차이

[results.json](./results.json)의 2차 측정에서 가져온 **스크립트 시간**이다.
전체 화면 갱신 시간과 구분해야 코어의 차이가 보인다.

| 시나리오      | Lithent | Preact hooks | 배수 |
| ------------- | ------: | -----------: | ---: |
| 1,000행 생성  |  10.7ms |        7.0ms | 1.53 |
| 1,000행 교체  |  15.7ms |       10.4ms | 1.51 |
| 10행마다 갱신 |  16.0ms |       10.0ms | 1.60 |
| 행 선택       |  11.0ms |        8.1ms | 1.36 |
| 행 교환       |  13.6ms |        8.5ms | 1.60 |
| 행 하나 삭제  |   6.2ms |        4.6ms | 1.35 |
| 10,000행 생성 |  91.5ms |       62.5ms | 1.46 |
| 1,000행 추가  |  14.4ms |        8.6ms | 1.67 |
| 전체 삭제     |  21.6ms |       10.8ms | 2.00 |

페인트 시간은 예를 들어 10,000행 생성에서 218ms 대 219ms, 전체 삭제에서 1.3ms 대 1.4ms다.
주요 격차는 JS 실행과 그 안에서 수행하는 DOM 작업이다.

비교 해석 정정:

- 로컬 `preact-hooks/src/main.jsx`는 `data.map`에서 직접 `tr`를 생성한다. 행 `memo`를 쓰지 않는다.
- 로컬 `react-hooks/src/main.jsx`는 행에 `memo`와 비교 함수를 사용한다.
- Lithent의 `cacheUpdate`는 출력 VDOM을 재사용하지만, 컴포넌트 갱신 입구에서 중단하지는 않는다.
  따라서 React의 행 메모이제이션과 목적은 비슷해도 건너뛰는 처리 범위가 다르다.
- 기존 2.00/1.59 등은 로컬 공식 러너 결과다. 공식 공개 순위가 아니며 React 등은 2차에 다시 재지 않았다.

## 2. 확인한 병목

### 2.1 캐시 적중 후에도 남는 컴포넌트 비용

관련 코드: `src/diff.ts:120`의 `syncResolverProps`, `:144`의 `runUpdate`,
`src/wDom.ts:356`의 `wDomMaker`, `:382`의 `wrapComponentMakerIfNeeded`, `:401`의 `addComponentProps`.

부모 업데이트 때 각 행은 다음 경로를 통과한다.

1. 새 resolver와 props·children 배열 생성.
2. 기존 props의 모든 키 삭제 후 새 값을 복사. 내용이 같아도 실행한다.
3. 자식 배열 동기화, 훅 상태 설정, 업데이트 콜백 확인.
4. `cacheUpdate` 확인. 적중하면 행의 기존 `tr` VDOM을 반환한다.
5. 반환값을 감싸는 새 Fragment, 부모 클로저, 컴포넌트 메타데이터와 redraw 클로저 생성.
6. Fragment diff·갱신 후에야 동일한 `tr`에서 하위 트리 처리를 생략한다.

계측 결과, 1,000행 중 선택을 다른 행으로 옮길 때 `runUpdate`, `syncResolverProps`,
래퍼 생성이 각각 **1,001회** 발생했다. 행 내부의 실제 변경은 두 행인데 래퍼 갱신은 전체에 발생한다.
CPU 프로파일에서도 `syncResolverProps`, `typeUpdate`, `wDomMaker`, `addComponentProps`가 상위에 있었다.

개선 방향: props에서 실제로 사라진 키만 삭제하고, 고정 메타데이터와 redraw 함수를 덜 재생성한다.
더 큰 개선은 명시적으로 캐시된 컴포넌트를 앞단에서 중단하는 방식이다.
단, props 참조 안정성, slots, 로컬 상태의 `renew`, 업데이트 훅 의미를 보존해야 한다.
props가 같다는 이유로 모든 컴포넌트를 자동 생략하는 변경은 기존 동작을 깨뜨릴 수 있다.

### 2.2 VDOM 메타데이터의 반복 `delete`

관련 코드: `src/diff.ts:58`, `src/render.ts:316`, `:436`의 `clearDiffMeta`.

매 갱신마다 `children`, `op`, `oi`, `nr`, `oc` 속성을 삭제하고 다른 단계에서 다시 추가한다.
임시 빌드에서 이 메타데이터 삭제를 `undefined` 대입으로 바꾸면 선택·부분 갱신·단일 삭제가 개선됐다.
`delete newWDom.op` 한 줄만 변경하는 실험에서는 큰 개선이 없었다.

따라서 **메타데이터 처리 전체**를 검토할 근거는 있다. 다만 이번에는 V8의 객체 내부 상태나
deoptimization 로그를 수집하지 않았으므로 dictionary mode가 원인이라고 확정하지는 않는다.
실제로 없어진 사용자 props를 제거하는 `delete`와 내부 메타데이터 정리는 구분해야 한다.

### 2.3 순서가 그대로여도 LIS 계산

관련 코드: `src/diff.ts:248`의 `diffLoopChildren`, `src/render.ts:336`의 `updateChildren`.

매칭된 모든 행에 `oi`가 붙는다. `updateChildren`은 `oi !== undefined`만으로 배치 경로에 진입하여
선택·텍스트 갱신에도 인덱스 배열, LIS 결과, `Set`, 앵커를 계산한다.
계측에서도 행 선택과 부분 갱신마다 LIS를 한 번 계산했다.

교환 자체는 실제 DOM 재삽입 **2회**였다. 전 행을 DOM에서 이동시키는 옛 문제는 현재 원인이 아니다.
증가하는 기존 인덱스만 있는 경우 LIS를 생략할 수 있다. 이번 간단한 생략 실험의 효과는 작고
시나리오별로 엇갈렸다. 주된 병목을 해결하는 변경으로 과대평가하면 안 된다.
현재 LIS는 정렬된 입력에서 이미 O(n)이며, 이 개선은 중복 계산·할당을 줄이는 것이다.

### 2.4 삭제: 단일 행은 개선됨, 여러 루트에서는 O(n²) 잔존

관련 코드: `src/render.ts:97`의 `findChildWithRemoveElement`.

기존 수정은 `items.length > 1`인 후보에서만 부모의 전체 자식을 센다.
단일 `tr`를 반환하는 행은 이 조건을 피한다. 하지만 컴포넌트가 `<Fragment><tr/><tr/></Fragment>`를
반환하면 각 내부 Fragment가 다시 후보가 되므로, 컴포넌트마다 부모 전체를 센다.

| 두 DOM 형제를 반환하는 컴포넌트 수 | 전체 삭제 시 형제 순회 횟수 |
| ---------------------------------: | --------------------------: |
|                                500 |                     250,500 |
|                              1,000 |                   1,001,000 |
|                              2,000 |                   4,002,000 |

반복 횟수가 `n(n+1)`로 증가하는 것을 현재 소스에서 직접 계측했다.
부모 전체를 비울 수 있는지는 상위 삭제 작업에서 한 번 판단하거나,
필요한 개수를 넘으면 탐색을 중단하도록 제한해야 한다.
다중 루트, 리스트 앞뒤 형제, portal, unmount 순서를 포함한 검증이 필요하다.
`lithentConcurrent/src/render.ts`에는 단일 행 개선조차 아직 반영되지 않았다.

단일 행 1,000개 삭제에는 여전히 `remove()` 1,000회와 이벤트 해제 2,000회가 발생한다.
현재 CPU 프로파일에서도 native `remove`의 self time이 약 6.73ms/op로 컸다.
그러나 컴포넌트 루트를 모아 `textContent = ''` 한 번으로 지우는 실험에서는 큰 개선이 없었다.
일괄 삭제 프로파일은 약 7.02ms/op가 해당 함수로 옮겨갔다.
DOM 하위 트리 자체를 해체하는 비용은 단일 API 호출로 바꿔도 남는다.

### 2.5 생성: 다중 순회·할당과 DOM 구성 비용

관련 코드: `src/wDom.ts:48`, `src/diff.ts:199`, `src/render.ts:621`.

`h`의 자식 정규화 → diff 트리 생성 → DOM 생성으로 트리를 여러 번 처리한다.
컴포넌트별 Fragment와 상태·클로저도 생성한다.
10,000행 생성 계측에는 `appendChild` 110,000회가 있었다.
이는 행의 실제 DOM 연결과 Fragment 경유 연결을 모두 포함하며, 모두 제거 가능한 작업이라는 뜻은 아니다.

별도 생성 프로파일에서 `appendChild` 약 27.6ms, `remakeNewWDom` 25.5ms,
`createElement` 16.5ms, GC 13.9ms, `DocumentFragment` 8.4ms가 관찰됐다.
생성에도 최적화 여지가 있지만, 이번 후보들로는 10,000행 생성의 일관된 개선이 없었다.
실제 화면 시간에서는 페인트 비중도 커서 우선순위는 부분 갱신보다 낮다.

## 4. 권장 순서와 검증 범위

1. **삭제의 남은 O(n²) 경로 제거**: 두 DOM 형제를 반환하는 경우도 선형화하고 concurrent 경로를 함께 검토.
2. **내부 메타데이터 처리 개선**: 변경 범위가 작고 실험에서 비교적 분명한 개선 신호가 있었다.
3. **컴포넌트의 고정 갱신 비용 절감**: props 동기화·래퍼·redraw 함수 재생성부터 줄이고,
   더 앞선 캐시 중단은 명시적 API 및 생명주기 의미와 함께 설계.
4. **LIS·key Map의 변경 없는 목록 경로 개선**: 이미 좋은 복잡도를 가진 코드를 미세 조정하는 작업.
5. **생성과 일괄 삭제**: DOM 호출 수만으로 효과를 가정하지 말고 실제 브라우저 결과로 선택.

실험용 후보는 정식 패치가 아니다. 브라우저 검증은 행 개수·내용·선택 상태·keyed DOM 정체성 및
교환 순서에 한정된다. 전체 단위·e2e, props 제거, slots, portal, 생명주기, 사용자 보유 VDOM 참조 등의
회귀 검증과 정식 러너 재측정은 코어 변경을 적용하는 단계에 필요하다.
