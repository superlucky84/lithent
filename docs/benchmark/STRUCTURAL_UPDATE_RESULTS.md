# 선택·부분 갱신의 구조 변경 비용 재검토 — 2026-10-19

> **후속:** 아래에서 제안한 Fragment 일괄 삭제도 별도로 구현·검증했다.
> [BULK_REMOVAL_RESULTS.md](./BULK_REMOVAL_RESULTS.md): 삭제는 줄었지만 선택 전체 시간이
> 세 차수 모두 늘어 코어를 복원했다. 아래 측정과 미채택 판단은 당시 원본으로 유지한다.

**개선 지점은 확인했으나 두 후보 모두 교체 적용하지 않았다.** 현재 VDOM을 재사용하면
선택·부분 갱신의 이득을 유지하면서 교환·한 행 삭제가 빨라졌다. 그러나 전체 삭제와 전체 교체가
두 차수 모두 느려졌다. 실제 upstream 작업트리는 앞선 `targeted-main.tsx` 그대로다.

기존 행별 `renew` 후보의 구조 갱신 비용을 두 가지 방법으로 조사했다. 먼저 행 컴포넌트 없이
변경된 행의 VDOM만 새로 만드는 [평범한 행 후보](./structural-main.tsx)를 비교했다.
구조 갱신은 빨라졌지만 선택 속도를 잃어, [현재 행 VDOM 재사용 후보](./retained-row-main.tsx)도
검증했다. 이전 실험의 원본과 [행별 renew 소스](./targeted-main.tsx)는 보존한다.

## 확인한 개선 지점

1. **부모 구조 갱신의 행별 컴포넌트 처리.** 기존 후보의 Table은 구조를 바꿀 때마다
   모든 행에 `h(RowView, row.viewProps)`를 호출한다. props 재사용과 내부 `cacheUpdate`만으로는
   코어의 `runUpdate`, 새 컴포넌트 wrapper, 컴포넌트 자식 diff를 생략할 수 없다.
   따라서 두 행만 교환해도 1,000개 행 컴포넌트가 부모 갱신을 거친다.
2. **컴포넌트 수명과 DOM 이동 비용.** 행마다 컴포넌트 상태와 Fragment가 추가된다.
   삭제 시 컴포넌트 정리, 교환 시 Fragment에서 실제 DOM을 찾는 경로가 생긴다.
   평범한 keyed `tr`와 같은 비용이라고 볼 수 없다. 특히 현재 전체 삭제의 일괄 제거 경로는
   직계 자식이 실제 Element/Text인 경우만 받으므로, 행 컴포넌트의 Fragment 목록은 이 경로에서
   제외된다. Fragment 아래의 실제 노드를 안전하게 일괄 제거하는 것은 별도 코어 개선 후보다.
3. **캐시의 검사 범위와 정적 셀 재사용.** 원래 앱은 선택 하나에도 모든 행에서 의존 배열을
   만들고 검사한다. 추가 후보는 store에서 변경 행만 식별해 그 행의 `view`를 교체한다.
   id·삭제 버튼·빈 셀은 재사용하고, 라벨 셀은 문자열이 바뀔 때만 만든다.

평범한 행 후보의 Table은 `rows.map(row => row.view)`를 렌더한다. 선택 이동은 두 행의 VDOM,
부분 갱신은 변경된 100행의 라벨 셀과 `tr`만 새로 만든다. DOM 쓰기는 여전히 Lithent의
공개 `h`, `mount`, `render`가 처리한다. 수동 DOM 조작이나 비공개 VDOM 필드 변경은 없다.

전체 목록 매칭은 남는다. 그러므로 행별 `renew`의 선택 시간을 그대로 유지하는 방법은 아니다.
선택 비용까지 더 줄이려면 keyed 목록의
순서가 같은 경우의 매칭 비용, 컴포넌트 출력 캐시 적중 시 wrapper 처리 등을 코어에서 따로
검토해야 한다. props 객체가 같다는 이유만으로 갱신을 생략하면 mutable props·외부 상태·생명주기
계약을 깨뜨릴 수 있어 코어에 그런 생략을 넣지 않았다.

## 현재 행 VDOM 재사용

행 컴포넌트가 마운트될 때 공개 `getComponentKey`, `getComponentSubInfo(key, 'vd')`로 코어가
관리하는 현재 VDOM 참조를 얻는다. 부모 Table은 이미 있는 행에서는 이 참조의 `value`를 읽고,
새 행에만 `h(RowView, ...)`를 호출한다. 선택과 라벨 변경은 계속 해당 행의 `renew`로 처리한다.

처음 만든 `<RowView />` 객체를 그대로 캐시하면 자기 갱신 뒤 폐기된 wrapper를 재사용하는 문제가
생긴다. 이 후보는 코어가 자기 갱신 때 교체하는 **현재** 노드를 읽는다. 반환된 참조와 VDOM의
메타데이터를 직접 수정하지 않는다. 컴포넌트 객체 재사용이므로 행의 DOM 정체성도 검증해야 한다.

이 앱에서 행 props는 고정이고 변경되는 label·selected는 store가 명시적으로 해당 행에 `renew`를
예약한다. 이 조건에서 부모 구조 갱신은 행의 updater를 다시 실행할 필요가 없다. 부모 props나
다른 외부 상태에 따라 출력이 달라지는 임의의 컴포넌트에 일반화할 수는 없다. 또한 `vd`라는
하위 메타데이터를 읽는 코드이므로 공개 export만 사용한다는 점과 별개로 고수준 JSX보다 코어와의
결합이 크다. 새로운 코어 API나 자동 memo 규칙을 추가한 것은 아니다.

부모에 의한 행 updater 호출이 사라지므로 행 전체의 `cacheUpdate`도 제거했다. id·삭제·빈 셀은
계속 재사용하며 라벨 셀은 마지막 문자열을 비교해 재사용한다. 의존 배열과 캐시 클로저 할당을 줄인다.

## 측정과 검증

원래 upstream 앱, 앞선 행별 renew 후보, 추가 후보를 같은 `lithent@1.25.2`와 upstream Vite
5.4.21 설정으로 빌드한다. 실제 `~/project/js-framework-benchmark-upstream`의 원본
`executeBenchmark`를 사용하며, 항목별 실행 순서를 회전한다. CPU 항목의 `total`은
클릭부터 화면 표시까지 걸린 시간이고 CPU 점유율이 아니다.

Apple M4 Pro 12코어·24GB, Chrome 155.0.8059.82, Node 20.3.0에서 측정했다.
첫 평범한 행 후보는 공식 CPU 435개 표본, 현재 VDOM 재사용 후보는 별도의 435개 표본이다.
선택은 구현당 25회, 나머지는 15회다. 전체 삭제·교체를 반대 순서로 각 15회씩 추가 측정해
최종 후보에는 총 495개 공식 CPU 표본이 있다. 두 후보의 수치를 서로 합쳐 개선율을 만들지 않는다.
메인 차수는 02:26–02:38 UTC, 추가 차수는 06:09–06:10 UTC에 실행됐다. 추가 차수는 별도
trace 디렉터리를 사용했으며 메인 표본·trace를 덮어쓰지 않았다. 전용 격리 머신이 아니므로
차수 사이 부하와 프레임 타이밍 차이는 남는다.

현재 VDOM 재사용 후보의 메인 차수 중앙값(ms)이다.

평범한 행 후보와 달리 두 항목의 이득을 유지했다. 새 React·Preact 비교를 수행한 것은 아니므로
이 수치로 다른 프레임워크의 순위를 새로 정하지 않는다.

로컬 결과표 가중치로 계산한 재사용/앞선 후보의 9개 항목 비율은 전체 **0.9654**, JS **0.8254**다.
원래 앱 대비는 전체 **0.9786**, JS **0.9056**다. 평균은 개선됐지만 개별 악화가 남는다.
선택만 추가 측정한 이전 보고서의 전체 값과 이 가중치를 섞지 않는다.

## 교체 적용하지 않은 이유

전체 삭제·교체의 악화가 반대 순서에서도 반복됐다. 아래는 차수별 앞선 후보 → 재사용 후보다.

| 항목 | 메인 전체 ms | 반대 순서 전체 ms | 두 차수 합친 전체 ms (각 30회) |
| --- | ---: | ---: | ---: |
| 전체 삭제 | 15.561 → 16.371 | 15.535 → 17.491 | **15.548 → 17.142 (+10.2%)** |
| 1,000행 교체 | 29.895 → 31.293 | 30.531 → 31.512 | **30.112 → 31.366 (+4.2%)** |

이 두 항목의 합친 JS 중앙값도 각각 **13.142 → 14.404ms**, **11.168 → 12.331ms**로 늘었다.
전체 삭제의 메인 trace에서 click `EventDispatch` 내부의 `MajorGC`/`MinorGC`는 두 후보 모두
관찰되지 않았다. 참조 유지에 따른 GC가 이 차이의 원인이라고 단정할 근거는 없다. 클릭 뒤
microtask나 전체 실행의 GC가 없다는 뜻도 아니다.

평범한 행 후보는 교환 **25.135 → 17.778ms**, 한 행 삭제 **14.790 → 11.974ms**,
추가 **34.304 → 31.165ms**로 회복했지만 선택이 **4.670 → 7.286ms**로 느려졌다.
이 후보도 선택 성능을 보존하는 대안으로 채택하지 않았다.

다음 코어 개선의 우선순위는 다음과 같다. 아직 구현·성능 검증한 결과로 해석하지 않는다.

1. **Fragment 아래의 행을 안전하게 일괄 삭제.** 컴포넌트 수명 정리는 유지하면서 DOM 제거는
   한 번으로 처리하는 경로를 검토한다. portal, 부분 목록 삭제, 외부 형제, HTML root를 보존해야 한다.
2. **변경 없는 행 컴포넌트의 부모 재실행 생략.** 이번 앱 실험에서 효과가 확인된 지점이다.
   일반 API로 옮기려면 명시적 캐시 조건과 자식 renew, props·children 변경, updateCallback 계약을
   함께 설계해야 한다. 단순 props 참조 동일성 비교만으로 건너뛰면 안 된다.
3. **행별 컴포넌트 생성 비용.** 재사용 후보도 원래 앱보다 10,000행 생성의 JS가 약 18% 크다.
   컴포넌트 wrapper·상태 할당 비용은 부모 재실행 생략만으로 없어지지 않는다.

## 메모리와 검증

원본 `measureUserAgentSpecificMemory()`를 항목·구현당 3회 측정했다. 1,000행 보유 시
**원래 앱 3.506MB / 앞선 후보 4.409MB / 재사용 후보 4.145MB**다. 재사용 후보는 앞선 후보보다
약 6.0% 적지만 원래 앱보다 약 18.2% 크다. 생성·삭제 5회 뒤에는 각각 **0.890 / 0.880 / 0.926MB**다.
JS heap만의 값이 아니며, 이 검사도 모든 메모리 비용의 개선을 뜻하지 않는다.

별도로 새 컨텍스트에서 3차수씩 생성·삭제를 100회 반복했다. 모든 구현이 GC 뒤 DOM 노드
**63개**, 리스너 **32개**로 돌아왔다. 재사용 후보의 부분 갱신 0회·100회 후 JS heap 중앙값은
**4.303 → 4.545MiB**였고, 이후 삭제 시 약 **2.150MiB**, DOM/리스너는 다시 **63 / 32**였다.
라벨 문자열이 늘어나는 조건이다. 이 경로에서 큰 선형 누적은 보이지 않았지만 보편적인 누수
부재를 증명하지는 않는다. 전체 삭제 저하를 GC나 누수 탓으로 단정하지 않는다.

공유 CSS를 제외한 HTML+JS gzip 합계는 원래 앱 **6,370B**, 앞선 후보 **6,476B**,
재사용 후보 **6,452B**다. 코어는 변경하지 않았으며 새 패키지 크기나 버전 변경은 없다.

두 후보는 strict TypeScript, ESLint와 브라우저 동작 검사를 통과했다. 원본 `isKeyed`,
9개 동작, 실제 glyph 폰트 로딩도 세 앱 모두 통과했다. DOM 검사는 선택 이동의 class 2개,
부분 갱신의 텍스트 100개만 바뀌고 행 정체성이 유지되는지 확인했다. 교환과 부분 갱신을
한 task 안에서 양쪽 순서로 예약하는 경우, 선택 뒤 추가·교체·삭제, 20회 갱신/삭제/재생성도
검사했다.

## 원본과 재현

[structural-update-results.json](./structural-update-results.json)에 두 후보의 공식 표본과
최종 후보의 메모리·반복 갱신 결과를 보존한다.
[structural-update-evidence.json.gz](./structural-update-evidence.json.gz)는 소스·프로덕션 번들,
빌드 manifest, 원본 러너와 측정 도구를 보존한다. 기존 `targeted-update-*` 원본은 덮어쓰지 않는다.
trace 파일은 JSON의 `traceDirectories`에 별도로 남으며 압축 증거 파일에는 포함하지 않는다.

현재 upstream 작업트리의 행별 renew 후보와 현재 VDOM 재사용 후보의 비교는 다음처럼 재현한다.
새로운 출력 경로를 쓰고 다른 성능 측정과 동시에 실행하지 않는다. 포트·Chrome 실행과 upstream
Vite 설정의 임시 파일 생성이 가능한 환경이 필요하다.

```sh
export LITHENT_BENCHMARK_ROOT="$HOME/project/js-framework-benchmark-upstream"
export LITHENT_PRODUCTION_OUT=/tmp/lithent-retained-rerun
export LITHENT_CANDIDATE_SOURCE=docs/benchmark/retained-row-main.tsx
node docs/benchmark/targeted-update.mjs prepare
node docs/benchmark/targeted-update.mjs contracts
node docs/benchmark/targeted-update.mjs verify lithent-before,lithent
node docs/benchmark/targeted-update.mjs cpu lithent-before,lithent
node docs/benchmark/targeted-update.mjs mem lithent-before,lithent 22,25
node docs/benchmark/targeted-update.mjs retention lithent-before,lithent
```

원래 컴포넌트 없는 앱을 기준으로 삼으려면 압축본의 `sources/lithent-before/src/main.tsx`를
추출해 `LITHENT_BASELINE_SOURCE`로 지정한다. 여기서 새 두 앱 비교만 실행했다면 3개 앱의
이번 실험 출력을 검증하는 요약 도구에 섞지 않는다. `structural-update-summarize.mjs`는
이번 측정 전체의 표본 수, 빌드 해시와 완료 여부를 검사하고 원본을 묶는 도구다.
