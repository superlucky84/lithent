# 컴포넌트 비용과 `h` 경량화 실험 — 2026-10-28

행마다 컴포넌트를 두는 보통의 lithent 코드가 공식 앱보다 얼마나 느린지 재고, 그 격차와
요소 생성(`h`) 비용을 코어에서 줄일 수 있는지 시험했다. **모든 후보를 채택하지 않았다.**
가중 전체 시간 변화는 모두 세션 간 흔들림(약 ±2%) 안이었다. 크기 한도 안에 드는 후보는
이득이 없었고, 이득이 가장 커 보인 후보는 한도를 넘었다. runtime, concurrent, guard 4,824B,
실제 4,819B는 그대로다.

남은 격차는 할당 몇 개가 아니라 업데이트 모델에서 나온다. 상태가 클로저의 평범한 변수라서,
코어는 업데이터를 다시 실행하고 새 VDOM을 비교해야만 바뀐 곳을 안다. 이 모델 안에서 남은
미세 최적화로는 측정 가능한 전체 개선을 확인하지 못했다.

## 측정 조건

- js-framework-benchmark 형제 checkout의 `lithent-1.25.3` 브랜치(PR #2136)와 그
  `keyed/lithent` 앱(A)을 썼다. 앱 소스와 Vite 5.4.21 설정은 그대로 두고
  `node_modules/lithent/dist`만 후보 빌드로 바꿨다. 후보는 모두 main `a0f2552` 기준이다.
- 공식 러너(Playwright 1.61.1), Chrome 156.0.8078.48, Node 24.22.1, Apple M4 Pro/24GB,
  비격리 머신이다. CPU 01~09는 동작마다 표본 15개, 선택은 25개다. 표의 값은 중앙값이고,
  가중 값은 공식 CPU 가중치의 가중 기하평균이다.
- 러너는 프레임워크를 디렉터리 이름순으로 실행한다. 순서를 뒤집으려고 같은 빌드를
  A 뒤에 실행되는 이름(`lithent-x*`, `lithent-z*`)과 앞에 실행되는 이름(`lit-*`)으로
  복사했다. 1~3절은 한 세션, 4절은 양순서 세션이다.
- 크기는 `pnpm size`의 base UMD Brotli다.
- 같은 A 빌드끼리도 세션마다 가중 전체 시간이 약 ±2% 흔들렸다. 그래서 한 세션 결과와
  2% 미만의 차이는 방향만 참고한다.

## 1. 행 컴포넌트 구조의 비용 (A/B/C)

A는 행을 컴포넌트로 만들지 않고 행 데이터에 `cacheUpdate` 뷰를 붙인다(사이트의 #1261
NOTE 대상). B는 행을 `mount` 컴포넌트로 만들고, C는 B의 업데이터 안에서 `cacheUpdate`를
쓴다. C가 보통 lithent 코드에 가깝다. 한 세션, vanillajs와 함께 측정했다.

| 동작                         |            A |      B 행 컴포넌트 | C 행 컴포넌트 + 캐시 |
| ---------------------------- | -----------: | -----------------: | -------------------: |
| 10행마다 갱신                |   16.6 (4.3) |        30.6 (17.5) |           21.7 (8.8) |
| 행 선택                      |    7.2 (3.3) |        25.1 (20.3) |           10.9 (6.8) |
| 행 교환                      |   16.4 (3.2) |        32.4 (17.1) |           22.7 (8.3) |
| 1행 삭제                     |   12.0 (1.2) |         19.9 (8.1) |           14.7 (3.1) |
| 10,000행 생성                | 271.7 (54.1) |       287.3 (65.7) |         294.3 (67.6) |
| 전체 삭제                    |   12.0 (9.2) |        13.0 (10.8) |          14.5 (11.5) |
| **가중 (vanillajs = 1.000)** |    **1.230** | **1.626 (+32.1%)** |   **1.431 (+16.3%)** |
| 1,000행 메모리               |       3.59MB |             4.16MB |               4.27MB |

괄호는 JS 시간(ms), 가중 괄호는 A 대비다. 행 컴포넌트를 두면 갱신 계열 JS가 A의 2~7배가
된다. 캐시(C)가 그 대부분을 줄이지만 생성과 삭제 비용은 남는다.

## 2. 컴포넌트 래퍼 재사용 (C 기준)

업데이터가 이미 그려 둔 바로 그 노드를 다시 돌려주면(캐시 적중), 새 Fragment 래퍼를 만들지
않고 이전 래퍼를 돌려줘서 컴포넌트 전체 diff를 건너뛴다. update 콜백이 있거나 빈 출력이면
건너뛰지 않는다. 한 세션 결과다.

| 항목                   |          C | C + 재사용 |      변화 |
| ---------------------- | ---------: | ---------: | --------: |
| 10행마다 갱신 JS       |        8.5 |        6.8 |      −20% |
| 행 선택 JS             |        6.7 |        5.5 |      −18% |
| 행 교환 JS             |        8.1 |        6.0 |      −26% |
| 1행 삭제 JS            |        3.1 |        2.5 |      −19% |
| 전체 삭제 JS           |       10.9 |       11.8 |       +8% |
| **가중 전체 (A 대비)** | **+16.2%** | **+14.3%** | **−1.6%** |

갱신 계열 JS 감소는 네 동작 모두 같은 방향이지만, 가중 전체 −1.6%는 세션 흔들림 안이다.
캐시를 쓰지 않는 B는 +0.6%로 영향이 없었고 메모리도 같았다. 크기는 +57B(4,876B)로 guard를
52B 넘는다.

갱신·선택·교환·1행 삭제를 A 수준까지 완벽히 줄여도 A 대비 +6.2%가 남는다(`whatif.py`).
나머지는 행마다 컴포넌트를 만들고 지우는 비용이다. 이전
[C3 실험](./PARENT_MEMO_CACHE_RESULTS.md)은 업데이터 실행 자체를 건너뛰었지만 전체가 더
느렸다.

## 3. 가벼운 컴포넌트 (A와 C)

컴포넌트마다 만드는 것을 줄였다.

- hook 큐 6개(`upR`, `upD`, `upCB`, `mts`, `umts`, `wdCB`)는 처음 push할 때까지 얼린 빈
  배열 하나를 공유한다.
- `h`는 자식이 없으면 부모 포인터와 `map` 없이 바로 노드를 만든다(4절 V1).
- 컴포넌트 resolver의 클로저를 `this`를 쓰는 메서드로 바꿨다.

한 세션 결과, C 대비 가중 전체 −0.7%, JS −3.3%였다. 1,000행 메모리는 4.29→4.19MB였다.
같은 코어를 A 앱에 적용하면 전체 −3.5%, JS −6.7%였다. 크기는 4,899B(+80B)다. 할당 수는 컴포넌트의 주된
비용이 아니었다. A 쪽 신호가 hook 큐가 아닌 `h` 변경에서 오는지 확인하려고 4절로 나눴다.

## 4. `h` 후보 (A 기준, 양순서)

지금의 `h`는 호출마다 부모 포인터 객체 `{ value }`를 만들고, `remakeChildren`이 자식들이
공유하는 getter 클로저와 `map` 결과 배열을 만든다. 행 하나에서 `h`는 8번 불리고, 그중
2번(`span`, 마지막 `td`)은 자식이 없다.

| 후보   | 내용                                  |   크기 | 세션 |             가중 전체 (세션별) | 가중 JS |
| ------ | ------------------------------------- | -----: | ---: | -----------------------------: | ------: |
| 후보 2 | V1 + resolver 메서드                  | 4,850B |    2 |             −1.5% (−1.6, −2.3) |   −5.2% |
| V1     | 자식이 없으면 바로 반환               | 4,828B |    4 | −0.6% (−0.4, −1.4, +1.9, −0.6) |   −3.3% |
| V2     | 같은 조건을 `makeNode` 인자에 넣음    | 4,822B |    2 |             −0.4% (−0.6, +0.4) |   −2.3% |
| V3     | V1 + 부모를 함수 스코프 클로저 변수로 | 4,804B |    2 |             +1.2% (+3.5, −1.3) |   +0.4% |
| V4     | V3의 변수를 `if` 블록 안으로          | 4,803B |    2 |             +0.6% (+1.8, −0.4) |   −1.0% |

V1은 같은 빌드(`59b6d8f9`)를 v12와 v4 두 쌍에서 쟀다. 4세션 pooled JS는 1,000행 생성 −10.4%,
추가 −6.8%, 1행 삭제 −8.3%였지만 교체는 두 쌍 모두 +8.3%였다. 전체 시간은 세션별 방향이
갈려 −0.6%다. 후보 2는 다른 시점의 세션이라 V1과 직접 비교하지 않는다. resolver 메서드가
더 낫다는 근거로 쓰지 않는다.

같은 세션에서 직접 비교한 결과는 다음과 같다.

- V2는 V1 대비 전체 +1.0%, JS +1.6%였고, 선택 JS가 3.2→4.0ms(+25%)였다.
- V3는 A 대비 교체 JS +10.0%, 10,000행 생성 JS +5.5%, 전체 삭제 JS +7.0%였다.
- V4는 V1 대비 전체 +0.6%, JS +1.8%였고, 전체 삭제 JS가 8.8→9.8ms(+10.8%, 두 순서 모두
  증가)였다. 압축 후에도 블록은 lithent UMD·ESM과 앱 번들 모두에 남아 있었다.

V3과 V4처럼 부모를 클로저 변수로 잡는 형태는 포인터 객체보다 느렸다. V3은 V8이 `h` 진입마다
함수 컨텍스트를 만들기 때문으로 추정한다. 자식 없는 호출도 마찬가지다. V4의 원인은 확인하지
않았다.

### 10,000행 생성 확인

후보 2의 첫 세션에서 10,000행 전체 시간이 +3.0%로 나와, `h` 변경(V1)만 CPU 프로파일로 따로
확인했다. 공식 러너와 같은 플래그와 측정 직전 강제 major GC, 프로덕션 앱 번들, 표본 24개, 교대
순서로 쟀다.

| 시나리오      |            JS base → V1 |    GC base → V1 |
| ------------- | ----------------------: | --------------: |
| 1,000행 생성  |  7.53 → 6.76ms (−10.1%) |   1.88 → 1.75ms |
| 10,000행 생성 | 82.91 → 78.65ms (−5.1%) | 16.78 → 15.65ms |

강제 GC 없이 한 이전 4회도 V1의 JS가 모두 낮았다(1k −1.4~−5.2%, 10k −0.7~−2.8%).
공식 10,000행 전체 시간은 V1 4세션 pooled −0.1%로, 전체 시간 회귀로 보지 않는다. 다만 공식
러너가 집계한 10,000행 JS는 V1 4세션 pooled +1.8%로 프로파일과 방향이 다르다. 두 집계의
범위 차이로 추정하지만 원인은 확인하지 않았다.

### 크기

main은 4,819B로 guard까지 5B 남는다. V1은 +9B로 4B를 넘는다. 자주 실행되지 않는 코드에서
4B를 찾았지만 안전한 후보가 없었다. 오류 문자열은 하나뿐이다. 반복되는 children 개수 비교를
predicator 함수로 묶으면 압축 전은 96B 줄지만 Brotli는 1B만 준다. DC-18의 24B 허용은 일반
예산이 아니므로, 전체 −0.6%를 근거로 guard를 올리지 않는다.

## 결정

- 래퍼 재사용, 가벼운 컴포넌트, 후보 2, V1~V4 모두 미채택이다. 기본 runtime, concurrent,
  guard, 앱은 바꾸지 않는다.
- PR #2136은 A 앱을 유지한다. C로 바꾸면 사이트 점수는 react-hooks·preact-hooks 수준으로
  추정된다(`site_rank.py`).
- concurrent 런타임에도 같은 `h`가 따로 있지만, base 이득이 확인되지 않아 이식하지 않았다.

## 남은 단서 (미착수)

2026-10-29 후속: [생성 시 부모 연결 제거의 반례](./RENDER_GAP_DIAGNOSIS.md#5-새로-확인한-부모-getter-제거의-반례)를 재현했다. render 전과 부모 mountReady에서 자식의 부모를 읽을 수 있으므로 무조건 제거는 보류한다. 아래는 당시 미착수 가설이다.

`h`가 자식에게 붙이는 부모 getter는 마운트(`src/render.ts`의 `wDomChildrenToDom`)와 diff
(`src/diff.ts`의 자식 생성 경로)에서 `makeParentGetter`로 모두 덮어써진다. 마운트나 diff
전에 이 getter를 읽는 경로가 없다면, `h`는 포인터·getter·`map`을 만들지 않아도 된다. 아직
그런 경로가 없는지 확인하지 않았다. 기존 `vite.config.js` 주석처럼 이전 diff 트리와 부모
getter를 격리하는 범위도 함께 검토해야 한다.
