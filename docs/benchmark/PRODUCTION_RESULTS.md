# 벤치마크 앱 개선 적용 및 프로덕션 재측정 — 2026-10-08

행별 `mount`를 제거하고 행마다 `cacheUpdate`로 keyed `tr`를 캐시하는 앱을 실제 벤치마크
checkout에 적용했다. 공식 러너의 CPU 측정 1,160개에서 가중 지표가 **1.609 → 1.388**로
약 **13.8% 감소**했다. 같은 측정의 Preact hooks는 1.529, React hooks는 1.565다.
이 로컬 CPU 측정에서는 개선한 Lithent가 Preact보다 약 9.2%, React보다 약 11.4% 앞선다.
추가 메모리 회수 수정까지 적용한 최종 코어는 별도 추가 CPU 비교에서 Preact hooks 대비
가중 비율 **0.9111**(약 8.9% 빠름)을 기록했다. 반복 갱신 시 이전 VDOM이 쌓이던 문제도 해결했다.

이는 최신 로컬 dist를 사용하는 결과다. 공개 공식 결과표나 npm 배포본의 결과는 아니다.
npm 릴리스와 등재 PR은 하지 않았다. 이후 사용자의 요청으로 변경을 커밋했으며,
커밋·푸시 상태와 다음 작업은 [HANDOFF.md](./HANDOFF.md)에 정리한다.

## 적용한 변경

- [벤치마크 앱](../../../js-framework-benchmark/frameworks/keyed/lithent/src/main.tsx):
  행별 컴포넌트의 props 동기화·훅 처리·Fragment 비용을 제거했다.
  캐시는 `[row.label, selectedId === row.id]`를 검사하고 행 ID를 key로 유지한다.
  핸들러는 행당 한 번 만든다. 선택 상태는 테이블의 ID 하나다.
- 화면 전체를 Lithent로 렌더한다. 버튼 영역은 한 번 렌더하고 Table만 `renew`한다.
  직접 DOM 조작·앱의 이벤트 위임·측정용 지연 렌더는 사용하지 않는다.
- [cacheUpdate](../../helper/src/hook/cacheUpdate.ts): 의존 배열 길이도 비교한다.
  `[1] → [1,2]` 및 끝의 `undefined` 추가·제거를 잘못 캐시하는 오류를 고쳤다.
  고정 길이 2요소를 쓰던 기존 벤치마크 캐시는 정상적으로 작동하고 있었다.
- [기존 helper 테스트](../../helper/src/tests/cacheupdate.tsx)는 `nextTick()`을 await한다.
  [새 계약 테스트](../../helper/src/tests/cacheupdate-contract.tsx)는 길이 변경과 실제 DOM 반영을 검사한다.
- 공유 Bootstrap CSS가 요청하는 `css/bootstrap/dist/fonts/`를 원본 폰트로 복원했다.
  생성된 폰트 파일은 git 무시 대상이다. 8개 앱 모두 실제 폰트 로딩을 확인했다.

아래의 **1차 앱 비교**는 코어의 렌더·diff를 바꾸지 않고 같은 코어·helper 빌드로 측정했다.
그 뒤 반복 갱신 진단에서 이전 VDOM 보유 문제를 발견해 base/concurrent의 부모 getter 생성도
수정했다. 최종 코어의 추가 검증은 뒤의 "부모 getter 회수 수정"에 구분한다.

## 부모 getter 회수 수정

5회 생성·삭제만으로는 발견하지 못한 문제가 추가 진단에서 재현됐다.
1,000행을 유지하며 100회 부분 갱신하면 GC 후에도 JS heap이 **3.886 → 17.769MB**로 늘었다.
생성·삭제만 반복할 때도 DOM 노드가 매회 2개씩 남았다(63 → 263).
리스너 수는 삭제 후 32개로 돌아왔으므로 리스너 누수와는 별개의 이전 VDOM 보유 문제다.

부모 getter와 이전 자식 배열을 사용하는 map 콜백을 같은 diff 함수 스코프에서 만들던 경로를
격리했다. [makeParentGetter](../../src/utils/index.ts)는 부모 하나만 받는 별도 함수다.
base의 세 생성 지점과 concurrent의 `planChildren`에서 이 함수를 사용한다.
행별 캐시나 DOM 처리 결과를 바꾸는 수정은 아니다.

같은 개선 앱과 **실제 프로덕션 dist**로 비교한 GC 후 JS heap MB다.
독립된 새 컨텍스트 3라운드의 중앙값이며 공식 UASM 메모리 값과 측정 방식이 다르다.

| 부분 갱신 횟수 | 코어 수정 전 | 최종 코어 | Preact hooks |
| -------------- | -----------: | --------: | -----------: |
| 0              |        3.886 |     3.781 |        3.524 |
| 1              |        4.021 |     3.783 |        3.519 |
| 5              |        4.593 |     3.818 |        3.523 |
| 25             |        7.399 |     3.882 |        3.568 |
| 100            |       17.769 |     4.026 |        3.715 |

갱신할 때마다 라벨에 ` !!!`가 추가되므로 데이터 크기도 정상적으로 증가한다.
최종 코어는 이전처럼 회당 약 0.14MB의 VDOM이 쌓이지 않는다.
생성·삭제 100회 후 DOM 노드는 **63개 그대로**, 리스너는 **32개 그대로**다.
JS heap은 5/25/100회 후 2.082/2.103/2.116MB로 큰 선형 증가가 없다.
이는 이 경로의 회수 오류가 해결됐다는 근거이며 모든 가능한 누수의 부재를 증명하지는 않는다.

[브라우저 회귀 테스트](../../e2e/parent-retention.spec.ts)는 WeakRef로 실제 이전 VDOM의 회수를 검사한다.
수정 전 base/concurrent 모두 50회 갱신한 span과 Fragment **51개가 전부 생존**해 실패했다.
수정 후에는 **현재 1개씩만 생존**하고 이전 50개는 GC됐다. 전체 브라우저 테스트 **52개**,
`pnpm test:dual`, 변경 파일 ESLint가 통과했다.

base는 **br 4,757 / 4,800B**(이 수정 +3B), concurrent는 **6,254 / 9,000B**로 크기 검사도 통과했다.
앞의 1차 CPU 표는 부모 getter 수정 전 수치다. 최종 코어의 CPU 비교는 별도로 기록한다.

앞의 1차 메모리 표와는 측정 차수가 다르므로 작은 차이를 개선율로 해석하지 않는다.

## 1차 앱 비교: 크기

프로덕션 HTML과 JS 파일을 각각 압축한 크기를 더했다. 공유 CSS는 제외한다.
이 값은 파일 크기 계산이며 공식 러너의 HTTP 전송 크기 항목은 아니다.

| 파일       | 변경 전 raw / gzip / br B | 변경 후 raw / gzip / br B |
| ---------- | ------------------------: | ------------------------: |
| index.html |         1,925 / 505 / 362 |           292 / 207 / 128 |
| main.js    |    13,958 / 5,757 / 5,302 |    14,483 / 5,967 / 5,495 |
| 합계       |    15,883 / 6,262 / 5,664 |    14,775 / 6,174 / 5,623 |

JS는 gzip 210B 늘었지만 합계는 88B 줄었다. `pnpm size`의 core base는
**br 4,754 / 4,800B**, concurrent는 6,235 / 9,000B, element는 998 / 1,000B로 통과했다.
부모 getter 수정 뒤의 최종 크기는 바로 앞 절의 값이다.
앱 JS의 크기에는 코어·helper·앱 코드가 함께 들어간다.

최종 코어의 앱은 main.js raw/gzip/br **14,494/5,971/5,490B**, HTML은 **292/207/128B**다.
합계는 **14,786/6,178/5,618B**다. 코어 회수 수정으로 앱 gzip이 4B 늘었지만,
기존 정적 화면 앱(1차 변경 전)의 합계 6,262B보다는 84B 작다.

## 초기 로딩 진단

캐시를 끈 새 브라우저 컨텍스트로 구현마다 15회 측정했다. CPU/네트워크 배율을 적용하지 않은
로컬 브라우저 진단이며 공식 Lighthouse 시작 지표가 아니다. 실제 런타임 Chrome 버전은
최종 진단에서 **154.0.8037.98**로 확인했다.

정적 화면 앱 → 전체 화면 Lithent 앱의 초기 script 중앙값은 0.624 → 0.910ms,
load는 16.525 → 16.460ms였다. 전체 렌더로 초기 JS 비용이 약 0.3ms 늘었다.
최종 코어 수정 전/후 script는 0.926/0.920ms, load는 17.065/16.660ms로 비슷했다.
최종 FCP 중앙값은 27.365ms였지만 프레임 대기 변동이 있으므로 시작 성능 개선율을 주장하지 않는다.

  생성 경로의 VDOM·props·DOM 할당을 프로파일링하는 것이 다음 우선순위다.
- 동일 VDOM 객체가 캐시에서 돌아왔을 때 diff 입구에서 조기 반환하는 후보가 있다.
  앞선 별도 진단에서는 작은 개선 신호와 약 +17B가 있었지만, 최종 앱·코어에서는 재측정하지 않았다.
  현재 크기 여유는 43B다. 회수 수정과 함께 성능을 확인한 뒤 적용할 후보이며 이번에는 적용하지 않았다.

## 재현

변경 전 소스는 [adapter-baseline](./adapter-baseline/)에 보존했다.
아래 준비 스크립트는 실제 앱의 Vite 설정과 현재 dist로 전후 앱을 임시 폴더에 빌드한다.
비교 구현의 설치 및 `build-prod`, core/helper dist는 미리 준비해야 한다.
폰트 응답은 `verify`에서 검사한다. 서로 다른 측정은 동시에 실행하지 않는다.

```sh
pnpm build:core
pnpm build:helper
node docs/benchmark/production-prepare.mjs
node docs/benchmark/production-run.mjs verify
node docs/benchmark/production-run.mjs cpu
node docs/benchmark/production-run.mjs mem lithent-before,lithent,preact-hooks,react-hooks,vanillajs
node docs/benchmark/production-run.mjs retention lithent-before,lithent,preact-hooks
node docs/benchmark/production-run.mjs startup lithent-before,lithent,preact-hooks
node docs/benchmark/production-run.mjs extras lithent-before,lithent
```

기본 출력은 `/tmp/lithent-production-review`다. `LITHENT_PRODUCTION_OUT`으로 바꿀 수 있다.
CPU/메모리 측정이 브라우저 종료로 중단되면 `LITHENT_PRODUCTION_RESUME=1`로 완료된 묶음을 보존하고
이어갈 수 있다. 이때 빌드·버전 메타데이터가 바뀌면 실패한다. 실패한 묶음은 전체를 다시 측정한다.

과거 4차 결과의 해석과 캐시 계측은 [APP_AUDIT.md](./APP_AUDIT.md)에 있다.
