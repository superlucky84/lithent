# js-framework-benchmark에 등재하기 위한 Lithent 성능 개선기

[Lithent](https://github.com/superlucky84/lithent)는 클로저로 상태를 관리하는 아주 작은 가상 DOM 라이브러리를 만들고 싶어서 시작했다. 처음에는 속도까지 생각해 본 적이 없었다. 내가 의도한 방식으로 정확히 동작하면서 라이브러리 크기를 작게 유지하는 데 집중했다.

처음 생각했던 동작을 거의 구현하고 나서야 속도에도 관심이 생겼다. 지금의 구조에서 얼마나 빠르게 동작하는지, 어디를 개선할 수 있는지 궁금해졌고, `js-framework-benchmark`에도 올려 보고 싶었다.

Lithent를 처음 만들기 시작했을 때만 해도 AI의 도움을 받아 개발할 수 있는 시대는 아니었다. 몇 년 동안 계속 만들어 오다 보니 어느새 AI와 함께 개발하는 시대가 됐다.

이번 렌더링 성능 개선에는 작정하고 AI 에이전트의 도움을 받았다. 병목이 될 만한 후보를 목록으로 뽑고, 어디를 고치면 가장 큰 효과를 볼 수 있을지 에이전트와 함께 우선순위를 정했다. 우선순위가 높은 후보부터 코드를 바꾸고, 테스트와 벤치마크로 확인해 나갔다.

여러 속도 저하 가능성을 진단하고 개선안을 적용해 보면서도, 번들 크기는 계속 중요한 기준으로 뒀다. 속도를 위해 라이브러리의 작은 크기를 포기하고 싶지는 않았다. 내가 생각한 4KB대의 크기(minified UMD의 Brotli 압축 기준)를 유지하는 선에서 개선하려고 했다. 빨라지더라도 늘어나는 용량에 비해 효과가 작은, 가성비가 떨어지는 후보는 탈락시키고 적용하지 않았다.

그렇게 하나씩 테스트하다 보니 내가 정확하게 처리하려고 공들인 부분들이 오히려 병목인 경우가 있었다. DOM은 하나씩 지우고, 이벤트는 빠짐없이 해제하는 식으로 정직하게 구현했던 코드들이다. 객체를 정리할 때 `delete` 대신 `undefined`를 대입하는 방법은 알고 있었지만, 그 선택이 성능에 이렇게 큰 차이를 만들 수 있다는 것은 AI 에이전트와 최적화를 해 보면서 체감했다. 한 줄짜리 함수를 만드는 위치를 옮겼더니 이전 화면의 메모리가 회수되기도 했다.

## 캐시가 있어도 행 하나를 선택하는 일이 무거웠다

[전편](https://subtleflo.com/2026/8/10/refactoring-key-diff-in-my-own-virtual-dom)에서 다룬 Map 매칭과 LIS(최장 증가 부분 수열)로 불필요한 탐색과 DOM 이동을 줄인 뒤에도, 행 하나를 선택하는 작업에는 비용이 남아 있었다.

선택 표시가 A행에서 B행으로 옮겨 가면 실제로 달라지는 행은 두 개다. 그런데 기존 벤치마크 앱은 부모를 갱신할 때 모든 행을 다시 그리면서, 이벤트 함수와 가상 DOM도 새로 만들고 있었다. DOM을 최소한으로 옮겨도 그전에 JavaScript가 해야 할 일이 많았다.

Lithent에는 이미 `cacheUpdate`라는 helper가 있었다. 처음 이 기능을 넣을 때는 React의 `memo`처럼, 바뀌지 않은 컴포넌트의 렌더링 작업을 생략하는 효과를 생각했다. 그래서 먼저 벤치마크 앱의 행에 이 캐시를 적용했다. 라벨과 선택 여부가 그대로면 이전 가상 DOM을 반환하고, 행의 이벤트 핸들러도 한 번 만들어 재사용하도록 했다. 하지만 캐시를 걸고 나서도 행 선택은 생각만큼 가벼워지지 않았다.

내가 간과한 부분이 있었다. Lithent의 컴포넌트는 처음 한 번만 실행되는 마운터와, 갱신할 때마다 실행되는 업데이터로 나뉜다. 마운터는 어차피 한 번만 실행되니, 여러 번 실행되는 업데이터에만 캐시를 걸어 주면 된다고 생각했다. `cacheUpdate`도 그 생각대로 업데이터를 감싸도록 만들었다.

```tsx
const Row = mount((renew, props) => {
  // 마운터: 처음 한 번만 실행된다.
  const onSelect = () => props.select(props.id);

  // 업데이터: 갱신할 때마다 실행된다. 여기에 캐시를 건다.
  return cacheUpdate(
    () => [props.label, props.selected],
    () => (
      <tr class={props.selected ? 'danger' : ''}>
        <td onClick={onSelect}>{props.label}</td>
      </tr>
    )
  );
});
```

하지만 부모가 갱신되면, 행의 업데이터가 호출되기 전부터 라이브러리가 컴포넌트마다 처리하는 일이 있었다. 이전과 같은 컴포넌트인지 확인하고, 새 props를 반영하고, 갱신할 준비를 한다. 그 뒤에야 업데이터, 즉 캐시 검사가 실행된다. 캐시가 이전 결과를 돌려준 뒤에도, 그 결과를 컴포넌트의 출력으로 감싸 정리하는 일이 남는다.

```text
부모 갱신
→ 행마다: 같은 컴포넌트인지 확인 → 새 props 반영 → 갱신 준비
→ 업데이터 실행 (캐시 적중: 가상 DOM 생성은 생략)
→ 돌려받은 결과를 컴포넌트의 출력으로 감싸 정리
```

캐시가 생략해 준 것은 업데이터 안에서 가상 DOM을 만드는 일뿐이었다. 그 앞뒤에서 컴포넌트마다 반복되는 일은 그대로였다. **출력을 다시 만들지 않는 것과 컴포넌트의 갱신 절차를 생략하는 것은 범위가 달랐다.** 직접 만든 구조인데도 캐시 바깥에서 반복되는 비용을 놓치고 있었다. 그 비용이 얼마나 쌓이는지는 성능을 측정하고 나서야 알게 됐다.

그 비용은 행 수만큼 쌓였다. 1,000행 중 선택을 다른 행으로 옮기는 진단에서, 이 컴포넌트 갱신 절차가 1,001번(부모 한 번과 행 1,000개) 실행됐다. 실제로 바뀐 행은 두 개뿐인데도 그랬다. [캐시가 적중해도 남는 갱신 비용 분석](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/CORE_ANALYSIS.md#21-캐시-적중-후에도-남는-컴포넌트-비용)

그래서 벤치마크 앱에서는 행을 아예 컴포넌트로 만들지 않기로 했다. 행 데이터를 만들 때 그 행을 그리는 캐시 함수도 함께 만들어 두고, Table이 그 함수를 직접 호출하게 했다.

```tsx
function createRow(id, label) {
  const onSelect = () => select(id); // 행을 만들 때 한 번만 만든다.

  const row = {
    id,
    label,
    view: cacheUpdate(
      () => [row.label, selectedId === id],
      () => (
        <tr key={id} class={selectedId === id ? 'danger' : ''}>
          <td onClick={onSelect}>{row.label}</td>
        </tr>
      )
    ),
  };

  return row;
}

const Table = mount(() => {
  return () => <Fragment>{rows.map(row => row.view(row))}</Fragment>;
});
```

행이 컴포넌트가 아니니, 위에서 본 업데이터 앞뒤의 처리도 없다. Table이 갱신되면 행마다 캐시 검사만 하고, 바뀌지 않은 행은 이전 결과를 그대로 돌려준다.

이건 보통의 사용법은 아니다. 평소 앱이라면 행을 컴포넌트로 두는 편이 자연스럽고, 나도 그렇게 만들 것이다.

그래도 라이브러리를 속이거나 규칙을 피해 간 코드는 아니라고 생각한다. Lithent에서는 컴포넌트가 아니어도 함수가 클로저로 자기 데이터와 핸들러를 들고 있을 수 있다. 행에 따로 상태나 생명주기가 필요 없다면 굳이 컴포넌트로 만들지 않아도 된다.

라이브러리 코드는 그대로 두고 앱만 바꿔서, 벤치마크의 공식 측정 도구로 전후를 비교했다. 결과는 꽤 컸다.

| 동작      |  변경 전 |  변경 후 | 전체 시간 감소 |
| --------- | -------: | -------: | -------------: |
| 부분 갱신 | 22.100ms | 17.592ms |          20.4% |
| 행 선택   | 10.136ms |  7.460ms |          26.4% |
| 전체 삭제 | 18.713ms | 10.996ms |          41.2% |

벤치마크의 9개 항목 결과를 정해진 비중으로 합친 점수(이하 가중 점수)로는 약 13.8% 줄었다. 라이브러리 코드는 한 줄도 바꾸지 않았는데 이 정도 차이가 났다. 라이브러리를 고치는 것도 중요하지만, 라이브러리의 특성을 알고 어떻게 활용할지도 그만큼 중요하다는 걸 느꼈다. [앱 전후 측정 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/PRODUCTION_RESULTS.md)

이 과정에서 배운 것은, 캐시를 걸었다는 사실만으로 그 앞뒤의 작업까지 없어지지는 않는다는 점이다. 캐시가 실제로 무엇을 생략해 주는지 구체적으로 봐야 했다.

### 그래도 캐시를 좋아하지는 않는다

사실 나는 `memo`나 `cacheUpdate` 같은 기능을 별로 좋아하지 않는다. `cacheUpdate`를 직접 만들어 놓고도 그렇다.

Lithent에서는 컴포넌트가 생성될 때 한 번만 필요한 함수와 상태를 마운터에 둘 수 있다. 그때 만든 클로저와 함수는 갱신 때도 그대로 쓴다. 이벤트 핸들러도 매번 업데이터에서 새로 만들 필요가 없다. 애초에 이 구조를 선택하면서, 함수와 클로저를 유지하기 위해 별도의 캐시를 고민해야 할 이유는 적을 거라고 생각했다.

컴포넌트마다 거치는 갱신 절차에도 비용이 있고, 그 비용이 이런 미세한 성능 측정에 드러난다는 것은 이번에 알게 됐다. 갱신할 때마다 새로 만들어지는 가상 DOM 같은 객체도 있다. 그래도 함수와 클로저를 어디에서 만들고 무엇을 갱신할지 잘 설계하면, 반복해서 메모리를 할당하는 일을 충분히 줄일 수 있다고 생각한다. 이번에 확인한 작은 갱신 비용이 이 구조의 큰 문제라고 느껴지지는 않는다.

생각해 보면 `memo` 같은 기능을 쓴다는 것 자체가 가상 DOM의 약점을 피해 가는 트릭에 가깝다. 가상 DOM은 상태가 바뀌면 화면을 다시 그려 보고, 이전 결과와 비교해서 바뀐 곳을 찾는다. 실제로 바뀐 곳이 한 줄뿐이어도, 다시 그리고 비교하는 일은 다시 그린 범위 전체에서 일어난다. 캐시는 그 일을 건너뛰게 해 주는 장치다. 이건 Lithent만의 이야기가 아니다. 가상 DOM을 쓰는 프레임워크라면 근본적으로 같은 문제를 안고 있고, 그래서 저마다 비슷한 장치를 두고 있다.

이번 벤치마크에서는 눈에 보이는 수치를 개선하고 싶어서 그 트릭을 적극적으로 썼고, 효과도 확인했다. 그래도 평소 앱을 만들 때까지 이런 기능에 의존하고 싶지는 않다. 별도의 `memo` 없이도 구조를 잘 설계하면 충분히 쓸 만한 속도가 나올 거라고 여전히 믿는다.

## 하나씩 정확하게 지우던 코드가 병목이었다

여기부터는 라이브러리 자체를 고친 이야기다. 그중 특히 인상적이었던 병목은 전체 삭제였다.

처음 AI의 도움 없이 직접 구현할 때는 삭제할 DOM마다 하나씩 `remove()`를 호출했다. 삭제 대상을 정확히 찾아서 각각 지우는 것이 가장 확실하다고 생각했다. 내가 보기에는 아주 정직한 구현이었다.

컴퓨터처럼 한 단계도 빠뜨리지 않고 정확하게 구현해야 한다는 강박이 있었던 것 같다. 각 항목을 제대로 처리하는 데 신경을 쓰다 보니, 부모 아래의 자식을 전부 지운다는 상황을 활용할 수 있다는 점은 보지 못했다.

그때 AI가 삭제 대상이 부모의 자식 전체라면 부모를 한 번 비우는 더 빠른 경로도 있다는 것을 알려줬다. 내가 정확하게 하려고 반복했던 호출들을 줄일 수 있었던 것이다. 다만 부모 안에 다른 내용이 함께 있으면 안 되므로, 삭제할 항목들이 부모의 전체 자식인지 확인하는 코드를 넣었다.

그런데 이번에는 그 빠른 경로를 쓰기 위한 확인 자체가 병목이 됐다. 문제는 이 확인이 호출되는 위치였다.

이 일은 목록의 행이 컴포넌트일 때 생겼다. 앞에서 벤치마크 앱의 행을 컴포넌트가 아니게 바꾼 것은 나중 일이고, 그전의 앱도, 평소의 많은 앱도 행을 컴포넌트로 만든다. 행이 컴포넌트이면 행 하나를 지울 때마다 이 확인 함수가 다시 불렸다. 그리고 그때마다 부모의 자식을 처음부터 다시 셌다.

1,000행을 지운다면 이런 식이다.

| 지우는 행 | 확인하는 자식 |
| --------- | ------------: |
| 첫 번째   |       1,000개 |
| 두 번째   |         999개 |
| 세 번째   |         998개 |
| …         |             … |
| 마지막    |           1개 |

모두 더하면 약 50만 번이다. 행이 두 배가 되면 확인 횟수는 네 배로 늘어난다. 빠른 삭제가 가능한지 알아보는 준비 작업이, 정작 삭제보다 훨씬 많은 일을 하고 있었던 것이다. 당시 프로파일에서는 전체 삭제 시간의 약 73%가 이 함수에 잡혔다.

우선 행 하나의 내용을 지우러 들어온 호출에서는 아예 세지 않도록 했다. 여러 항목을 한꺼번에 지울 때만 확인한다. CPU를 4배 느리게 만든 진단 환경에서 전체 삭제는 76.7ms에서 15.9ms로 줄었다. 공식 측정 도구의 점수와는 다른 조건이지만, 반복 확인에 얼마나 많은 시간이 들어갔는지 보여 주는 결과였다. [삭제 병목과 수정 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/STATUS.md)

이어서 자식을 세다가 지울 항목 수를 넘으면 바로 멈추게 했다. 지울 항목이 두 개인데 자식을 세 개째 봤다면, 나머지 수천 개를 셀 필요가 없다. 이미 부모 전체를 비울 수 없다는 결론이 났기 때문이다.

나중에는 개수 대신 실제 DOM이 일치하는지 확인하도록 바꿨다. 컴포넌트 안으로 들어가 삭제할 DOM을 찾고, 부모의 자식들과 순서대로 같은 객체인지 비교한다. 끝까지 일치할 때만 한 번에 비우고, 다른 것이 나오면 그 자리에서 멈춘다. 이렇게 하면 외부 코드가 라이브러리가 관리하는 DOM을 바꿔 두더라도, 그 DOM까지 함께 지우지는 않는다. 사실 가상 DOM이 관리하는 영역을 외부 코드가 직접 건드리는 것은 올바른 사용법이 아니다. 그래도 잘못 사용했을 때 라이브러리가 엉뚱한 DOM까지 지우지 않는다면 그만큼 더 안전하다.

사실 처음 구현할 때부터 외부 코드가 바꾼 DOM까지 이렇게 대조하고 싶었던 것은 아니다. 라이브러리를 작게 유지하고 코드가 하는 일도 줄이는 쪽이 더 가성비 있다고 생각했다. 단순한 구현을 선택한 데는 그런 의도가 있었다.

AI의 도움 없이 혼자 했다면 이번에도 가성비를 택하고 그 정도에서 멈췄을 것 같다. 잘못된 사용에서 생길 수 있는 이런 경우까지 챙길 수 있었던 건 AI가 이 부분을 끝까지 검토해 준 덕분이다.

이 확인도 공짜는 아니었다. 원래부터 한 번에 지울 수 있었던 일반 DOM 행에서는 실행 시간이 약 1% 늘어날 수 있다는 신호가 있었다. 다만 측정 순서에 따라 늘기도 하고 줄기도 해서 확실한 손해라고 보지는 않았다. 반면 행이 컴포넌트인 목록은 DOM을 1,000번 하나씩 지우던 것을 한 번에 비울 수 있게 됐고, 공식 측정 도구로 잰 전체 삭제 시간이 13.311ms에서 12.267ms로 약 7.84% 줄었다. [후속 삭제 구현의 이득과 비용](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/BULK_REMOVAL_V2_RESULTS.md)

부모를 통째로 비우면서 외부 DOM까지 지우지 않으려면 이 확인은 필요했다. 그래서 일반 DOM 행의 작은 추가 비용 가능성을 받아들이고, 컴포넌트 행의 일괄 삭제와, 잘못 사용했을 때의 안전장치를 얻는 쪽을 선택했다.

## 이벤트를 하나도 빠짐없이 해제하려고 했다

이벤트 정리는 Lithent를 처음 구현할 때부터 특히 신경 썼던 부분이다.

`destroy()`를 호출하거나 컴포넌트의 생명주기가 끝나면, DOM에 붙여 둔 이벤트도 전부 해제하고 싶었다. `onClick`, `onInput`처럼 `on` 접두사로 전달받아 등록한 이벤트는 하나도 빠짐없이 `removeEventListener`를 호출하도록 했다. 자식 DOM까지 내려가며 빠뜨리는 이벤트가 없도록 구현하는 데 공을 들였다.

그런데 그렇게 신경 써서 만든 정리 작업이 전체 삭제의 병목 중 하나였다. 행마다 이벤트가 두 개씩만 있어도 1,000행을 지울 때 수천 번의 해제 호출이 더해진다. 화면에서 사라질 DOM을 순회하며 붙어 있는 이벤트를 일일이 떼고 있었던 것이다.

DOM과 그 리스너를 더 이상 아무도 참조하지 않으면, 브라우저가 둘을 함께 메모리에서 정리할 수 있다. 버려지는 DOM의 이벤트를 모두 직접 해제하는 데 들인 작업을 줄일 여지가 있었다.

그래서 버려지는 일반 DOM에서는 개별 리스너 해제를 생략하도록 바꿨다. 이 변경만 따로 비교한 진단에서 전체 삭제 시간의 중앙값은 9.6ms에서 8.2ms로 줄었다. 공식 측정 도구의 점수와는 다른 조건이지만, 이벤트를 하나씩 해제하던 작업에도 비용이 있었음을 확인할 수 있었다. [이벤트 해제 생략의 측정 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/STATUS.md#54-코어-버려지는-dom의-리스너-해제-제거--수정함-미커밋)

물론 DOM을 화면에서 떼었다는 이유만으로 메모리가 바로 회수되는 것은 아니다. 사용자가 제거된 DOM을 따로 보관하면 리스너도 남을 수 있고, 그 DOM에 이벤트를 보내면 핸들러가 실행될 수도 있다. 그래서 계속 살아 있는 DOM의 정리는 그대로 유지한다. 핸들러가 바뀌거나 없어질 때의 해제, 컴포넌트가 사라질 때 실행하는 정리 함수, portal로 다른 위치에 그린 내용의 이벤트 정리가 그렇다.

내가 꼼꼼하게 구현했다고 생각하던 코드가 실제로 얼마나 자주 실행되는지 보면서, 한 가지에 몰두하면 시야가 얼마나 좁아질 수 있는지 실감했다. 라이브러리를 만들다 보면 계산 과정과 동작의 정확성을 계속 따지게 되는데, 거기에 몰두하다 보니 숲을 보지 못했던 것 같다.

나는 평소 성실함에만 매몰돼 비효율적으로 일하게 되는 것을 경계하고, 같은 일도 더 영리하게 할 수 있는 방법을 찾으려고 노력하는 편이다. 그런데도 이벤트를 하나도 빠뜨리지 않고 해제하는 데 집중한 나머지, 그 일을 전부 직접 해야 하는지는 돌아보지 못했다.

## 한 줄짜리 함수가 메모리 회수를 늦추고 있었다

메모리 사용과 회수는 나도 처음부터 중요하게 생각했다. 테스트를 반복하면서 메모리 사용량이 계속 쌓이지 않도록 신경 써 왔다.

다만 사용이 끝난 메모리가 그 즉시 회수돼야 한다고 생각한 것은 아니다. 회수까지 어느 정도 유예가 생겨 중간에 메모리 사용량이 늘어나 보이는 것은 받아들이고 있었다.

그런데 이번에는 성능을 끝까지 끌어올리려고 반복 갱신을 더 집요하게 테스트하다 보니, 이전 화면의 메모리가 예상보다 오래 남는 문제를 발견하게 됐다.

1,000행을 유지하며 부분 갱신을 100회 반복한 뒤 강제로 메모리를 정리(GC)해도 JS heap이 약 17.77MB까지 올라갔다. 생성하고 전부 지우는 몇 차례의 검사에서는 충분히 드러나지 않았던 문제였다.

관련된 코드는 부모를 찾아가는 getter였다. 가상 노드는 실제 DOM 부모와 삽입 위치를 찾을 때 이 함수를 사용한다.

아래는 당시 구조를 단순화한 예제다.

```ts
function reconcileChildren(newParent, oldParent) {
  const oldChildren = oldParent.children;
  const getParent = () => newParent;

  return newParent.children.map((child, index) => {
    return reconcile(child, oldChildren[index], getParent);
  });
}
```

겉으로는 `getParent`가 새 부모만 반환한다. 그런데 JavaScript 엔진은 같은 함수 안에서 만든 클로저들이 쓰는 변수를 한 공간에 모아 둘 수 있다. 이 예제에서는 오래 살아 있는 `getParent`와, 이전 자식 배열(`oldChildren`)을 쓰는 `map` 콜백이 같은 함수 안에서 만들어졌다. 관찰한 환경에서는 그 때문에 `getParent`가 남아 있는 동안 이전 가상 DOM까지 필요 이상으로 오래 붙잡혀 있었다.

수정은 부모 getter를 별도 함수에서 생성하는 것이었다.

```ts
const makeParentGetter = parent => () => parent;

// diff 함수 안에서는 부모만 전달한다.
const getParent = makeParentGetter(newParent);
```

반환하는 값은 같다. 함수가 만들어지는 환경을 분리해서, 이제 getter는 부모 하나만 붙잡는다.

같은 반복 갱신 조건에서 수정 후 JS heap은 약 **4.03MB**였다. WeakRef를 이용한 브라우저 검사에서도, 수정 전에는 50회 갱신한 과거 노드까지 남았지만 수정 후에는 현재 노드만 남는 것을 확인했다. [메모리 회수 측정과 검증](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/PRODUCTION_RESULTS.md#부모-getter-회수-수정)

가볍게 생각했던 한 줄짜리 클로저도, 어디서 만드느냐에 따라 메모리가 정리되는 시점을 바꿀 수 있다는 걸 느꼈다. 중첩 함수를 줄이는 게 낫겠다는 생각도 들었지만, 그게 언제나 정답인지는 모르겠다. 생각보다 미묘했다.

## 객체를 깨끗하게 정리하는 데도 비용이 들었다

렌더러는 노드에 임시 정보를 붙인다. 이전 인덱스, 이전 props, 삭제할 자식 같은 정보다. 작업이 끝나면 더 이상 필요하지 않으니 지우는 것이 나에게는 자연스러운 정리 방법이었다.

```ts
delete node.oi;
delete node.op;
delete node.oc;
```

그런데 수많은 노드를 갱신할 때마다 속성을 추가하고 지우면 객체의 속성 구성이 반복해서 바뀔 수 있다. JavaScript 엔진이 속성 접근을 최적화하는 데도 이 구성이 영향을 준다.

`delete` 대신 `undefined`를 대입하는 방법 자체는 알고 있었다. 하지만 직접 바꾸고 측정해 보기 전까지는 크게 신경 쓰지 않았다. 그래서 이 임시 정보는 속성의 자리는 그대로 두고 값만 비우도록 바꿨다.

```ts
node.oi = node.op = node.oc = undefined;
```

이전 객체를 가리키던 값이라면 `undefined`를 대입하는 것만으로 연결을 끊을 수 있다. 객체를 놓아 주는 데 속성 자체까지 없앨 필요는 없었다. 다만 사용자가 실제로 지운 prop은 지금도 속성째 제거한다.

비슷한 반복 작업은 컴포넌트 props에도 있었다. 기존 객체의 key를 전부 지우고 새 값을 복사하던 것을, 사라진 key만 지우고 나머지 값은 갱신하도록 바꿨다. 컴포넌트가 클로저로 참조하는 props 객체는 유지하면서 불필요한 삭제와 재추가를 줄였다.

이후에는 element나 text처럼 종류마다 다르게 만들던 가상 DOM 객체를, 하나의 생성 함수에서 만들도록 바꿨다. 자주 쓰는 속성 13개를 같은 순서로 넣고, 아직 값이 없는 속성도 `undefined`로 미리 만들어 뒀다. JavaScript 엔진이 비슷한 구조의 객체를 계속 다루게 해서, 노드의 속성을 반복해서 읽고 쓰는 비용을 줄이려는 변경이었다. 컴포넌트나 root에서만 쓰는 나머지 속성은 필요한 노드에만 추가했다.

이 변경의 별도 비교에서 가중 점수는 약 **5.9%**, JS 시간은 약 **14.4%** 줄었다. 대신 1만 행 메모리는 약 **2.5%**, 0.68MB 늘었다. 자리를 미리 잡아 두는 데 드는 비용도 있었던 셈이다. 모든 필드를 초기화하는 더 큰 안은 메모리 증가가 커서 선택하지 않았다. [노드 생성 구조 실험](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/NODE_SHAPE_RESULTS.md)

AI 에이전트가 여러 안을 비교하고 측정해 준 덕분에 이런 차이를 볼 수 있었다. 나는 그 결과를 보면서, 속도를 조금 더 얻기 위해 메모리와 번들 크기를 어디까지 늘려도 괜찮을지 생각해 보게 됐다. 당시에는 속도와 번들 크기의 균형을 우선으로 보고 있었기 때문에, 이 정도의 메모리 증가는 받아들이고 속도 개선을 선택했다.

## 이미 아는 사실을 매번 다시 계산하고 있었다

어느 정도 큰 계산 비용을 줄인 뒤에는 비교적 작은 부분에서도 성능을 개선할 여지를 찾았다. 물론 내가 찾은 건 아니고, AI가 찾아줬다. 😅

직접 가상 DOM diff를 구현할 때는 흐름이 조금만 틀어져도 자꾸 오동작해서 스트레스를 많이 받았다. 그래서 같은 조건을 한 번 더 확인하는 식으로 방어 로직을 정직하게 겹쳐 넣은 부분도 있었다. 그런 중복이 남아 있다는 건 나도 어느 정도 알고 있었다.

다만 그 작은 확인들이 미세한 속도 차이에까지 영향을 줄 거라고는 생각하지 못했다.

새 노드를 추가하는 경로에는 필요 없는 타입 비교가 있었다. 이전 노드가 없는데도 새 노드와 이전 노드의 타입이 같은지 확인하고 있었던 것이다. 여기에 이전 노드가 있을 때만 비교하도록 조건을 붙였다.

```ts
const sameType = !!originalWDom && compareType(newWDom, originalWDom);
```

수정은 작지만 호출 횟수가 컸다. 당시 1만 행을 생성할 때 자식 노드를 비교할 준비 작업이 약 10만 번 실행됐다. 공식 측정 도구로 따로 비교해 보니 1,000행 생성의 JS 시간은 약 4.5% 줄었다. 브라우저 렌더링을 포함한 전체 시간 감소는 약 1.0%였다. [생성 경로 프로파일과 비교](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/CREATION_PROFILE.md)

목록 갱신에서도 비슷한 일이 있었다. 행 하나를 선택할 뿐이라면 목록 순서는 그대로고, 대부분의 행은 내용도 바뀌지 않는다. 그런데 매번 항목을 다시 찾고, 옮길 일이 있는지 계산할 준비까지 하고 있었다.

각 단계에서 이미 알 수 있는 사실을 조금 더 일찍 활용하도록 바꿨다.

항목의 위치를 굳이 다시 찾을 필요가 없을 때는 탐색을 건너뛰었다. 순서가 유지된 목록은 재배치 준비를 건너뛰고, 캐시에서 그대로 돌아온 객체는 내용을 다시 비교하지 않도록 했다. 조건이 맞지 않으면 기존 방식으로 처리한다.

나는 보통 개발할 때 만들어 놓은 함수를 최대한 재사용한다. 같은 일을 할 때마다 다시 생각하고 구현하는 부담을 줄이고 싶어서다. 그게 개발할 때는 확실히 도움이 되지만, 성능까지 좋아지는 것은 아니라는 걸 이번에 느꼈다. 내가 다시 생각할 일을 줄였어도, 컴퓨터는 그 함수 안에서 같은 계산을 계속하고 있었다.

내 딴에는 더 많은 생각을 하기 싫어서, 반복되는 일은 그냥 컴퓨터에게 맡기면 된다고 생각했다. 내가 신경 써야 할 부분은 줄이고, 그만큼 컴퓨터에게 일을 더 시키면 된다고 여겼다. 그런데 성능을 극단적으로 따져야 할 때는 아니었다.

사실 내가 편하고 컴퓨터가 일을 많이 하는 게 더 정상인 것 같긴 한데… 🥲

이런 작은 작업을 줄이는 최신 변경들을 묶어 공식 측정 도구로 로컬에서 비교한 결과, 가중 점수는 **2.59%** 줄었다. 부분 갱신은 **9.21%**, 선택은 **12.91%** 줄었다. [최신 최적화 묶음의 측정 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/POSITIONAL_KEYS_OFFICIAL_RESULTS.md)

내가 대수롭지 않게 생각했던 작은 확인도 컴퓨터는 빠짐없이 반복하고 있었다. 정말 컴퓨터는 정직하다.

## 그럴듯한 최적화도 되돌렸다

AI의 도움으로 후보를 만들기는 훨씬 수월해졌다. 그러다 보니 채택 여부를 판단하는 일이 더 중요해졌다.

안정적인 event proxy도 그중 하나였다. 이름만 들으면 어려워 보이지만, 가상 DOM이 화면을 다시 그릴 때 이벤트를 어떻게 다루는지 보면 어렵지 않다.

```tsx
<button onClick={() => select(row.id)}>선택</button>
```

이렇게 JSX 안에서 바로 함수를 만들면(inline 핸들러), 화면을 다시 그릴 때마다 새 함수가 만들어진다. 코드는 똑같아도 JavaScript에서는 이전 함수와 다른 객체다. 가상 DOM은 이전 props와 새 props를 비교하다가 `onClick`이 바뀌었다고 판단한다. 그래서 실제 DOM에서 이전 리스너를 `removeEventListener`로 떼고, 새 리스너를 `addEventListener`로 다시 붙인다. 1,000개의 행에 이런 버튼이 하나씩 있으면, 화면에 보이는 내용이 그대로여도 갱신할 때마다 DOM 호출이 2,000번 생긴다.

event proxy는 이 반복을 피하는 방법이다. DOM에는 처음 한 번만 고정된 중계 함수(proxy)를 등록해 둔다. 이벤트가 발생하면 이 함수가 그 요소에 저장된 최신 핸들러를 찾아 대신 호출한다. 다시 그릴 때는 DOM의 리스너를 건드리지 않고, 저장해 둔 핸들러만 새 함수로 바꿔 끼운다.

```text
proxy 없음: 갱신마다 removeEventListener(이전 함수) → addEventListener(새 함수)
proxy 있음: 처음 한 번 addEventListener(proxy) → 갱신마다 저장된 핸들러만 교체
```

실제로 inline 핸들러를 쓰는 1,000행 화면을 따로 만들어 비교해 보니, 전체 시간이 선택은 약 9.4%, 부분 갱신은 약 5.2% 줄었다.

하지만 Lithent에서는 이런 상황이 흔하지 않다. 앞에서 말했듯 컴포넌트가 처음 만들어질 때 한 번 실행되는 마운터에 핸들러를 미리 선언해 두면, 다시 그릴 때도 같은 함수를 그대로 쓴다.

```tsx
const Row = mount((renew, props) => {
  const onSelect = () => props.select(props.id); // 마운터에서 한 번만 만든다.

  return () => <button onClick={onSelect}>선택</button>;
});
```

함수가 바뀌지 않으니 리스너를 떼고 다시 붙일 일도 없다. 업데이터 안에서 매번 inline으로 함수를 만드는 것은 오히려 특수한 경우에 가깝다.

벤치마크 앱도 핸들러를 재사용하고 있어서, 선택과 부분 갱신에서 리스너 재등록이 0이었다. proxy가 줄이려는 비용을 애초에 지불하고 있지 않았던 것이다. 결국 event proxy는 항상 이득을 보는 개선이 아니었다. 이득은 inline 핸들러를 쓰는 경우에 한정됐는데, 그 대가로 모든 앱이 proxy의 크기와 메모리, 브라우저 이벤트를 직접 다루는 코드와 맞추는 비용을 부담해야 했다. 그래서 기본 구현은 핸들러를 DOM에 직접 등록하는 원래 방식으로 돌아갔다. [이벤트 구현 복원 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/NATIVE_EVENTS_RESULTS.md)

## 숫자를 믿기 전에 확인한 것들

측정 결과를 믿는 일도 생각보다 까다로웠다. 한번은 삭제 코드만 고쳤는데 행 선택 시간이 9% 가까이 줄어든 결과가 나왔다. 자세히 보니 코드가 빨라진 것이 아니라, 브라우저가 다음 화면을 그릴 차례를 기다리는 시간이 우연히 짧아진 것이었다. 숫자가 좋아졌다고 해서 그게 곧 내가 고친 코드의 효과는 아니었다.

그래서 결과를 한 번에 믿지 않았다. 고치기 전과 후를 번갈아 잴 때도, 어느 쪽을 먼저 실행하느냐에 따라 결과가 조금씩 달라졌다. 그럴 때는 순서를 바꿔 한 번 더 재고, 두 결과가 같은 방향을 가리키는지 확인했다.

빨라졌다는 이유만으로 채택하지도 않았다. 속도를 위해 지름길을 내다 보면 원래 하던 일을 빠뜨리기 쉽다. 예를 들어 목록을 다시 그릴 때 기존 요소를 재사용하지 않고 새로 만들어 버리면, 입력창에 글자를 치던 중에 커서가 사라질 수 있다. 화면에서 사라진 컴포넌트의 정리 작업이 실행되지 않거나, 이전 화면의 메모리가 계속 남을 수도 있다. 그래서 이런 동작이 그대로인지도 함께 검사했다. 벤치마크 수치를 얻는 대신 원래 동작을 잃어버린다면 채택할 이유가 없었다.

이 글에 나온 개선율들도 각자 다른 시점의 비교다. 앱 변경의 13.8%, 노드 생성 구조의 5.9%, 최신 묶음의 2.59%를 더해서 전체 개선율로 만들 수는 없다. 측정 기록을 남긴 덕분에 지금 다시 글을 쓰면서도 어디까지 말할 수 있는지 확인할 수 있었다.

## 작은 차이를 파고드는 재미

사실 처음에는 이런 렌더링 성능 측정을 내심 우습게 여기기도 했다. 사람들이 아주 미세한 시간 차이까지 따지는 게 그렇게 중요한가 싶었다. 이미 주류가 된 React도 이런 벤치마크에서 빠르기만 한 것은 아니다. 이번에 남긴 로컬 비교에서도 React는 행 교환과 1만 행 생성에서 상대적으로 느렸다. [당시 React·Preact 비교 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/PEER_BASELINE_RESULTS.md#cpu-전체-시간과-목표)

그런데 직접 렌더링 성능에 집중하다 보니, 그 차이를 파고드는 재미가 있었다. 아주 사소해 보이는 함수 처리 하나도 반복되면 지연을 만들고, 미세한 성능 차이로 나타난다는 것을 알게 됐다. 매번 만들던 함수나 배열, 이미 결론이 났는데도 계속하던 검사를 따라가면서 내가 만든 코드가 실제로 얼마나 많은 일을 하고 있었는지 보게 됐다.

삭제할 DOM을 하나씩 지우고 이벤트를 빠짐없이 해제하려고 공들였는데, 그 부분들이 병목이었다는 점이 특히 아이러니했다. 내가 정확하게 한다고 신경 쓴 작업을 줄여도 필요한 결과를 얻을 수 있다는 것이 신기했다. 이미 알고 있던 `undefined` 대입이 실제 성능 차이로 이어지는 것도 확인했고, 부모 getter를 만드는 위치가 이전 화면의 수명을 바꾸는 것도 봤다. 코드를 바꾸고 다시 측정하면서, 왜 차이가 생겼는지 이해해 가는 과정 자체가 재미있었다.

그래도 이런 미세한 속도 차이보다 프레임워크의 예측 가능성과 동작의 투명성이 더 중요하다는 생각에는 변함이 없다. 어떤 상태에서 무엇이 갱신되는지 예상할 수 있고, 왜 그런 동작을 하는지 코드를 따라가며 이해할 수 있는 쪽을 더 중요하게 생각한다.

그 생각을 유지하면서도, 작은 비용을 찾아 하나씩 줄여 보는 일에는 예상하지 못했던 재미가 있었다.
