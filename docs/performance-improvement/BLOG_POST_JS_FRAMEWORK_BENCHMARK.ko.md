# js-framework-benchmark에 등재하기 위한 Lithent 성능 개선기

Lithent는 클로저로 상태를 관리하는 아주 작은 가상 DOM 라이브러리를 만들고 싶어서 시작했다. 처음에는 속도까지 생각해 본 적이 없었다. 내가 의도한 방식으로 정확히 동작하면서 라이브러리 크기를 작게 유지하는 데 집중했다.

처음 생각했던 동작을 거의 구현하고 나서야 속도에도 관심이 생겼다. 지금의 구조에서 얼마나 빠르게 동작하는지, 어디를 개선할 수 있는지 궁금해졌고, `js-framework-benchmark`에도 올려 보고 싶었다.

Lithent를 처음 만들기 시작했을 때만 해도 AI의 도움을 받아 개발할 수 있는 시대는 아니었다. 몇 년 동안 계속 만들어 오다 보니 어느새 AI와 함께 개발하는 시대가 됐다.

이번 렌더링 성능 개선에는 작정하고 에이전트의 도움을 받았다. 병목이 될 만한 후보를 목록으로 뽑고, 어디를 고치면 가장 큰 효과를 볼 수 있을지 에이전트와 함께 우선순위를 정했다. 우선순위가 높은 후보부터 코드를 바꾸고, 테스트와 벤치마크로 확인해 나갔다.

여러 속도 저하 가능성을 진단하고 개선안을 적용해 보면서도, 번들 크기는 계속 중요한 기준으로 뒀다. 속도를 위해 라이브러리의 작은 크기를 포기하고 싶지는 않았다. 내가 생각한 4KB대의 크기(minified UMD의 Brotli 압축 기준)를 유지하는 선에서 개선하려고 했다. 빨라지더라도 늘어나는 용량에 비해 효과가 작은, 가성비가 떨어지는 후보는 탈락시키고 적용하지 않았다.

그렇게 하나씩 테스트하다 보니 내가 정확하게 처리하려고 공들인 부분들이 오히려 병목인 경우가 있었다. DOM은 하나씩 지우고, 이벤트는 빠짐없이 해제하는 식으로 정직하게 구현했던 코드들이다. 객체를 정리할 때 `delete` 대신 `undefined`를 대입하는 방법은 알고 있었지만, 그 선택이 성능에 이렇게 큰 차이를 만들 수 있다는 것은 AI 에이전트와 최적화를 해 보면서 체감했다. 한 줄짜리 함수를 만드는 위치를 옮겼더니 이전 화면의 메모리가 회수되기도 했다.

## 캐시가 있어도 행 하나를 선택하는 일이 무거웠다

[전편](https://subtleflo.com/2026/8/10/refactoring-key-diff-in-my-own-virtual-dom)에서 다룬 Map 매칭과 LIS(최장 증가 부분 수열)로 불필요한 탐색과 DOM 이동을 줄인 뒤에도, 행 하나를 선택하는 작업에는 비용이 남아 있었다.

선택 표시가 A행에서 B행으로 옮겨 가면 실제로 달라지는 행은 두 개다. 그런데 기존 벤치마크 앱은 부모를 갱신할 때 모든 행의 업데이터를 실행하고, 이벤트 함수와 가상 DOM도 새로 만들고 있었다. DOM을 최소한으로 옮겨도 그전에 JavaScript가 해야 할 일이 많았다.

Lithent에는 이미 `cacheUpdate`라는 helper가 있었다. 처음 이 기능을 넣을 때는 React의 `memo`처럼, 바뀌지 않은 컴포넌트의 렌더링 작업을 생략하는 효과를 생각했다. 그래서 벤치마크 앱의 행에도 적용했다. 라벨과 선택 여부가 그대로면 이전 가상 DOM을 반환하고, 행의 이벤트 핸들러도 한 번 만들어 재사용하도록 했다.

그런데 내가 간과한 부분이 있었다. Lithent는 클로저에 상태를 유지하기 위해, 처음 한 번 실행하는 마운터와 갱신할 때 실행하는 업데이터를 구분한다. `cacheUpdate`가 반환하는 함수를 그 업데이터로 사용한다. 캐시가 적중하면 실제 행의 가상 DOM을 만드는 함수는 생략하지만, 캐시를 확인하는 위치까지는 컴포넌트의 갱신 경로를 따라 들어와야 했다.

트리에서 같은 컴포넌트인지 확인하면 기존 마운터가 만든 클로저와 업데이터를 재사용한다. 이때 props를 동기화하고 갱신 문맥을 준비한 뒤에야 캐시 검사 함수를 호출한다. 캐시가 이전 가상 DOM을 반환한 뒤에도, 그 출력을 감싸는 Fragment와 컴포넌트 메타데이터를 처리하는 작업은 남는다.

나는 출력이 캐시되면 그 컴포넌트에서 할 일도 대부분 없어질 거라고 생각했다. 하지만 **출력을 다시 만들지 않는 것과 컴포넌트의 갱신 절차를 생략하는 것은 범위가 달랐다.** 직접 만든 구조인데도 캐시 바깥에서 반복되는 비용을 놓치고 있었다. 그 비용이 얼마나 쌓이는지는 성능을 측정하고 나서야 알게 됐다.

당시 구조는 행마다 별도의 컴포넌트였다. 1,000행의 선택을 바꾸는 진단에서 props 동기화와 래퍼 생성 등이 각각 1,001회 발생했다. 부모 한 번과 모든 행의 갱신 입구를 통과하고 있었던 것이다. [캐시가 적중해도 남는 갱신 비용 분석](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/CORE_ANALYSIS.md#21-캐시-적중-후에도-남는-컴포넌트-비용)

벤치마크 앱에서는 행마다 독립적인 컴포넌트 수명을 둘 필요가 크지 않았다. 그래서 Table 안에 행별 캐시를 두고, 캐시가 keyed `tr`를 반환하도록 구성을 바꿨다.

```text
변경 전: Table → 행 컴포넌트 → 행 캐시 → tr
변경 후: Table → 행 캐시 → tr
```

같은 코어를 사용해 앱 전후를 비교한 결과는 꽤 컸다.

| 동작      |  변경 전 |  변경 후 | 전체 시간 감소 |
| --------- | -------: | -------: | -------------: |
| 부분 갱신 | 22.100ms | 17.592ms |          20.4% |
| 행 선택   | 10.136ms |  7.460ms |          26.4% |
| 전체 삭제 | 18.713ms | 10.996ms |          41.2% |

이 앱 변경 묶음의 가중 지표는 약 13.8% 줄었다. 캐시와 행 경계, 핸들러 등을 함께 정리한 결과이므로 컴포넌트 하나를 없애서 전부 얻은 효과로 볼 수는 없다. 그래도 렌더러를 더 고치기 전에 앱이 라이브러리를 어떻게 사용하고 있는지 살펴볼 이유는 충분했다. [앱 전후 측정 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/PRODUCTION_RESULTS.md)

행이 독립적인 상태와 생명주기를 가져야 한다면 컴포넌트 경계는 필요하다. 이번에 배운 것은 그 경계와 캐시가 생략하는 범위를 구체적으로 봐야 한다는 점이었다. 캐시가 있다는 사실만으로 그 앞의 작업까지 없어지지는 않았다.

사실 나는 `memo`나 `cacheUpdate` 같은 기능을 별로 좋아하지 않는다. `cacheUpdate`를 직접 만들어 놓고도 그렇다.

Lithent에서는 컴포넌트가 생성될 때 한 번만 필요한 함수와 상태를 마운터에 둘 수 있다. 그때 만든 클로저와 함수는 갱신 때도 그대로 쓴다. 이벤트 핸들러도 매번 업데이터에서 새로 만들 필요가 없다. 애초에 이 구조를 선택하면서, 함수와 클로저를 유지하기 위해 별도의 캐시를 고민해야 할 이유는 적을 거라고 생각했다.

마운터와 업데이터를 나누어 관리하는 데 드는 비용이 이런 미세한 성능 측정에 영향을 준다는 것은 알게 됐다. 가상 DOM이나 래퍼처럼 갱신 때 새로 만들어지는 객체도 있다. 그래도 함수와 클로저를 어디에서 만들고 무엇을 갱신할지 잘 설계하면, 반복해서 메모리를 할당하는 일을 충분히 줄일 수 있다고 생각한다. 이번에 확인한 작은 갱신 비용이 이 구조의 큰 문제라고 느껴지지는 않는다.

이번 벤치마크에서 캐시의 효과를 확인했어도, 평소 앱을 만들 때까지 이런 기능에 의존하고 싶지는 않다. 별도의 `memo` 없이도 구조를 잘 설계하면 충분히 쓸 만한 속도가 나올 거라고 여전히 믿는다.

다만 이번 벤치마크 앱에서는 눈에 보이는 수치를 개선하고 싶어서 `cacheUpdate`를 적극적으로 활용했다. React나 Preact에서 행 전체를 메모이제이션하듯, 바뀌지 않은 행의 가상 DOM 전체를 캐시해 재사용하도록 했다. 평소에는 이런 캐시에 기대고 싶지 않다고 생각하면서도, 벤치마크에서는 수치를 위해 약간의 기교를 부린 셈이다. 그 점은 인정한다.

## 하나씩 정확하게 지우던 코드가 병목이었다

코어 쪽에서 특히 인상적이었던 병목은 전체 삭제였다.

처음 AI의 도움 없이 직접 구현할 때는 삭제할 DOM마다 하나씩 `remove()`를 호출했다. 삭제 대상을 정확히 찾아서 각각 지우는 것이 가장 확실하다고 생각했다. 내가 보기에는 아주 정직한 구현이었다.

컴퓨터처럼 한 단계도 빠뜨리지 않고 정확하게 구현해야 한다는 강박이 있었던 것 같다. 각 항목을 제대로 처리하는 데 신경을 쓰다 보니, 부모 아래의 자식을 전부 지운다는 상황을 활용할 수 있다는 점은 보지 못했다.

그때 AI가 삭제 대상이 부모의 자식 전체라면 부모를 한 번 비우는 더 빠른 경로도 있다는 것을 알려줬다. 내가 정확하게 하려고 반복했던 호출들을 줄일 수 있었던 것이다. 다만 부모 안에 다른 내용이 함께 있으면 안 되므로, 삭제할 항목들이 부모의 전체 자식인지 확인하는 코드를 넣었다.

그런데 이번에는 그 빠른 경로를 쓰기 위한 확인 자체가 병목이 됐다. 문제는 이 확인이 호출되는 위치였다.

행이 컴포넌트이면 내부 Fragment를 지우면서 같은 함수에 반복해서 들어왔다. 그리고 그때마다 부모의 전체 자식을 다시 세었다.

```text
첫 번째 행을 지우기 전에 부모의 자식을 전부 확인
두 번째 행을 지우기 전에 남은 자식을 전부 확인
세 번째 행을 지우기 전에 남은 자식을 전부 확인
...
```

부모의 자식이 줄어드는 경우에도 확인 횟수는 대략 `n + (n - 1) + ... + 1`이다. 빠른 삭제가 가능한지 알아보는 준비 작업에서 O(n²) 비용이 생긴 것이다. 당시 프로파일에서는 전체 삭제 시간의 약 73%가 이 함수에 잡혔다.

우선 일괄 삭제 후보가 되는 경우에만 검사하고, 확인한 자식 수가 삭제 후보 수를 넘으면 바로 멈추도록 바꿨다. 삭제 후보가 두 개인데 실제 자식을 세 개 봤다면, 나머지 수천 개를 확인할 필요가 없다. 이미 부모 전체를 비울 수 없다는 결론이 났기 때문이다.

초기 수정의 4배 CPU 스로틀 프로파일에서 전체 삭제는 76.7ms에서 15.9ms로 줄었다. 공식 화면 시간과는 다른 진단값이지만, 반복 검사에 얼마나 많은 시간이 들어갔는지 보여 주는 결과였다. [삭제 병목과 수정 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/STATUS.md)

후속 구현에서는 개수 대신 실제 DOM이 일치하는지 확인하도록 바꿨다. 컴포넌트와 Fragment 안으로 들어가 삭제할 DOM을 찾고, 부모의 자식들과 순서대로 같은 객체인지 비교한다. 끝까지 일치할 때만 한 번에 비운다. 개수만 확인하던 방식에는 외부 코드가 자식 하나를 다른 DOM으로 바꿔 둬도 그 외부 노드까지 함께 지우는 문제가 있었다.

사실 처음 구현할 때부터 외부 코드가 바꾼 DOM까지 이렇게 대조하고 싶었던 것은 아니다. 라이브러리를 작게 유지하고 코드가 하는 일도 줄이는 쪽이 더 가성비 있다고 생각했다. 단순한 구현을 선택한 데는 그런 의도가 있었다.

이 확인도 공짜는 아니었다. 이미 한 번에 지울 수 있었던 일반 DOM 행에서는, 별도 교차 진단의 스크립트 시간이 약 1% 늘어나는 신호가 있었다. 공식 러너의 전체 삭제 시간은 실행 순서에 따라 증감 방향이 달라 확정적인 성능 저하로 보지는 않았다. 반면 컴포넌트로 감싼 행은 개별 DOM 삭제를 1,000번 하던 것을 한 번으로 줄일 수 있었고, 공식 러너의 전체 삭제 시간이 13.311ms에서 12.267ms로 약 7.84% 줄었다. [후속 삭제 구현의 이득과 비용](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/BULK_REMOVAL_V2_RESULTS.md)

부모를 통째로 비우면서 외부 DOM까지 지우지 않으려면, 그 자식들이 모두 삭제 대상이라는 확인은 필요했다. 이번에는 일반 DOM 행의 작은 추가 비용 가능성을 받아들이고, 컴포넌트 행의 일괄 삭제와 외부 노드 보존을 얻는 쪽을 선택했다. 검사는 첫 불일치에서 멈추도록 해, 결론이 난 뒤에도 남은 형제를 계속 확인하던 과거 문제는 피했다.

AI의 도움 없이 혼자 했다면 이번에도 가성비를 택하고 그 정도에서 멈췄을 것 같다. 하지만 AI가 이 부분을 끝까지 검토해 주지 않았다면, 개수는 같아도 실제 DOM은 다른 경우에 숨어 있던 버그를 찾지 못했을 것 같기도 하다.

## 이벤트를 하나도 빠짐없이 해제하려고 했다

이벤트 정리는 Lithent를 처음 구현할 때부터 특히 신경 썼던 부분이다.

`destroy()`를 호출하거나 컴포넌트의 생명주기가 끝나면, DOM에 붙여 둔 이벤트도 전부 해제하고 싶었다. `onClick`, `onInput`처럼 `on` 접두사로 전달받아 등록한 이벤트는 하나도 빠짐없이 `removeEventListener`를 호출하도록 했다. 자식 DOM까지 내려가며 빠뜨리는 이벤트가 없도록 구현하는 데 공을 들였다.

그런데 그렇게 신경 써서 만든 정리 작업이 전체 삭제의 병목 중 하나였다. 행마다 이벤트가 두 개씩만 있어도 1,000행을 지울 때 수천 번의 해제 호출이 더해진다. 화면에서 사라질 DOM을 순회하며 붙어 있는 이벤트를 일일이 떼고 있었던 것이다.

DOM과 그 리스너에 더 이상 도달할 수 없다면 함께 GC 대상이 될 수 있다. 버려지는 DOM의 이벤트를 모두 직접 해제하는 데 들인 작업을 줄일 여지가 있었다.

그래서 버려지는 일반 DOM에서는 개별 리스너 해제를 생략하도록 바꿨다. 이 변경만 비교한 새 페이지 12개의 진단에서는 전체 삭제 중앙값이 9.6ms에서 8.2ms로 줄었다. 공식 러너의 화면 시간과는 다른 수치지만, 이벤트를 하나씩 해제하던 작업에도 비용이 있었음을 확인할 수 있었다. [이벤트 해제 생략의 측정 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/STATUS.md#54-코어-버려지는-dom의-리스너-해제-제거--수정함-미커밋)

물론 DOM을 화면에서 떼었다는 이유만으로 메모리가 바로 회수되는 것은 아니다. 사용자가 제거한 DOM을 따로 보관하면 리스너도 남을 수 있고, 그 DOM에 이벤트를 보내면 핸들러가 실행될 수도 있다. 살아 있는 노드에서 핸들러가 바뀌거나 없어질 때의 해제, 컴포넌트 unmount 콜백, 계속 살아 있는 portal target의 이벤트 정리는 유지한다.

내가 꼼꼼하게 구현했다고 생각하던 코드가 실제로는 얼마나 자주 실행되는지 보면서, 한 가지에 집중할 때 내 시야가 얼마나 좁아질 수 있는지 실감했다. 이런 라이브러리를 만드는 일은 계산 과정과 동작의 정확성을 계속 따지게 되는데, 거기에 몰두하다 보니 숲을 보지 못했던 것 같다.

나는 평소 성실함에만 매몰돼 비효율적으로 일하게 되는 것을 경계한다. 같은 일도 더 영리하게 할 수 있는 방법을 찾으려고 노력하는 편이다. 그런데 한 가지에 너무 집중하면 나도 기계적으로 같은 처리를 반복하는 실수를 하게 되는 것 같다. 이벤트를 하나도 빠뜨리지 않고 해제하는 데 집중한 나머지, 그 일을 전부 직접 해야 하는지는 돌아보지 못했던 것이다.

## 한 줄짜리 함수가 메모리 회수를 늦추고 있었다

메모리 사용과 회수는 나도 처음부터 중요하게 생각했다. 테스트를 반복하면서 메모리 사용량이 계속 쌓이지 않도록 신경 써 왔다.

다만 사용이 끝난 메모리가 그 즉시 회수돼야 한다고 생각한 것은 아니다. 회수까지 어느 정도 유예가 생겨 중간에 메모리 사용량이 늘어나 보이는 것은 받아들이고 있었다.

그런데 이번에는 성능을 끝까지 끌어올리려고 반복 갱신을 더 집요하게 테스트하다 보니, 이전 화면의 메모리가 예상보다 오래 남는 문제를 발견하게 됐다.

1,000행을 유지하며 부분 갱신을 100회 반복한 뒤 GC를 해도 JS heap이 약 17.77MB까지 올라갔다. 생성하고 전부 지우는 몇 차례의 검사에서는 충분히 드러나지 않았던 문제였다.

관련된 코드는 부모를 찾아가는 getter였다. 가상 노드는 실제 DOM 부모와 삽입 위치를 찾을 때 이 함수를 사용한다.

아래는 당시 구조를 단순화한 예제다.

```ts
function reconcileChildren(newParent, oldParent) {
  const oldChildren = oldParent.children;
  const getParent = () => newParent;

  return newParent.children.map((child, index) => {
    return reconcile(child, oldChildren[index], getParent);
  });
}
```

겉으로는 `getParent`가 새 부모만 반환한다. 그런데 오래 살아 있는 이 getter와 이전 자식 배열을 사용하는 콜백이 같은 함수 스코프에서 만들어지고 있었다. 관찰한 실행 환경에서는 이 구조가 이전 VDOM의 참조를 필요 이상으로 오래 유지하는 경로와 연결돼 있었다.

수정은 부모 getter를 별도 함수에서 생성하는 것이었다.

```ts
const makeParentGetter = parent => () => parent;

// diff 함수 안에서는 부모만 전달한다.
const getParent = makeParentGetter(newParent);
```

반환하는 값은 같다. 함수가 만들어지는 환경을 분리했다.

같은 반복 갱신 조건에서 수정 후 JS heap은 약 **4.03MB**였다. WeakRef를 이용한 브라우저 검사에서도, 수정 전에는 50회 갱신한 과거 노드까지 남았지만 수정 후에는 현재 노드만 남는 것을 확인했다. [메모리 회수 측정과 검증](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/PRODUCTION_RESULTS.md#부모-getter-회수-수정)

가볍게 생각했던 클로저 함수 하나도 미세한 성능 차이를 따지는 상황에서는 문제가 될 수 있다는 걸 느꼈다. 중첩 함수를 줄이는 게 낫겠다는 생각도 들었지만, 그게 언제나 정답인지는 모르겠다. 생각보다 미묘했다.

## 객체를 깨끗하게 정리하는 데도 비용이 들었다

렌더러는 노드에 임시 정보를 붙인다. 이전 인덱스, 이전 props, 삭제할 자식 같은 정보다. 작업이 끝나면 더 이상 필요하지 않으니 지우는 것이 나에게는 자연스러운 정리 방법이었다.

```ts
delete node.oi;
delete node.op;
delete node.oc;
```

그런데 수많은 노드를 갱신할 때마다 속성을 추가하고 지우면 객체의 속성 구성이 반복해서 바뀔 수 있다. JavaScript 엔진이 속성 접근을 최적화하는 데도 이 구성이 영향을 준다.

`delete` 대신 `undefined`를 대입해 정리할 수 있다는 것은 이미 알고 있었다. 다만 내부 메타데이터를 반복해서 정리하는 이 경로에서, 그 선택이 성능에 얼마나 큰 차이를 만들 수 있는지는 AI 에이전트와 함께 최적화를 해 보면서 알게 됐다. 이번처럼 직접 바꾸고 측정해 보지 않았다면, 알고 있었어도 별로 신경 쓰지 않았을 것 같다. 내부 메타데이터는 속성의 자리를 유지하면서 값을 비우는 방식으로 바꿨다.

```ts
node.oi = node.op = node.oc = undefined;
```

값이 이전 객체의 참조였다면 `undefined`를 대입하는 것으로 연결을 끊을 수 있다. 이전 객체를 놓아 주는 일과 속성 자체를 없애는 일은 구분할 수 있었다. 이 내부 정보는 속성 자체를 없애야 할 필요가 없었다. 실제로 사라진 사용자 prop을 제거하는 일과는 구분해서 처리했다.

비슷한 반복 작업은 컴포넌트 props에도 있었다. 기존 객체의 key를 전부 지우고 새 값을 복사하던 것을, 사라진 key만 지우고 나머지 값은 갱신하도록 바꿨다. 컴포넌트가 클로저로 참조하는 props 객체는 유지하면서 불필요한 삭제와 재추가를 줄였다.

이후에는 element나 text처럼 종류마다 다르게 만들던 가상 DOM 객체를, 하나의 생성 함수에서 만들도록 바꿨다. 자주 쓰는 속성 13개를 같은 순서로 넣고, 아직 값이 없는 속성도 `undefined`로 미리 만들어 뒀다. JavaScript 엔진이 비슷한 구조의 객체를 계속 다루게 해서, 노드의 속성을 반복해서 읽고 쓰는 비용을 줄이려는 변경이었다. 컴포넌트나 root에서만 쓰는 나머지 속성은 필요한 노드에만 추가했다.

이런 부분은 AI가 알려주지 않았다면 쉽게 간과하거나, 아예 모르고 지나갔을 것 같다.

이 변경의 별도 비교에서 가중 전체 시간은 약 **5.9%**, JS 시간은 약 **14.4%** 줄었다. 대신 1만 행 메모리는 약 **2.5%**, 0.68MB 늘었다. 자리를 미리 잡아 두는 데 드는 비용도 있었던 셈이다. 모든 필드를 초기화하는 더 큰 안은 메모리 증가가 커서 선택하지 않았다. [노드 생성 구조 실험](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/NODE_SHAPE_RESULTS.md)

AI 에이전트가 여러 안을 비교하고 측정해 준 덕분에 이런 차이를 볼 수 있었다. 나는 그 결과를 보면서, 속도를 조금 더 얻기 위해 메모리와 번들 크기를 어디까지 늘려도 괜찮을지 생각해 보게 됐다. 당시에는 속도와 번들 크기의 균형을 우선으로 보고 있었기 때문에, 이 정도의 메모리 증가는 받아들이고 속도 개선을 선택했다.

## 이미 아는 사실을 매번 다시 계산하고 있었다

어느 정도 큰 계산 비용을 줄인 뒤에는 비교적 작은 부분에서도 성능을 개선할 여지를 찾았다. 물론 내가 찾은 건 아니고, AI가 찾아줬다. 😅

직접 가상 DOM diff를 구현할 때는 흐름이 조금만 틀어져도 자꾸 오동작해서 스트레스를 많이 받았다. 그래서 같은 조건을 한 번 더 확인하는 식으로 방어 로직을 정직하게 겹쳐 넣은 부분도 있었다. 그런 중복이 남아 있다는 건 나도 어느 정도 알고 있었다.

다만 그 작은 확인들이 미세한 속도 차이에까지 영향을 줄 거라고는 생각하지 못했다.

새 노드를 추가할 때도 타입 비교를 수행하던 부분이 있었다. 이전 노드가 없는데 새 노드와 이전 노드의 타입이 같은지 확인하고 있었던 것이다. 여기에 이전 노드가 있을 때만 비교하도록 조건을 붙였다.

```ts
const sameType = !!originalWDom && compareType(newWDom, originalWDom);
```

수정은 작지만 호출 횟수가 컸다. 당시 1만 행 생성의 자식 diff 준비는 약 10만 번 실행됐다. 별도의 공식 러너 비교에서 1,000행 생성의 JS 시간은 약 4.5% 줄었다. 브라우저 렌더링을 포함한 전체 시간 감소는 약 1.0%였다. [생성 경로 프로파일과 비교](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/CREATION_PROFILE.md)

목록 갱신에서도 비슷한 일이 있었다. 행 하나를 선택할 뿐이라면 목록 순서는 그대로고, 대부분의 행은 내용도 바뀌지 않는다. 그런데 매번 항목을 다시 찾고, 옮길 일이 있는지 계산할 준비까지 하고 있었다.

각 단계에서 이미 알 수 있는 사실을 조금 더 일찍 활용하도록 바꿨다.

항목의 위치를 굳이 다시 찾을 필요가 없을 때는 탐색을 건너뛰었다. 순서가 유지된 목록은 재배치 준비를 건너뛰고, 캐시에서 그대로 돌아온 객체는 내용을 다시 비교하지 않도록 했다. 조건이 맞지 않으면 기존 방식으로 처리한다.

나는 보통 개발할 때 만들어 놓은 함수를 최대한 재사용한다. 같은 일을 할 때마다 다시 생각하고 구현하는 부담을 줄이고 싶어서다. 그게 개발할 때는 확실히 도움이 되지만, 성능까지 좋아지는 것은 아니라는 걸 이번에 느꼈다. 내가 다시 생각할 일을 줄였어도, 컴퓨터는 그 함수 안에서 같은 계산을 계속하고 있었다.

이걸 보면서 성실함에도 멍청한 성실함과 영리한 성실함이 있겠다는 생각이 들었다. 한 번 성실하게 확인해 둔 덕분에 다음부터는 같은 일을 반복하지 않아도 되는 쪽이 영리한 성실함인 것 같다.

이런 작은 작업을 줄이는 최신 변경들을 묶어 공식 러너로 로컬 비교한 결과, 가중 전체 시간은 **2.59%** 줄었다. 부분 갱신은 **9.21%**, 선택은 **12.91%** 줄었다. [최신 최적화 묶음의 측정 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/POSITIONAL_KEYS_OFFICIAL_RESULTS.md)

내가 대수롭지 않게 생각했던 작은 확인도 컴퓨터는 빠짐없이 반복하고 있었다. 정말 컴퓨터는 정직하다.

## 그럴듯한 최적화도 되돌렸다

AI의 도움으로 후보를 만들기는 훨씬 수월해졌다. 그러다 보니 채택 여부를 판단하는 일이 더 중요해졌다.

안정적인 event proxy도 그중 하나였다. DOM에는 같은 함수를 등록해 두고 실제로 호출할 handler만 교체하면, 렌더마다 새로운 inline handler를 만드는 UI의 리스너 재등록을 줄일 수 있다. 실제로 그런 UI에서는 이득이 관찰됐다.

하지만 이미 handler를 재사용하는 벤치마크 앱의 선택과 부분 갱신에서는 리스너 재등록이 0이었다. 그 앱은 proxy가 줄이려는 비용을 지불하고 있지 않았다. proxy의 크기와 메모리, native 이벤트 연동 비용을 함께 검토한 뒤 기본 구현은 원래 callback을 직접 등록하는 방식으로 돌아갔다. [이벤트 구현 복원 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/NATIVE_EVENTS_RESULTS.md)

반대로 작은 최적화의 이득을 측정에서 확신하기 어려운 경우도 있었다. JS 실행 시간이 줄어도 전체 화면 시간은 스타일·레이아웃·페인트와 대기의 영향을 받는다. 일부 선택 측정에서는 러너의 강제 GC가 끝나는 시점에 따라 다음 프레임까지 기다리는 시간이 달라졌다. 삭제 코드를 바꿨는데 선택 결과가 달라졌다면, 그 숫자를 곧바로 삭제 수정의 효과라고 해석할 수 없었다.

측정 도중 두 차수 사이에 Chrome이 자동 업데이트된 일도 기록에 남아 있다. 이 결과는 같은 조건의 표본으로 합치지 않았고, 후속 실험에서는 브라우저 실행 파일을 고정하고 해시를 확인하도록 했다.

그래서 같은 앱과 helper를 유지한 채 코어를 비교하고, 실행 순서를 바꿔 다시 재고, 실제로 어떤 번들을 측정했는지 남기는 작업이 뒤따랐다. DOM 정체성, 입력 포커스, 생명주기와 메모리 회수도 함께 검사했다. 벤치마크를 빠르게 끝내는 동안 원래 동작을 잃어버리면 채택할 수 없기 때문이다.

이 글에 나온 개선율들도 각자 다른 시점의 비교다. 앱 변경의 13.8%, 노드 생성 구조의 5.9%, 최신 묶음의 2.59%를 더해서 전체 개선율로 만들 수는 없다. 측정 기록을 남긴 덕분에 지금 다시 글을 쓰면서도 어디까지 말할 수 있는지 확인할 수 있었다.

## 작은 차이를 파고드는 재미

사실 처음에는 이런 렌더링 성능 측정을 내심 우습게 여기기도 했다. 사람들이 아주 미세한 시간 차이까지 따지는 게 그렇게 중요한가 싶었다. 이미 주류가 된 React도 이런 벤치마크에서 빠르기만 한 것은 아니다. 이번에 남긴 로컬 비교에서도 React는 행 교환과 1만 행 생성에서 상대적으로 느렸다. [당시 React·Preact 비교 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/PEER_BASELINE_RESULTS.md#cpu-전체-시간과-목표)

그런데 직접 렌더링 성능에 집중하다 보니, 그 차이를 파고드는 재미가 있었다. 아주 사소해 보이는 함수 처리 하나도 반복되면 지연을 만들고, 미세한 성능 차이로 나타난다는 것을 알게 됐다. 매번 만들던 함수나 배열, 이미 결론이 났는데도 계속하던 검사를 따라가면서 내가 만든 코드가 실제로 얼마나 많은 일을 하고 있었는지 보게 됐다.

삭제할 DOM을 하나씩 지우고 이벤트를 빠짐없이 해제하려고 공들였는데, 그 부분들이 병목이었다는 점이 특히 아이러니했다. 내가 정확하게 한다고 신경 쓴 작업을 줄여도 필요한 결과를 얻을 수 있다는 것이 신기했다. 이미 알고 있던 `undefined` 대입이 실제 성능 차이로 이어지는 것도 확인했고, 부모 getter를 만드는 위치가 이전 화면의 수명을 바꾸는 것도 봤다. 코드를 바꾸고 다시 측정하면서, 왜 차이가 생겼는지 이해해 가는 과정 자체가 재미있었다.

그래도 이런 미세한 속도 차이보다 프레임워크의 예측 가능성과 동작의 투명성이 더 중요하다는 생각에는 변함이 없다. 어떤 상태에서 무엇이 갱신되는지 예상할 수 있고, 왜 그런 동작을 하는지 코드를 따라가며 이해할 수 있는 쪽을 더 중요하게 생각한다.

그 생각을 유지하면서도, 작은 비용을 찾아 하나씩 줄여 보는 일에는 예상하지 못했던 재미가 있었다.
