# js-framework-benchmark에 등재하기 위한 Lithent 성능 개선기

직접 만든 UI 라이브러리 Lithent를 `js-framework-benchmark`에 올려 보고 싶었다.

평소에 예제를 돌려 보는 것과, 같은 화면에서 다른 라이브러리들과 나란히 측정되는 것은 꽤 다른 일이었다. 행 1,000개를 만들고, 일부 텍스트를 바꾸고, 행 하나를 선택하고, 두 행을 교환하고, 전부 지운다. 화면만 보면 단순한 테이블인데, 그 뒤에서 라이브러리가 무슨 일을 얼마나 하는지가 숫자로 드러났다.

먼저 밝혀 둘 게 있다. 이 성능 개선 과정에서는 AI의 도움을 아주 많이 받았다. 병목 후보를 찾고, 코드를 바꾸고, 테스트와 벤치마크를 만드는 과정까지 큰 도움을 받았다. 개선된 코드를 모두 처음부터 이해하고 진행한 것도 아니었다. 결과가 쌓인 뒤에야 변경 이력과 측정 기록을 다시 따라가며 공부하게 된 부분도 많다.

그 기록을 돌아보니 기억에 남는 장면들이 있었다. 알고리즘을 바꿔 빨라진 부분도 있지만, 빠르게 처리하려고 넣었던 검사나 꼼꼼하게 정리하던 코드가 오히려 병목이 된 경우도 있었다. 한 줄짜리 함수를 만드는 위치를 옮겼더니 이전 화면의 메모리가 회수되기도 했다.

이번 글에서는 등재를 준비하며 발견한 그런 사례들을 골라 보려고 한다. 수치는 당시 공식 러너를 로컬에서 실행한 비교와 별도의 진단 기록이다. 공개된 공식 순위나 등재 완료를 뜻하지는 않는다.

## LIS를 넣었는데도 행 하나를 선택하는 일이 무거웠다

출발점에는 리스트 비교 알고리즘이 있었다.

이전 구현은 새 항목마다 이전 배열에서 같은 key를 찾았다. 긴 배열을 반복해서 탐색하니 행이 많아질수록 비용이 가파르게 늘었다. 이를 Map 기반 매칭으로 바꾸고, 순서가 바뀔 때는 LIS, 즉 최장 증가 부분 수열을 이용해 그대로 둘 항목을 골랐다.

예를 들어 아래 목록에서 B와 D의 위치를 바꾼다고 하자.

```text
이전: A B C D E
이후: A D C B E
```

A, C, E의 상대 순서는 이미 맞는다. 이 항목들은 두고 B와 D만 옮기면 된다. LIS는 이렇게 유지할 수 있는 항목들을 찾는 데 사용한다. 내용 갱신과 DOM 위치 변경을 나누고, 필요한 항목만 이동하도록 만든 것이다.

이렇게 큰 알고리즘 문제를 해결한 뒤에도, 행 하나를 선택하는 작업에는 비용이 남아 있었다.

선택 표시가 A행에서 B행으로 옮겨 가면 실제로 달라지는 행은 두 개다. 그런데 기존 벤치마크 앱은 부모를 갱신할 때 모든 행 컴포넌트를 다시 실행하고, 이벤트 함수와 가상 DOM도 새로 만들고 있었다. DOM을 최소한으로 옮겨도 그전에 JavaScript가 해야 할 일이 많았다.

그래서 기존 helper인 `cacheUpdate`를 행에 적용했다. 라벨과 선택 여부가 그대로면 이전 가상 DOM을 반환하고, 행의 이벤트 핸들러도 한 번 만들어 재사용하도록 했다.

여기서 한 번 더 들여다봐야 할 부분이 있었다. 캐시가 적중해도 **캐시에 도달하기까지 드는 비용**은 남아 있었다.

당시 구조는 행마다 별도의 컴포넌트였다. 부모 갱신 때 각 행의 props를 동기화하고, 컴포넌트 갱신을 준비하고, 그 뒤에 출력 캐시를 확인했다. 1,000행의 선택을 바꾸는 진단에서 props 동기화와 래퍼 생성 등이 각각 1,001회 발생했다. 부모 한 번과 모든 행을 통과하고 있었던 것이다.

벤치마크 앱에서는 행마다 독립적인 컴포넌트 수명을 둘 필요가 크지 않았다. 그래서 Table 안에 행별 캐시를 두고, 캐시가 keyed `tr`를 반환하도록 구성을 바꿨다.

```text
변경 전: Table → 행 컴포넌트 → 행 캐시 → tr
변경 후: Table → 행 캐시 → tr
```

같은 코어를 사용해 앱 전후를 비교한 결과는 꽤 컸다.

| 동작      |  변경 전 |  변경 후 | 전체 시간 감소 |
| --------- | -------: | -------: | -------------: |
| 부분 갱신 | 22.100ms | 17.592ms |          20.4% |
| 행 선택   | 10.136ms |  7.460ms |          26.4% |
| 전체 삭제 | 18.713ms | 10.996ms |          41.2% |

이 앱 변경 묶음의 가중 지표는 약 13.8% 줄었다. 캐시와 행 경계, 핸들러 등을 함께 정리한 결과이므로 컴포넌트 하나를 없애서 전부 얻은 효과로 볼 수는 없다. 그래도 렌더러를 더 고치기 전에 앱이 라이브러리를 어떻게 사용하고 있는지 살펴볼 이유는 충분했다. [앱 전후 측정 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/PRODUCTION_RESULTS.md)

행이 독립적인 상태와 생명주기를 가져야 한다면 컴포넌트 경계는 필요하다. 이번에 배운 것은 그 경계와 캐시가 생략하는 범위를 구체적으로 봐야 한다는 점이었다. 캐시가 있다는 사실만으로 그 앞의 작업까지 없어지지는 않았다.

## 삭제를 빠르게 하려고 넣은 검사가 삭제를 느리게 했다

코어 쪽에서 특히 인상적이었던 병목은 전체 삭제였다.

부모 아래의 자식을 모두 지운다면, 각 항목마다 `remove()`를 호출하는 대신 부모를 한 번 비우는 빠른 경로를 사용할 수 있다. 다만 부모 안에 다른 내용이 함께 있으면 안 된다. 그래서 삭제할 항목들이 부모의 전체 자식인지 확인하는 코드를 넣었다.

문제는 이 확인이 호출되는 위치였다.

행이 컴포넌트이면 내부 Fragment를 지우면서 같은 함수에 반복해서 들어왔다. 그리고 그때마다 부모의 전체 자식을 다시 세었다.

```text
첫 번째 행을 지우기 전에 부모의 자식을 전부 확인
두 번째 행을 지우기 전에 남은 자식을 전부 확인
세 번째 행을 지우기 전에 남은 자식을 전부 확인
...
```

부모의 자식이 줄어드는 경우에도 확인 횟수는 대략 `n + (n - 1) + ... + 1`이다. 빠른 삭제가 가능한지 알아보는 준비 작업에서 O(n²) 비용이 생긴 것이다. 당시 프로파일에서는 전체 삭제 시간의 약 73%가 이 함수에 잡혔다.

우선 일괄 삭제 후보가 되는 경우에만 검사하고, 확인한 자식 수가 삭제 후보 수를 넘으면 바로 멈추도록 바꿨다. 삭제 후보가 두 개인데 실제 자식을 세 개 봤다면, 나머지 수천 개를 확인할 필요가 없다. 이미 부모 전체를 비울 수 없다는 결론이 났기 때문이다.

초기 수정의 4배 CPU 스로틀 프로파일에서 전체 삭제는 76.7ms에서 15.9ms로 줄었다. 공식 화면 시간과는 다른 진단값이지만, 반복 검사에 얼마나 많은 시간이 들어갔는지 보여 주는 결과였다. [삭제 병목과 수정 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/STATUS.md)

후속 구현은 자식 수를 세는 방식에서도 더 나아갔다. 컴포넌트와 Fragment 안으로 들어가 삭제할 실제 DOM을 확인하고, 부모의 자식들과 순서대로 같은 객체인지 비교한다. 끝까지 일치할 때만 한 번에 비운다. 외부 코드가 자식 하나를 다른 DOM으로 바꿔 둔 경우에도 개수만 같다고 함께 지우는 일을 막는다.

꼼꼼하게 하려던 또 다른 작업은 이벤트 정리였다. 과거에는 버릴 DOM을 내려가며 이벤트 리스너도 하나씩 해제했다. 행마다 이벤트가 두 개씩 있으면 1,000행을 지울 때 수천 번의 해제 호출이 더해진다.

지금은 버려지는 일반 DOM의 리스너를 그대로 두고 DOM을 제거한다. DOM과 리스너에 더 이상 도달할 수 없으면 함께 GC 대상이 될 수 있기 때문이다. 살아 있는 노드에서 핸들러가 바뀌거나 없어질 때의 해제, 컴포넌트 unmount, 계속 살아 있는 portal target의 정리는 유지한다. 사용자가 제거한 DOM을 따로 보관하면 그 핸들러도 남을 수 있다는 동작 차이도 있다.

삭제에서는 확인과 정리가 필요한 대상, 그리고 결론을 내리는 데 필요한 범위를 구체적으로 정하는 것이 중요했다. 부모 전체를 매번 검사하고, 사라질 노드까지 전부 손으로 정리하는 방식에는 생각보다 큰 비용이 있었다.

## 한 줄짜리 함수가 이전 화면을 붙잡고 있었다

시간이 줄어든 뒤에도 반복 갱신을 해 보면 다른 문제가 드러났다. 화면에는 같은 수의 행이 있는데 메모리는 계속 늘었다.

1,000행을 유지하며 부분 갱신을 100회 반복한 뒤 GC를 해도 JS heap이 약 17.77MB까지 올라갔다. 생성하고 전부 지우는 몇 차례의 검사에서는 충분히 드러나지 않았던 문제였다.

관련된 코드는 부모를 찾아가는 getter였다. 가상 노드는 실제 DOM 부모와 삽입 위치를 찾을 때 이 함수를 사용한다.

아래는 당시 구조를 단순화한 예제다.

```ts
function reconcileChildren(newParent, oldParent) {
  const oldChildren = oldParent.children;
  const getParent = () => newParent;

  return newParent.children.map((child, index) => {
    return reconcile(child, oldChildren[index], getParent);
  });
}
```

겉으로는 `getParent`가 새 부모만 반환한다. 그런데 오래 살아 있는 이 getter와 이전 자식 배열을 사용하는 콜백이 같은 함수 스코프에서 만들어지고 있었다. 관찰한 실행 환경에서는 이 구조가 이전 VDOM을 계속 도달 가능하게 만드는 보유 경로와 연결돼 있었다.

수정은 부모 getter를 별도 함수에서 생성하는 것이었다.

```ts
const makeParentGetter = parent => () => parent;

// diff 함수 안에서는 부모만 전달한다.
const getParent = makeParentGetter(newParent);
```

반환하는 값은 같다. 함수가 만들어지는 환경을 분리했다.

같은 반복 갱신 조건에서 수정 후 JS heap은 약 **4.03MB**였다. WeakRef를 이용한 브라우저 검사에서도, 수정 전에는 50회 갱신한 과거 노드까지 남았지만 수정 후에는 현재 노드만 남는 것을 확인했다. [메모리 회수 측정과 검증](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/PRODUCTION_RESULTS.md#부모-getter-회수-수정)

이 경험을 “클로저는 스코프의 모든 변수를 항상 붙잡는다”는 규칙으로 외우면 부정확하다. 엔진과 빌드의 영향을 받는 부분이고, 이번 판단의 근거는 실제 보유 현상과 수정 전후의 회수 검증이었다.

코드 한 줄의 크기와 그 코드가 살아 있는 동안 붙잡는 객체의 크기는 전혀 다를 수 있었다. 작은 함수 하나를 이해하려고 해도, 그 함수가 어떤 환경에서 만들어지고 어디에 보관되는지까지 봐야 했다.

## 객체를 깨끗하게 정리하는 데도 비용이 들었다

렌더러는 노드에 임시 정보를 붙인다. 이전 인덱스, 이전 props, 삭제할 자식 같은 정보다. 작업이 끝나면 더 이상 필요하지 않으니 지우는 것이 자연스러워 보인다.

```ts
delete node.oi;
delete node.op;
delete node.oc;
```

그런데 수많은 노드를 갱신할 때마다 속성을 추가하고 지우면 객체의 속성 구성이 반복해서 바뀔 수 있다. JavaScript 엔진이 속성 접근을 최적화하는 데도 이 구성이 영향을 준다.

그래서 내부 메타데이터는 속성의 자리를 유지하면서 값을 비우는 방식으로 바꿨다.

```ts
node.oi = node.op = node.oc = undefined;
```

값이 이전 객체의 참조였다면 `undefined`를 대입하는 것으로 연결을 끊을 수 있다. 이 내부 정보는 속성 자체를 없애야 할 필요가 없었다. 실제로 사라진 사용자 prop을 제거하는 일과는 구분해서 처리했다.

비슷한 반복 작업은 컴포넌트 props에도 있었다. 기존 객체의 key를 전부 지우고 새 값을 복사하던 것을, 사라진 key만 지우고 나머지 값은 갱신하도록 바꿨다. 컴포넌트가 클로저로 참조하는 props 객체는 유지하면서 불필요한 삭제와 재추가를 줄였다.

이 방향은 이후 노드 생성 방식의 개선으로 이어졌다. element, text, Fragment 등을 각각 다른 형태의 객체로 만들던 것을 공통 팩토리로 모으고, 자주 쓰는 필드 13개를 같은 순서로 생성했다. 자주 쓰는 필드는 처음부터 자리를 잡고, 컴포넌트와 root에만 필요한 드문 필드는 별도로 둔 것이다.

이 변경의 별도 비교에서 가중 전체 시간은 약 **5.9%**, JS 시간은 약 **14.4%** 줄었다. 대신 1만 행 메모리는 약 **2.5%**, 0.68MB 늘었다. 자리를 미리 잡아 두는 데 드는 비용도 있었던 셈이다. 모든 필드를 초기화하는 더 큰 안은 메모리 증가가 커서 선택하지 않았다. [노드 생성 구조 실험](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/NODE_SHAPE_RESULTS.md)

여기서도 설명을 과장하면 안 된다. 기존 노드들이 전부 dictionary mode였다는 진단 결과는 없었다. 실제 관찰에서는 기존 노드도 fast properties를 유지했다. 객체 구성의 다양성을 줄인 뒤 엔진 진단의 변화와 실제 CPU 개선이 함께 관찰됐다는 정도로 이해하고 있다.

메모리를 덜 쓰는 것과 더 빨리 처리하는 것 사이에는 선택이 필요했다. 모든 필드를 지우는 방식이나 모든 필드를 미리 넣는 방식 중 어느 한쪽을 원칙으로 정하기보다, 자주 실행되는 코드에서 어떤 비용을 지불하는지 측정해야 했다.

## 이미 아는 사실을 매번 다시 계산하고 있었다

큰 반복 순회를 줄인 뒤에는 더 작은 중복 작업들이 눈에 들어왔다.

새 노드를 추가할 때도 타입 비교를 수행하던 부분이 있었다. 이전 노드가 없는데 새 노드와 이전 노드의 타입이 같은지 확인하고 있었던 것이다. 여기에 이전 노드가 있을 때만 비교하도록 조건을 붙였다.

```ts
const sameType = !!originalWDom && compareType(newWDom, originalWDom);
```

수정은 작지만 호출 횟수가 컸다. 당시 1만 행 생성의 자식 diff 준비는 약 10만 번 실행됐다. 별도의 공식 러너 비교에서 1,000행 생성의 JS 시간은 약 4.5% 줄었다. 브라우저 렌더링을 포함한 전체 시간 감소는 약 1.0%였다. [생성 경로 프로파일과 비교](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/CREATION_PROFILE.md)

목록 갱신에서도 비슷한 일이 있었다. 예를 들어 행 하나를 선택하는 순간을 따라가 보자.

목록의 key와 순서는 그대로다. 대부분의 행은 캐시에서 같은 가상 노드가 돌아온다. 그런데 기존 경로는 key Map을 만들고, 이전 인덱스를 배열에 담고, 배치 준비를 한 뒤에야 이동할 일이 없다는 결론에 도달했다.

각 단계에서 이미 알 수 있는 사실을 조금 더 일찍 활용하도록 바꿨다.

이전 매칭에서 key의 유일성이 확인된 목록은 같은 위치의 key부터 비교한다. 일치하는 동안에는 위치로 짝을 찾고, 처음 어긋날 때 남은 원본으로 Map을 만든다. 아직 유일성이 확인되지 않은 목록은 기존 Map 경로를 사용한다. key를 안정적으로 유지한다는 조건도 필요하다.

배치 쪽에서는 추가나 교체가 없고 이전 인덱스의 순서가 유지되면, LIS용 배열을 만들기 전에 현재 위치에서 자식을 갱신한다. LIS를 계산하지 않는 데서 한 걸음 더 나아가 계산 준비도 줄인 것이다.

캐시가 같은 위치의 동일한 nonempty 가상 노드를 반환하면 diff 입구에서 바로 반환한다. 같은 객체를 자신과 비교하고, 변경 없음 표시를 붙이기 위해 여러 단계를 통과할 필요를 줄였다.

작업을 생략하는 데는 근거가 필요했다. 아무 목록이나 위치로 매칭할 수는 없고, 같은 key라는 이유만으로 같은 객체처럼 취급할 수도 없다. 조건이 확인된 경로를 짧게 만들고, 그렇지 않으면 일반 처리로 돌아가게 했다. 목록 전체를 방문하는 O(n) 비용은 여전히 남는다.

일반 HTML 태그의 custom element 확인을 줄이는 수정까지 함께 적용한 최신 묶음은 580표본의 로컬 공식 러너 비교에서 가중 전체 시간이 **2.59%** 줄었다. 부분 갱신은 **9.21%**, 선택은 **12.91%** 줄었다. 네 변경을 함께 측정한 결과이며 각 수정 하나의 독립 효과는 아니다. [최신 최적화 묶음의 측정 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/POSITIONAL_KEYS_OFFICIAL_RESULTS.md)

이 단계에서는 큰 알고리즘 이름보다, 매번 반복하는 준비 작업이 더 중요해졌다. 결과가 그대로라는 사실을 충분히 일찍 알 수 있다면 그 뒤의 일을 줄일 수 있었다.

## 그럴듯한 최적화도 되돌렸다

AI의 도움으로 후보를 만들기는 훨씬 수월해졌다. 그러다 보니 채택 여부를 판단하는 일이 더 중요해졌다.

안정적인 event proxy도 그중 하나였다. DOM에는 같은 함수를 등록해 두고 실제로 호출할 handler만 교체하면, 렌더마다 새로운 inline handler를 만드는 UI의 리스너 재등록을 줄일 수 있다. 실제로 그런 UI에서는 이득이 관찰됐다.

하지만 이미 handler를 재사용하는 벤치마크 앱의 선택과 부분 갱신에서는 리스너 재등록이 0이었다. 그 앱은 proxy가 줄이려는 비용을 지불하고 있지 않았다. proxy의 크기와 메모리, native 이벤트 연동 비용을 함께 검토한 뒤 기본 구현은 원래 callback을 직접 등록하는 방식으로 돌아갔다. [이벤트 구현 복원 기록](https://github.com/superlucky84/lithent/blob/d594983/docs/benchmark/NATIVE_EVENTS_RESULTS.md)

반대로 작은 최적화의 이득을 측정에서 확신하기 어려운 경우도 있었다. JS 실행 시간이 줄어도 전체 화면 시간은 스타일·레이아웃·페인트와 대기의 영향을 받는다. 일부 선택 측정에서는 러너의 강제 GC가 끝나는 시점에 따라 다음 프레임까지 기다리는 시간이 달라졌다. 삭제 코드를 바꿨는데 선택 결과가 달라졌다면, 그 숫자를 곧바로 삭제 수정의 효과라고 해석할 수 없었다.

측정 도중 두 차수 사이에 Chrome이 자동 업데이트된 일도 기록에 남아 있다. 이 결과는 같은 조건의 표본으로 합치지 않았고, 후속 실험에서는 브라우저 실행 파일을 고정하고 해시를 확인하도록 했다.

그래서 같은 앱과 helper를 유지한 채 코어를 비교하고, 실행 순서를 바꿔 다시 재고, 실제로 어떤 번들을 측정했는지 남기는 작업이 뒤따랐다. DOM 정체성, 입력 포커스, 생명주기와 메모리 회수도 함께 검사했다. 벤치마크를 빠르게 끝내는 동안 원래 동작을 잃어버리면 채택할 수 없기 때문이다.

이 글에 나온 개선율들도 각자 다른 시점의 비교다. 앱 변경의 13.8%, 노드 생성 구조의 5.9%, 최신 묶음의 2.59%를 더해서 전체 개선율로 만들 수는 없다. 측정 기록을 남긴 덕분에 지금 다시 글을 쓰면서도 어디까지 말할 수 있는지 확인할 수 있었다.

## 등재를 준비하며 내 라이브러리를 다시 읽게 됐다

이 작업은 Lithent를 다른 라이브러리들과 같은 조건에서 측정해 보고 싶다는 생각으로 시작했다. 그 과정에서 작은 테이블 하나가 꽤 많은 질문을 던졌다.

행 하나를 선택하는데 왜 모든 행의 갱신 준비를 하는지, 삭제를 빠르게 하려는 검사가 왜 매번 전체 형제를 세는지, 부모만 반환하는 함수가 어떤 환경에서 만들어지는지. 평소에는 쉽게 지나쳤을 코드들이 벤치마크와 반복 갱신 앞에서 비용을 드러냈다.

AI는 그 질문들을 탐색하고 구현과 검증을 진행하는 데 큰 도움이 됐다. 그 도움으로 바뀐 코드들을 다시 읽으면서, 가상 DOM이 실제 DOM으로 반영되기까지의 과정과 객체가 메모리에 남는 이유를 구체적으로 배우고 있다.

특히 오래 남을 것 같은 장면은 삭제 전의 반복 검사와 부모 getter 수정이다. 삭제할 때의 조심스러운 확인이 가장 비싼 작업이었고, 한 줄짜리 함수를 만드는 위치가 이전 화면의 수명을 바꿨다. 성능 개선 기록을 다시 읽는 재미도 그런 곳에 있었다.

이제 성능을 살펴볼 때는 함수의 길이보다 그 함수가 몇 번 호출되는지, 임시 객체가 얼마나 생기는지, 필요한 일이 끝난 뒤에도 어떤 참조가 남는지를 함께 보게 된다. 등재를 준비하며 얻은 것은, 측정 결과와 실제 코드를 연결해서 읽을 수 있는 구체적인 사례들이었다.
